# series-curriculum-design skill

規劃「導讀系列」或「學習路徑」類的系列文時，在開始寫之前先跑這套流程。
核心原則：**用學習者的旅程排序，不用教授的知識分類排序。**

## 課程導讀共用規格

課程系列先直接讀 `../post/references/course-guide-contract.md`，在規劃表分開記原課堂次／週次／作業與本站 order。中文完整標題採主題前置、課程「第 N 堂」後置，不把 order 直接翻成堂次。每篇範圍卡補例子與檢驗目標的問題／答案。

岩場系列（一篇一個岩場）規劃時讀 `../post/references/crag-guide-contract.md`，規劃表的每篇結構照它的固定 H2 與依程度路線表。

單篇課程教學重構也套用範圍卡、先備橋接與角色檢查；不為單篇任務重排整個系列。一般獨立文與僅來源更新仍走 post／post-update。

## 步驟一：列出主題與依賴

1. 把所有預定主題列成表（order / 主題 / 狀態 / 對應來源）
2. 畫依賴關係：B 需要先讀 A 才懂 → A 必須在 B 前面
3. 標記每篇的**目標讀者狀態**：讀完這篇後，讀者會知道什麼、能做什麼

## 步驟二：排弧線

按**學習者的認知順序**排，不是按知識的邏輯分類排。

### 弧線原則

| 原則 | 說明 | 反例 |
|---|---|---|
| 可見先於不可見 | 先教看得到摸得到的（token、輸出），再教內部機制（梯度、loss） | 第一篇就講反向傳播 |
| 動機先於抽象 | 先讓讀者感受到「為什麼需要這個」，再教這個東西 | 還沒解釋模型會犯錯，就教 loss function |
| 一次一個跳躍 | 每篇只引入一個新的核心概念，不同時塞兩個 | Transformer 篇同時教 attention + 位置編碼 + layer norm |
| 具體→半形式→形式 | 類比和圖在前，公式在折疊區或連結 | 開頭就貼數學定義 |
| 螺旋式加深 | 同一概念可以在不同篇出現，每次加深一層 | RLHF 只出現一次就要全部講完 |

### 弧線模板（依主題調整，不要硬套）

```
基礎概念（看得到的東西）
  → 表示（資料怎麼被編碼）
    → 學習（模型怎麼從錯誤中改進）
      → 架構（用什麼結構來學）
        → 規模（變大會怎樣）
          → 評估（怎麼判斷好壞）
            → 進階（特殊技巧）
              → 實用（實際怎麼用）
```

## 步驟三：找斷崖

逐對檢查相鄰兩篇之間的**認知跳躍**。

### 斷崖診斷清單

| 訊號 | 處理 |
|---|---|
| 前一篇全是概念性的，下一篇突然需要數學思維 | 插入橋接篇或在該篇加「直覺先行」段落 |
| 一篇裡同時引入 ≥ 2 個全新的核心概念 | 自行規劃的系列：拆成兩篇。課程系列：維持一堂一篇，篇內分節並補橋接段（見 `course-guide-contract.md`） |
| 標題用了前面沒出現過的術語 | 要嘛前面先鋪墊，要嘛標題改成白話 |
| 讀者需要前置知識但系列裡沒教 | 加站內連結指向對應課程導讀（如 CS109） |

### 輸出格式

```
斷崖報告：
| 位置 | 問題 | 建議處理 |
|---|---|---|
| order 3→4 | 從概念跳到數學 | 拆 order 4 為兩篇 |
| order 5 | 認知負荷過高 | 正文只講核心直覺，細節折疊 |
```

## 步驟四：定每篇的內容範圍

逐篇檢查，為每篇定一個**聚焦問題**和**邊界**。

### 範圍卡格式

```
Order N：標題
  聚焦問題：這篇要回答讀者的什麼問題？（一句話）
  邊界：
    - 講：___
    - 不講（留給其他篇或折疊區）：___
  讀完後讀者能：___（一個具體能力）
  原課範圍：___（不能由 order 推算）
  例子／推導：___
  自我檢查與答案／判準：___
  前置：需要先讀 order ___
  連結：碰到 X 概念 → 連回 ___（站內課程導讀）
```

### 常見的範圍問題

| 問題 | 怎麼修 |
|---|---|
| 一篇塞太多主題 | 砍到一個聚焦問題，其餘拆出去或放折疊；課程系列的單堂多主題例外，在篇內分節，不拆篇 |
| 標題承諾的比內容廣 | 縮標題，或擴內容（通常縮標題比較對） |
| 內容跟其他篇重疊 | 決定誰講、誰連結，不要兩篇都講一半 |
| 「已寫」的篇章位置不對 | 調 order，不要為了遷就已寫的文章扭曲弧線 |

## 步驟五：定硬文章的內部結構

認知負荷高的篇章（涉及數學、架構、抽象概念），統一用這個五層結構：

1. **場景**——一個讀者熟悉的模型行為當 hook（「為什麼 ChatGPT 有時會重複自己？」）
2. **直覺**——類比或圖解，零公式（「想像你在山谷裡找最低點…」）
3. **機制**——半形式化說明，用圖 + 文字，公式放 `<details>` 折疊
4. **連回模型**——「所以你用 Claude 時看到的 XX，就是這個在運作」
5. **想深入**——連結站內課程導讀（CS109、CS224N、CS336 等）

概念性的篇章（tokenization、授權、API 比價）不需要這個結構，用自然的說明順序即可。

## 步驟六：輸出完整規劃表

最終產出格式：

```markdown
## 系列名：___
目標讀者：___
總篇數：___（order 0–N）
弧線：___→___→___→…
入口：order 0 是___（總覽／入門：這個領域是什麼、整個流程、每篇在流程哪一段、讀完能做到什麼）

| order | 主題 | 聚焦問題 | 狀態 | 對應來源 |
|---|---|---|---|---|
| 0 | ... | ... | 待寫 | — |
| 1 | ... | ... | 待寫 | ... |

### 斷崖處理
- order X→Y：___

### 站內前置知識連結
- 數學/統計 → CS109 導讀
- NLP 基礎 → CS224N 導讀
- ...
```

## 給使用者確認

規劃表完成後，交給使用者確認以下三點再開始寫：
1. **弧線順序**——這個順序讀起來自然嗎？
2. **每篇範圍**——有沒有哪篇太大要拆、太小要併？
3. **斷崖處理**——橋接方式 OK 嗎？

確認後照下一節存檔，再用 post skill 逐篇產出。

## 規劃表存檔與閘門

- 規劃表存成 `.work/series-plans/<series-slug>.md`（slug 與 `src/utils/series.ts` 一致），跟著 repo commit。不要只寫進 memory：雲端 session、routine 與之後接手的 agent 讀不到 memory。
- 規劃表要有：目標讀者、弧線、入口、斷崖處理、每篇範圍卡（含「讀完後讀者能」），以及使用者確認後補上的一行 `使用者確認：YYYY-MM-DD`。`pnpm check:series-plan` 對新登錄的系列逐項檢查；2026-10-15 前登錄的系列列在 `scripts/config/series-plan-baseline.json`，大改或重寫某系列時先補規劃表，再把它從清單移除。
- **入口不能是事件文。** 單篇查證文、新聞評論、熱門貼文回應，不能事後改標成 order 0。它要收進系列，就放到讀者看得懂它的位置（通常是附錄）。
- **先寫總覽＋第 1 篇給使用者看。** 沒有人即時看的工作每批最多 2 篇，交出後停下來等回覆。
- 每篇的審稿紀錄見 post skill「系列文章閘門」：`.work/reviews/<文章 slug>.md` 要有 post-verify、post-review、post-polish 三節。

本站踩過：「從零開始的資安獵人」沒有規劃表，入口是一篇事後升格的獎金查證文，一個雲端 session 兩天內每批四篇寫完 12 篇；主軸變成讀獎金表，網站 → 記憶體 → 虛擬機 → TEE 之間沒有銜接，整個系列要重寫（2026-10-14）。

## 跟其他 skill 的關係

- **research-selection**：系列涉及多案例對比時，先用 research-selection 選案
- **post**：規劃確認後，逐篇用 post skill 寫文
- **post-review**：每篇寫完用 post-review 自審
- **post-translate**：中文篇完成後用 post-translate 出英文版
- **deep-research**：單篇需要深入研究時用 deep-research
