# 案例選取標準（多案例研究 / 系列文 / 橫向比較）

當研究任務是「整理 N 個案例做橫向比較」或「寫系列文」時，在步驟 1（拆子問題）之前，先跑這三步。單一主題的研究（「研究一下 LangGraph」）不需要。

## 判斷時機

以下任一成立就走本流程：
- 使用者問的是「有哪些 X」「整理一下 X 的案例」「比較幾個 Y」
- 題目天然需要多個對象（「電子報創業」「vector DB 選型」「Agent 框架比較」）
- 預計產出是系列文、比較表、或選型指南

## 步驟零 A：定義母群

**在搜尋之前**做，不是搜完才回頭畫邊界。

1. 寫一句話定義什麼算、什麼不算（邊界條件）
2. 用系統性方法掃母群：
   - 平台排行榜（Substack leaderboard、GitHub trending、Product Hunt 等）
   - 分類目錄（awesome-list、survey paper 的 related work）
   - 推薦鏈（A 推薦 B、B 推薦 C）
   - 業界報告（Gartner、a16z annual report、State of JS/AI 等）
3. 列出掃到的完整清單，**掃完才開始選**

### 反合理化

| 想偷懶 | 為什麼不行 |
|---|---|
| 從「我知道的」開始挑 | 你知道的 = 訓練資料裡有名的 = 倖存者偏誤 + 英語圈偏誤 |
| 搜跟選同時做 | 搜到一個順眼的就放進去，最後選出來的東西偏第一頁搜尋結果 |
| 「先搜再定義邊界」 | 搜尋結果會反過來縮窄你的定義——你只看到 Substack 的就定義成「Substack 上的電子報」|

## 步驟零 B：覆蓋矩陣

列出需要覆蓋的維度，用二維表強迫檢查盲區。

### 維度該不該列的判斷標準

> **沿著這個維度的不同值，會不會導致讀者得出不同的行動結論？**
> 會 → 列入。不會 → 不列。

例：
- ✅ 規模分層（只看大的 → 讀者以為「不到百萬就是失敗」）
- ✅ 變現路線（走廣告和走訂閱的邏輯完全不同）
- ❌ 創辦人星座（不影響行動結論）

### 常用維度（依主題調整，不要硬套）

| 維度 | 覆蓋要求 | 為什麼 |
|---|---|---|
| 規模分層 | 大/中/小各至少 1 個 | 避免「做大才算成功」的偏誤 |
| 路線/類型 | 每條路線至少 1 個代表 | 讓讀者看到不同選擇 |
| 生命週期 | 至少 1 個失敗/收掉/轉型 | 避免倖存者偏誤 |
| 地理/語言 | 至少 1 個非主流語言/市場 | 避免英語圈偏誤 |
| 時間 | 早期/中期/近期各有代表 | 環境在變，2015 的規律不一定適用 2025 |

維度不要超過 5–7 個——太多會讓每個維度只能塞一個案例，失去深度。

### 格式

填完這張表再往下走：

```
母群定義：___
掃描方法：___

| 維度 | 值 | 選入的案例 | 缺口（空的格子） |
|---|---|---|---|
| 規模 | 大 | ... | |
| 規模 | 中 | ... | |
| 規模 | 小 | ... | |
| 路線 | 廣告 | ... | |
| 路線 | 訂閱 | ... | |
| ... | ... | ... | |
```

缺口欄空的格子 = 你需要補搜的方向。

## 步驟零 C：標註偏誤

選完案例後，在 research note 和最終文章裡明確寫出：

1. **偏哪裡**：這批案例在語言、平台、規模、時間、地區上的偏向
2. **缺什麼**：覆蓋矩陣裡還有哪些空格沒補上
3. **為什麼還是選了這些**：資料可得性、讀者 relevance、或刻意的範圍限制

### 反合理化

| 想偷懶 | 為什麼不行 |
|---|---|
| 不標偏誤，讓讀者自己判斷 | 讀者看到 10 個案例會以為這是「全貌」，不標等於誤導 |
| 把偏誤標註藏在文末小字 | 偏誤影響整篇的解讀，放在導讀或開頭段 |
| 「因為找不到資料所以沒有失敗案例」 | 這本身就是偏誤——寫出來，讓讀者知道 |

## 與 deep-research 主流程的關係

```
步驟零 A（定義母群）
  ↓
步驟零 B（覆蓋矩陣）
  ↓
步驟零 C（標註偏誤）
  ↓
步驟 1（拆子問題）← 原流程從這裡開始
  ↓
步驟 2-7（蒐集、驗證、萃取、產出、交接）
```

步驟零只在多案例研究時跑。單一主題研究直接從步驟 1 開始。
