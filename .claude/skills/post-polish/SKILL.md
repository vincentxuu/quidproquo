# post-polish skill

治的是語域（register）：文章事實對、結構對、但讀者讀不下去。

## 這支 skill 不做什麼

| 症狀 | 用哪支 |
|---|---|
| 數字錯、連結失效、引述不逐字 | `post-verify` |
| 缺章節、沒描述被討論的對象、覆蓋不全 | `post-review` |
| 諂媚開場、罐頭結尾、排比三段式 | 不在本站的病症清單裡 —— 見下方「為什麼不抓 AI 腔」 |
| 內容要改、要補、要翻新 | `post-update` |

### 為什麼不抓 AI 腔

繁中生態的潤稿工具幾乎都在做「去 AI 味」。本站的失敗模式相反：文章讀起來像**真的期刊論文**——那是人寫出來的病，不是模型的痕跡。抓 AI 腔的詞表對它完全無效。

本 skill 的方法論借自繁中社群幾個專案（保護片段預檢、密度閾值而非單點、力度分檔、annotation mode 借自 [shuorenhua-zh-tw](https://github.com/tentenco/shuorenhua-zh-tw) 與 [speak-human-tw](https://github.com/Raymondhou0917/speak-human-tw)；氣口／錯落／句尾的節奏規則借自 [writing-skills.TW 的 good-writing-tw](https://github.com/aeopress/writing-skills.TW)），規則本體則是本站實際犯過的病。

## 執行步驟

### 1. 先鎖保護片段（動筆前）

以下內容**改寫全程不得更動**，先在心裡圈起來：

- 數字、效果量、信賴區間、版本號、日期
- 引號內的原話與 blockquote 內容（逐字，連標點都不動）
- 連結網址、程式碼、命令、檔案路徑
- 專有名詞與人名
- **作者的立場強度**——「我不建議」不可以被潤成「這可能需要斟酌」
- 標了【未驗證】【轉引】的取用層級標記

### 2. 跑掃描

```bash
bash .agents/skills/post-polish/scripts/register-scan.sh src/content/posts/<category>/<檔名>.md
```

輸出六項指標。**已知誤判**：連結網址內含括號時（例如 `(2018)` 出現在 URL 裡），第 4 項會殘留 `%20` 之類的字串並虛報數字量；看到就跳過。

### 3. 對照閾值

閾值是**密度**，不是單點。單一長句不算違規，一段裡三句都超長才算。

| 指標 | 綠 | 該處理 | 判準 |
|---|---|---|---|
| 長句（>60 字） | < 10% 句數 | > 15% | 兩個句號之間超過 60 字就該斷。中文的氣口在 15–20 字 |
| 但書密度 | < 20% 段落 | > 30% | 每個結論剛成形就被自己收回，讀者拿不走完整的話 |
| 引述區塊 | ≤ 3 | ≥ 5 | 判準見下 |
| 數字密度 | 每段 ≤ 3 | 單段 ≥ 4 | 樣本數／CI／I²／p 值下放附錄 |
| 姓名當主詞 | ≤ 3 | ≥ 6 | 讀者不認識這些人，追蹤姓名沒有回報 |
| 可執行動作 | 每個「建議照做」都有 | 有缺 | 見下 |

### 4. 逐條處理

**長句**——先斷句再說。中文沒有被動語態與副詞可砍，斷句是主要手段。同時檢查錯落：相鄰句長差 > 5 字，避免連續三句長度相近。

**但書**——不是刪掉但書（那會犧牲誠實），是**換位置**。把「主張——但書——但書的但書」改成主張落地，但書集中到該節末尾或附錄。

**引述**——每個 blockquote 問一句：**作者原話比我的轉述更有力嗎？**
- 有力（留）：作者自承簡化、作者自己下的反直覺判斷、原文措辭本身有爭議
- 沒有（改成一句白話＋連結）：分類學句子、方法學描述、只是懶得翻譯

**數字**——正文每個主張最多留一個數字，並且是「讀者會拿來做決定」的那一個。其餘搬到附錄，附錄可以無上限。

**姓名**——姓名從主詞位置移到括號或連結裡。「Pan 與 Rickard 2018 年的 meta-analysis 發現……」→「校正發表偏誤後往往顯示零遷移（[Pan & Rickard 2018](...)）」。

**可執行動作**——這是最常缺的一層。每一個判「該做」的建議，都要有一句**做得出來的動作**：讀者今晚就能照著做，而不是理解一個概念。

> ❌ 「用自我測驗取代重讀」
> ✅ 「讀完一節就闔上書，拿張白紙寫下你記得的東西，再翻回去對。寫不出來的地方，就是你剛才以為自己懂的地方。」

### 5. 定力度與範圍

| 檔位 | 何時 | 行為 |
|---|---|---|
| `minimal` | 使用者只說「稍微順一下」 | 只斷長句、只調氣口 |
| `standard`（預設） | 「讀不下去」「很研究」 | 全部六項處理 |
| `aggressive` | 明確說「大改」 | 加上段落重組 |

| 範圍 | 何時 | 行為 |
|---|---|---|
| `bounded`（長文預設，> 150 行） | 一般 | **整句刪除列成「建議刪除（待確認）」清單交使用者拍板**，不擅自縮水 |
| `in-place` | 「不要刪東西」 | 一句不刪，只句內降調與搬位置 |
| `structural` | 明確要重寫 | 可自由刪併重排 |

**長文不縮水**：本站文章的價值有一半在證據密度。搬到附錄 ≠ 刪除。改完總字數不該掉超過 10%，掉了就是刪到內容了。

### 6. 預設只標不改

第一輪**只輸出問題清單**，每條寫明：在哪一段、哪一項指標、為什麼是問題、建議怎麼改。列完停下來問一句「要我直接改嗎」。

使用者明說「直接改」「不用先問」才跳過這關。

### 7. 保真回讀

改完逐項核對步驟 1 的保護清單，然後跑：

```bash
pnpm check:references
```

### 8. 記錄與提交

內容性改動要在 `## 更新紀錄` 加一行（最新在上），照 `post-update` 的規矩。commit 前給 `git diff` 讓使用者看過。

## 誤殺邊界（不要改的東西）

| 看起來該改 | 為什麼留著 |
|---|---|
| 有事實撐著的長句 | 資訊密度高不等於句子壞。只有「拆開來不損失東西」才拆 |
| 作者刻意的排比或重複 | 節奏是刻意的就留。改之前先問這是不是設計 |
| 被文章討論的詞本身 | 文章在講「效果量」時，「效果量」出現二十次是正常的 |
| 附錄裡的數字密度 | 附錄的工作就是放帳。閾值只適用正文 |
| 取用層級標記與但書 | 【未驗證】那類標記是本站的識別，不是贅字 |
| 已經是短句的段落 | 不要為了「錯落」把好句子拆壞 |

## 反合理化

| 想偷懶 | 為什麼不行 |
|---|---|
| 「把數字刪掉最快」 | 刪不是搬。本站文章的可信度建立在數字上，正文留一個、其餘進附錄，一個都不能消失 |
| 「引述全部改成轉述，比較順」 | 作者自承、反直覺判斷那類引述，換成轉述就變成你在替作者說話 |
| 「順便把語氣調柔和一點」 | 立場強度是保護片段。「我不推薦」不可以變成「可能需要評估」 |
| 「長句一律拆」 | 閾值是密度不是單點。拆到每句都一樣長，是另一種病 |
| 「跑完掃描就當作改完了」 | 掃描只量六個可計算的指標。「抽象而沒有可執行動作」機器抓不到，一定要人讀 |
| 「英文版照翻就好」 | 英文有被動語態、副詞、Flesch-Kincaid 可用，中文沒有。兩邊的檢查項不同，別互相套 |
| 「改完不用重跑 check:references」 | 搬段落最容易弄斷站內連結 |
