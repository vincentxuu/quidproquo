# post-review skill

發文前的最後一關。**只報告，不動文**——這個 skill 的價值就在於使用者可以決定要不要採納。

## 課程文章審稿（必讀）

涉及課程總覽、單堂導讀、作業或週次文章，審稿前必須直接讀 `../post/references/course-guide-contract.md`，先辨識文章角色。中文單堂標題採「主題｜課程 第 N 堂」，英文使用 `Lecture N`；其他角色依該規格處理，原課堂次不能用 `series.order` 代替。

對本次課程文章執行獨立標題檢查（明列檔案，不把全站既有問題混成本次驗收）：

```bash
node .agents/skills/post/scripts/check-course-titles.mjs src/content/posts/<category>/<檔名>.md
```

教學品質以正文證據判斷，每項附行號或段落位置：

- 讀者先備與讀完能做的事是否明確？開頭承諾是否由正文兌現？
- 單堂概念導讀是否有可走完的例子、推導或反例，交代條件、推理、結果與解釋？實作篇是否有步驟、預期結果與失敗判斷？
- 理解檢查是否測同一學習目標，並提供答案、判準或可觀察結果？只有問題清單不算完成。
- 正文是否在教概念，還是在羅列來源、投影片頁碼、查詢日期與驗證工作？必要來源限制可留，檢索歷程應移到研究筆記。

總覽按選課判斷、內容地圖與學習路徑驗收，不硬塞單堂例題；僅更新來源的任務回報變更範圍及既有教學缺口，不宣稱已完成教學改寫。判準不靠章節關鍵字或字數配額；步驟 6.55 的篇幅比例對課程文章只作診斷線索，不能代替上述正文證據。

報告須分開列「機械檢查」「事實查證」「教學品質」。未跑事實查證就標未查，找不到教學證據就列缺口；任何一層通過都不能推定另兩層通過。

## 模型家族文章審查（必讀）

審查「AI 模型家族」／「AI Model Families」系列時，先讀 `../post/references/model-family-contract.md`，依文章角色檢查；每日模型卡不套家族長文模板。執行 `node .agents/skills/post/scripts/check-model-family-format.mjs <中英檔案...>`；這是本 skill 的專項檢查，不取代 pnpm verify，也不改寫文章。

- 家族主篇的共同 H2、前置版本矩陣、tldr、語言化系列名稱與文末排列是否一致？跨家族篇不硬套。
- 矩陣與正文是否同一版本／數字／用途？模型與端點、權重與服務是否混在一起？
- 評測是否交代來源和可比較條件？限制／未知是否有實際內容，或只是用固定套話填節？
- 中英的模型、價格、來源、限制與選型結論是否一致？H2 數相同不等於語意一致。
- 改過章節順序後，指代、前後承諾、引用連結與結論是否接得上？格式日期有沒有冒充事實查證日期？

違反專用格式列必修，缺未知資訊的來源邊界列需補；glossary 是選填，不以缺欄位判缺陷。報告分開格式、事實範圍與選型可讀性，不能用機械檢查綠宣稱整篇事實最新。

## 執行步驟

### 1. 定位草稿

使用者指定的路徑、slug 或關鍵字。多個候選 → 列出讓使用者挑，**不要自己選**。

### 2. 機械檢查（先跑命令）

```bash
pnpm verify        # lint + references + post-quality + glossary + series-order + lang-parity + skills-sync
pnpm astro check
pnpm exec tsx scripts/diagram-preview.ts <檔案路徑> --out <暫存目錄>   # 有 diagram / flow-diagram 區塊時，中英兩版都跑
```

任何一項紅，先列在報告開頭，**這些是必修**。

外部連結要另外跑（會打網路，所以不在 `verify` 裡）：

```bash
pnpm check:links src/content/posts/<category>/<檔名>.md
```

它分兩欄輸出：「壞掉的連結」（404/410/逾時）要修；「需人工確認」多半是出版社與社群網站擋機器人（403/429），開瀏覽器看一眼即可。

### 3. frontmatter 檢查

對照 `../post/references/frontmatter-schema.md`：

- [ ] 必填齊全：`title` / `date` / `category` / `tags` / `lang`
- [ ] `date` 格式為 `YYYY-MM-DD`
- [ ] `category` 在合法清單內
- [ ] `tags` 全小寫 kebab-case
- [ ] `tags` 數量 3-7（過多或過少都標）
- [ ] `lang` 是 `zh-TW` 或 `en`
- [ ] `tldr` 對 `tech` / `ai` / `deep-dive` 類有沒有填
- [ ] `description` 跟 `tldr` 內容是不是一樣（重複是 smell）
- [ ] `type` 跟內容性質是否一致（debug 文卻標 deep-dive 等）

### 4. tldr / description 強度

| 弱 | 強 |
|---|---|
| 「介紹這個工具的特色」 | 「Skill 是一個資料夾、一份 SKILL.md。三層 progressive disclosure 讓 Claude 在需要時才載入細節」 |
| 「四個起點不是四種功能，是四種 loop 歸屬的安排」 | 「已有 harness 用 PiHarness；做 chat 且要自己組 model call 用 AIChatAgent，交給框架用 Think；不是 chat 但要 state、排程、MCP 用 Agent」 |

檢查點：
- 有具體名詞、版本範圍或選型取捨嗎？數字只在已核對且有助理解時放，不以沒有數字判摘要弱。
- 有點出「跟讀者切身相關的資訊」嗎？
- 是不是「這篇有多好」（弱）而不是「這篇講什麼」（強）
- 是資訊型（寫出答案）還是指示型（只預告談什麼）？遮掉正文只看 tldr，讀者能做決定嗎？
- 答案有沒有在正文決策段，而 tldr 卻取材自導言或「整體來說」？
- `check:post-quality` 的 tldr 警告（自指、否定式對比、意義抬高）逐條看；誤判要能說出理由，不然列必修。規則見 `../post/references/writing-guide.md` §tldr / description 原則

### 4.5 衍生內容的事實一致性（tldr / faq / glossary）

`tldr`、`faq`、frontmatter `glossary` 都是從正文改寫來的**衍生內容**，而且比正文更短、更斷言、更容易被搜尋引擎與 answer engine 整段抽走。它們也最常在最後一刻趕出來，是錯誤最容易溜進去的地方。

逐條檢查：

- [ ] 每個數字都跟正文一致（不是「差不多」——效果量、樣本數、百分比要逐字對）
- [ ] **數字帶著它的對照條件**：「效果量 0.51」不算，「相較重讀 +0.51」才算
- [ ] **歸屬正確**：衍生內容常把相鄰兩段的研究併成一句。檢查每個「某某研究發現 X」的 X 真的出自那一篇，不是隔壁段落的
- [ ] 強度沒有被放大：正文寫「傾向」「其中一項分析顯示」，摘要不能變成「證明」「最有效」
- [ ] 樣本數小、未同儕審查、預印本等限制，若正文有標，摘要不該悄悄拿掉
- [ ] `faq` 的答案可獨立閱讀（會被單獨引用），但**不得因此省略但書**

判斷原則：**改寫等於重新宣稱一次。** 有疑慮就回原始來源對，不是回正文對——正文的錯會被原封不動複製過來。

### 5. tags 衛生

跟同 category 既有 tag 比對：

```bash
grep -h "^tags:" src/content/posts/<category>/*.md | sort -u
```

找：
- 同義詞分裂（`llm` vs `large-language-model`、`agent` vs `ai-agent`）
- 過於一般（`tech`、`programming` — 不傳達資訊）
- 拼錯字
- 該有沒有的核心 tag（題目主軸沒進 tag）

Canonical 判斷跟 `tag-audit` 一致：
- 全小寫 kebab-case。
- 既有高頻 tag 優先，除非低頻 tag 明顯更符合官方名稱或更不易誤解。
- 通用縮寫如 `llm` / `rag` 可保留；不穩定縮寫不要新增。
- category 名稱不要重複當 tag，除非跨分類時有額外辨識價值。
- 核心主題排在 tags 前面，不要求字母排序。

### 6. 結構

模型家族先按上方專用規格；其餘按 `type` 對應預期：

- `debug`：情境 → 問題 → 嘗試 → 解法 → 原因 → 學到的事
- `deep-dive`：開頭段 → 多個展開段 → 整體架構（如有）→ 整體來說 → 參考資料
- `guide`：前置 → 步驟 → 預期輸出 → 常見錯誤
- `project`：問題 → 為什麼做 → 怎麼做 → 現況

缺主要段落 → 列。

### 6.5 對象覆蓋（導讀／評論／拆解類必查）

只要文章在討論一個外部對象——課程、工具、論文、專案、產品——就檢查**對象本身有沒有被描述**，而不只是被評論。

- [ ] 前三段之內，沒接觸過這個對象的讀者知道它是什麼、主張什麼了嗎？
- [ ] 對象的主要部件有沒有被列出來？（課程的模組、工具的功能面、論文的論證鏈）
- [ ] 文章實際只審了其中一部分嗎？有沒有**明講範圍**與略過的理由？

最常見的失效不是寫錯，是**文章繼承了研究過程的形狀**：研究時以「可被檢驗的主張」為單位，於是沒有證據可掛的部件整批消失，讀者拿到一份沒有對象的對帳單。

快速檢法：把對象的主要部件列成清單，逐項 `grep` 文章。零命中的項目集中在同一類（例如「全是沒有 meta-analysis 的那些」）→ 這是覆蓋缺口，要列。

### 6.55 文體一致性（導讀／評論／拆解類必查）

比對**標題與 tldr 承諾的文體**（介紹／審查／教學…）和**各章節實際字數占比**。

- [ ] 標題與 tldr 承諾的文體，跟占最多篇幅的章節一致嗎？（承諾介紹，卻有一半以上篇幅是錯誤清單 → 不一致）
- [ ] 標題或 tldr 有沒有放工作量數字（讀了幾堂、跑了幾支、覆核幾條），而讀者的決定並不取決於它？
- [ ] 評測發現是否合併成一節、約 15–20%？分散成多個「判決」章節、或合計超過三成 → 標紅
- [ ] 介紹類文章的「是什麼／內容地圖」是否占一成以上？

快速檢法：

```bash
awk '/^## /{if(h)print n, h; h=$0; n=0; next}{n+=length($0)}END{print n, h}' <post.md>
```

把各 `##` 字數算成占比，逐節標類型（介紹／評測發現／方法／參考），對照標題承諾。規則見 `../post/references/writing-guide.md#研究過程不進門面`。不一致標 🔴；單純數字放錯位置標 🟡。

### 6.6 語域（zh-TW 長文）

事實對、結構對，但讀者讀不下去——這是獨立的一層，機械檢查抓得到一半：

```bash
bash .agents/skills/post-polish/scripts/register-scan.sh <post.md>
bash .agents/skills/writing-phrase-ledger/scripts/scan-ledger.sh <post.md>
```

七項指標（長句、但書密度、引述區塊數、數字密度、姓名當主詞、可執行動作、模板化轉折）與閾值見 `post-polish` skill。本步驟只**報告**；要改寫走 `post-polish`。

第二個掃描抓使用者已指出的慣性句型與不像台灣中文的用詞，例如 `本地*`、`台灣語境`、`不是 A，而是 B`。

機器抓不到、必須人讀的一項：**每個「建議讀者照做」的主張，有沒有配一句做得出來的動作。**

### 6.65 台灣讀者位置（zh-TW 導讀／評論／拆解類必查）

繁體字、台灣用詞、或多寫幾次「台灣」都不等於台灣讀者位置。這一層查的是：文章有沒有把外部材料翻成台灣讀者會遇到的問題、限制、決策或行動。

適用範圍：`lang: zh-TW`，尤其是 `tech` / `ai` / `learning` / `education` / `policy` / `design` / `marketing` / `product` / `career` / `daily`，以及任何從外國工具、課程、論文、公司、政策或英文材料翻寫而來的文章。

檢查點：

- [ ] 前三段之內，讀者知道「這件事為什麼跟台灣讀者／繁中使用者／台灣市場／台灣工作現場有關」嗎？
- [ ] 外國工具、論文、課程、公司或政策被介紹時，有沒有接回台灣這邊的採用限制、職場情境、教育制度、採購流程、法規、供應鏈或語言問題，而不只是摘要來源？
- [ ] 如果文章主題本身是台灣，有沒有優先使用台灣硬證據：法規、政府資料、採購公告、公司 filings、財報、台灣媒體、學研機構或第一手觀察？
- [ ] 標題與 `tldr` 有沒有具體張力或決策點，而不是「完整指南」「深入解析」「趨勢觀察」「一次看懂」這類不定位讀者的泛題？
- [ ] 缺作者自身經驗或台灣一手脈絡時，有沒有標成「需作者補」，而不是替作者發明第一人稱故事？

判準：

- 🟡 建議修：zh-TW 文章整體像英文來源摘要，前幾段沒有交代台灣讀者為什麼要讀。
- 🔴 必修：標題、`tldr` 或開頭承諾台灣／繁中 relevance，但內文沒有兌現。
- 🔴 必修：台灣文章使用中國語境 framing（例如「內地」「我國」但不是引用中國來源），或把中國制度／市場條件默默套到台灣。
- 🟢 可選：全球議題不需要硬塞台灣案例；但至少要有台灣讀者可用的判斷角度或行動問題。

站內語氣錨點見 `.research/2026-08-29-quidproquo-voice-reference-set.md`；外部參考來源見 `.research/2026-08-29-taiwan-article-sources-for-tone.md`。結構模板見 `../post/references/taiwan-voice-structure.md`。檢查時優先看「讀者位置」與「問題翻譯」，不要只算台灣詞彙出現次數。

### 6.7 通順與接縫（改過兩輪以上必查）

**機械檢查全綠 ≠ 文章讀得通。** 前面每一步都是分項檢查；這一步是**從第一行讀到最後一行**，看它還是不是一篇完整的文章。

必查時機：文章被改過兩輪以上、或用字串取代／腳本動過內容。那種改法會在接縫留下機械檢查抓不到的東西。

通讀時「碰巧注意到」不算檢查。先做下面三個會把問題逼出來的動作，順序由深到淺，前一步改完才做下一步：

1. **反向大綱（看全文結構）**：替每一段寫一句摘要，寫的是這段實際講了什麼，不是原本想講什麼。然後只看這份摘要，問四件事：一段是否塞了兩件事（寫不出一句摘要）、同一個主題是否散在不相鄰的段落、順序是否說得出道理、開頭承諾的是否都交代了。
2. **一致性另跑一輪（看前後說法）**：列出全文的關鍵事實（價格、數量、狀態、「唯一」「只有」這類全稱句），逐一搜尋它在全文每一次出現的說法並對照。系列文章要連同系列其他篇一起搜。
3. **逐句看句首（看段落內的銜接）**：只讀每句開頭幾個字。句首應該是前文已經出現過的東西，新資訊放句尾；句首突然出現沒鋪墊的新名詞、或一段裡句首的主題一直換，就是接不上的地方。發現自己想加轉折詞時，先試著調句子順序。

做完這三步再逐項對：

- [ ] **開頭的承諾兌現了嗎**：開場說「我測錯了一次」，內文其實錯了三次 → 開頭要改
- [ ] **跨節指代還指得到嗎**：「上面那節」「見上一節第四點」「下面會說明」——每一個都點進去確認目標還在、還在那個相對位置
- [ ] **前後結論一致嗎**：第 3 節說「這五個詞要收進清單」，第 9 節說「其中一個我後來推翻了」→ 第 3 節要補註，不能只在後面補
- [ ] **同一個數字全篇一致嗎**：改過的數字常只改了一處。全篇 grep 那個數字
- [ ] **章節標題改名後，內文的引用也改了嗎**
- [ ] **新插入的段落跟前後文接得起來嗎**：有沒有重複說同一件事、有沒有突然轉折
- [ ] **有沒有機械替換留下的怪字**：例如 `貼上標籤籤`、混進非中文字元

掃描輔助（抓不到語意問題，只抓得到明顯殘骸）：

```bash
# 跨節指代，逐條人工確認
grep -nE "上面|上一節|下面|前面|如上|下一節|那節|這一節" <post>
# 非預期字元（西里爾、全形英數混入）
grep -nP '[\x{0400}-\x{04FF}\x{FF21}-\x{FF5A}]' <post>
# 疊字殘骸
grep -nE "(.)\1{2,}" <post>
```

**本站踩過（2026-10-12）**：AI 證照備考系列用腳本改了 64 檔，只讀了自己改過的段落就回報完成。被問「通順嗎」才整篇讀，讀出開頭寫「Anthropic 沒有公開價格」而後面列了價格表、節標題寫「Google 只有 PMLE 一張」而別節提到第三張、AWS 一節講續期講到一半被插進重考規則。反向大綱與一致性搜尋都能在第一輪抓到這些。

**本站踩過**：一篇文章用字串取代改了三輪，機械檢查全綠、外部連結全通、語域掃描乾淨，讀一遍才發現開頭寫「錯了一次」但內文有三次、某節說「這五個詞要收」而後面說「其中一個推翻了」、還有一處改字時混進西里爾字母。**這三個沒有任何自動檢查抓得到。**

### 6.8 主題歸屬（站上已有相關系列時必查）

站愈大愈容易犯：某一節把另一個系列已經擁有的主題重講一遍。結果不是寫錯，是**兩處會各自過期的重複描述**——而且日後更新只有其中一處會被改到，另一處靜靜爛掉。

觸發條件：文章有一節在講的東西，站上已經有專文或系列在處理。

```bash
# 查站上有沒有專門系列在管這個主題
grep -n "slug:" src/utils/series.ts
grep -rl "<該節的核心關鍵詞>" src/content/posts/
```

- [ ] 這一節的主題，站上有沒有專文／系列已經在講？
- [ ] 有的話，這節現在寫的是「**分界 + 轉手**」還是「濃縮版重講」？
- [ ] 節裡出現的細節（運作機制、授權條款、benchmark 數字），是不是在那個系列裡已經有更完整、更常被更新的版本？

判準：**在這篇裡，越界的主題只需要回答「為什麼它不屬於這篇的範圍、該去哪裡看」。** 一旦開始解釋它怎麼運作，就是越界。

最陰險的觸發點是 review 本身：發現某節分類講錯了，於是「補一段說清楚」——方向剛好相反。分類錯要修的是分界句與轉手連結，**正確的修法讓那一節變短，不是變長**。本站踩過：爬蟲工具全景圖的「文件轉檔」一節把 MinerU / Marker / Docling 這三個 OCR 解析工具跟純轉換工具混在一起，發現後補了兩段解釋 OCR 機制與授權差異——而那些內容「文件解析實戰」六篇早就寫得更完整。最後是把那節砍到三分之一、只留分界與連結。

### 7. 標題與清單可讀性

對照 Google-style 的可掃讀原則，檢查文章是否容易被人和模型穩定解析：

- [ ] heading 層級沒有跳級（例如 `##` 後直接 `####`）
- [ ] heading 具體，不用「介紹」「補充」「其他」「一些想法」這種空標
- [ ] heading 底下不是空段落，也不是只有一個孤立清單
- [ ] 清單前有引導句，讀者知道這串項目在回答什麼問題
- [ ] 同一個清單的項目語意平行，不混合步驟、原因、結論
- [ ] 超過 6 項且需要比較的清單，評估是否改成表格

### 8. 參考資料覆蓋

- [ ] `tech` / `ai` / `learning` / `education` / `policy` / `design` / `marketing` / `product` 類有沒有 `## 參考資料` 段
- [ ] 文中提到的每個工具 / 框架 / 論文 / 模型有沒有對應條目
- [ ] 每條連結是不是指向**該主題的官方頁**（不是某個泛用首頁）
- [ ] `lang: en` 的文章中，中文資源有沒有標 `(in Mandarin)`；`lang: zh-TW` 不需要

### 8.5 inline source link 覆蓋（數據與引述）

逐段掃文章正文，找出所有「引用外部事實」的句子——包含數字、百分比、研究結論、人物引言、公司行為描述——然後檢查：

- [ ] 每個外部數據（如「45% 的生成程式碼引入了 OWASP Top 10 漏洞」）在該句就有 inline link 指向來源
- [ ] 每個人物引言（如「Sal Khan 說...」）在人名或引言處有 inline link
- [ ] 每個公司行為描述（如「LinkedIn 結束 APM 計畫」）在該句就有 inline link
- [ ] 讀者不需要跳到文末參考資料去對照——所有引述在原位就能點

如果一段有數字或引述但沒有超連結，標為 🔴 必修。理由：讀者不會主動去文末參考資料對照，沒有 inline link 等於沒有來源。

### 9. 寫作品質（風格層）

對照 `../post/references/writing-guide.md`：

- [ ] 標題具體（不是「一些想法」「淺談 X」）
- [ ] 開頭直接，不客套
- [ ] 沒有「綜上所述」「眾所周知」這種廢字
- [ ] 程式碼塊有指定語言
- [ ] 表格 / ASCII 圖如果有比較多項，比文字描述更清楚

### 9.3 圖表使用（所有文章必查）

對照 `../diagram/SKILL.md`。不論長短，逐節問：這段讀者看圖會不會比讀文字更快懂？

- [ ] **該有圖卻沒有**：有多步驟流程、分支判斷、元件關係、角色交接、時間順序、兩個維度的定位、層級或包含關係的段落，只用文字（或一大段條列）交代 → 🟡，寫出建議的圖型與放在哪一段。反過來，三欄表格就講得清楚的，不要硬加圖。
- [ ] **圖型選對**：用 `diagram` skill 的選圖表對一次（例如講時間順序卻畫成架構圖、講交接卻沒用泳道）。整篇都是同一種方框箭頭圖，而內容其實有定位、層級、對照 → 🟡 建議換圖型。
- [ ] **沒有偷渡主張**：每條線、每個分組、每格內容都能在正文或參考資料找到出處；來源只寫相關卻畫成因果箭頭 → 🔴。
- [ ] **格子填滿**：象限、矩陣、金字塔、分層只填了一部分 → 🟡，依 `diagram` skill 的規則查原始框架補齊並附出處。
- [ ] **檢查腳本全 ✓**：步驟 2 的 `diagram-preview.ts` 有 ✗ → 🔴；全 ✓ 也要打開淺色、深色、手機三張截圖看一次（對齊、留白、重點明不明顯）。
- [ ] **中英一致**：兩版的圖結構、步驟數相同，英文沒有溢出框或被截斷。
- [ ] **mermaid 舊圖**：節點 ≤ 9、手排得出來的 mermaid 圖 → 🟢 可選，建議改用 `diagram`（深淺色、可逐步播放）。

### 9.5 台灣用語（只查 `lang: zh-TW`）

繁體字不等於台灣用語——模型的中文語料以中國內容為大宗，中國詞彙與翻譯腔會自動流進來。先跑掃描指令，再逐句看翻譯腔：

```bash
pnpm check:tw <post>
```

分兩級：**A 級**（用戶、視頻、激活、插件…）標 🔴 必修；**B 級**（質量、智能、信號、界面、反饋）標 🟡，因為它們在物理、專有名詞、控制理論等語境下是正確的，要看過再判斷。

廣度檢查另外跑 `zhtw-mcp lint`（不進 CI，用法見 `../post/references/writing-guide.md#兩層檢查`）。

- [ ] 掃描命中的每一處都確認過（命中不等於一定要改，但要看過）
- [ ] 翻譯腔四型逐句掃：形容詞直譯（「很不性感」）、名詞化（「執法啟動」）、英文語序（「壞的 X 的代表案例」）、術語硬譯（framing →「框架」多半該寫「說法」）
- [ ] 金額寫成「4,000 萬美元」而不是「$4,000 萬」
- [ ] 從英文材料翻寫的段落特別檢查——那是翻譯腔密度最高的地方

替換對照表在 `../post/references/writing-guide.md#台灣用語`。這類問題標 🟡 建議修，除非整段讀起來明顯不像中文母語者寫的（🔴）。

### 10. 報告格式

把所有 issue 分成三層回報：

```
🔴 必修（影響發布）
- ...
- 文體一致性：標題／tldr 承諾「X」，實際章節占比是「Y」（列各節占比）
- 圖表：diagram-preview ✗、圖上有正文沒有的主張

🟡 建議修（影響可讀性 / 一致性）
- ...
- 圖表：第 N 節「…」適合畫成 <圖型>（理由）；圖型不合內容；格子沒填滿

🟢 可選（風格偏好）
- ...
```

每條 issue 帶：
- 位置（行號或段落名）
- 為什麼是 issue
- 建議怎麼改

**不要直接動文**。讓使用者選要採納哪些。

## 反合理化

| 想偷懶 | 為什麼不行 |
|---|---|
| 「直接幫他改下去」 | review 跟 update 是兩件事；這 skill 只報告，使用者要主動觸發 post-update 才動 |
| 「跑完命令沒紅就 OK」 | 機械檢查通過 ≠ 內容好；要讀內文做品質檢查 |
| 「不檢查 tag 分裂」 | 站內聚合靠 tag，這是長期負債 |
| 「tldr 弱算了不提」 | tldr 弱直接影響點擊率，是發文前最該修的 |
| 「tldr / faq 是從正文抄的，正文對就對」 | 改寫會併句、會丟掉對照條件、會把「其中一項分析」變成「研究證明」。這三種錯都只在衍生內容裡，正文檢查抓不到 |
| 「分類講錯了，補一段說明清楚」 | 補充等於把別的系列的內容複製一份過來，變成兩處各自過期。分類錯要修的是分界句與轉手連結，修完那節應該**變短** |
| 「這段寫得不錯，重複也沒差」 | 重複描述的成本在未來——更新時只有一處會被改到，另一處靜靜過期，而且沒人會提醒你 |
| 「這段沒改過，跳過」 | 沒改過只代表沒被檢查過。review 是看現在的文章對不對，不是看這次改了什麼 |
