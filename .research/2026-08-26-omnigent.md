## 草稿骨架

### 核心概念
Omnigent 要解的是「每個 harness 都是孤島」的問題。單一 harness（Claude Code、Codex、Pi、Cursor…）把模型能力包成 agent，但它的 context、控制、運行方式都不會帶到下一個 harness。當團隊實際上同時開 4–5 個 agent、在 Docs/Slack 之間複製貼上，並想把「Harvey 用 frontier advisor 帶 open-source worker」、「Anthropic 用 lead agent 帶並行 subagents」這類跨 harness 模式產品化時，缺乏一個共通層。

Omnigent 的答案是 **meta-harness**：在所有 harness 之上提供一個共通 API（messages/files in, text streams/tool calls out + cancel），把「可攜、治理、協作」這三個跨 harness 問題拉到同一層解。它不取代你已在用的 harness，而是讓 session、policy、skill 跟著你走，模型與 harness 可以一鍵替換。

### 關鍵設計決定
1. **Runner / Server 分離，而非「大腦與手分離」。** Server 只做協調（持久化 session 歷史到 Postgres/SQLite、policy 執行、MCP proxy、auth、多介面同步），Runner 在你選定的 host（筆電 / devbox / K8s Pod / Modal/Daytona 等雲沙盒）上實際跑 harness 與工具，inference 與憑證留在 host。代價是需要部署與維運一個 server，但換來可接續、可分享、可審計的 session。
2. **共通 API 抽象所有 harness。** 以「terminal agent」與「SDK agent」兩條路徑覆蓋 Claude Code/Codex/PI 等 CLI 與 Claude SDK/OpenAI Agents 等 SDK，後續新增 harness 以插件形式接入（Atlassian 的 Robo harness 即為外部擴充案例）。代價是每當上游 harness 改 API，Omnigent 需跟進。
3. **Policy 不是 prompt 規則，是 server 層的狀態機。** Policy 以 Python 函式表達，看到的是整個 session（已讀資料 + 請求動作），可回 allow / deny / ask。內建 cost budget、tool call cap、allowlist 等，並支援三層堆疊（server-wide > per-agent > per-session）。這把「治理」從 prompt 裡拉出來，避免被 prompt drift 繞過。
4. **雙層沙盒 + 證書代理。** Omnibox 在 OS 層用 bwrap / seatbelt（含 egress proxy 與 secretless credential injection）做最小權限；外層再用雲沙盒做隔離與 always-on。Windows 以 Job Object 降級（僅 process 樹隔離，無 FS/network）。目的是讓 YOLO mode 敢開。
5. **Agent 即 YAML，而 agents 可當 tools。** `name/prompt/executor/tools` 四件套，tools 支援 `function / mcp / agent` 三類，sub-agent 可指定不同 harness。Polly（plan → 並行 git worktree 委派 → 跨 vendor review）與 Debby（雙模型並排 + /debate）是官方示範；Deep Research 是最簡可抄模板。

### 跟替代方案的比較
- **vs 單一 harness 原生使用（Claude Code / Codex / Pi 各自為政）：** 原生最省事、零伺服器成本；但切換模型/harness 要重寫、無法跨裝置接續、無法讓同事即時共看/共駕、沒有狀態化的成本/安全護欄。Omnigent 用一個 server 換來這些。
- **vs 自行拼多 agent 腳本 / LangGraph / CrewAI 類 orchestrator：** 自製腳本彈性高但需自己維護 harness 差異與 policy；LangGraph 等框架擅長「單一 harness 內的流程編排」，Omnigent 擅長「跨 harness 的可攜與治理」。兩者可互補。
- **vs 內部平台自建（如 Databricks 先前的 Isaac）：** 自建能完全客製但需長期投入；Omnigent 開源、插件化，且可直接部署在 Fly/Railway/Modal/Daytona/K8s/Cloudflare/Databricks Apps 等，適合不想從零造輪子的團隊。
- **vs 直接用託管的 Databricks Omnigent（Unity AI Gateway 整合）：** 開源版立即可用、無廠商綁定；託管版提供統一的模型閘道、審計與資料就近性，但目前仍在 beta，適合提早驗證、未來切換。

### 適合 / 不適合的情境
**適合：**
- 團隊已同時使用多種 harness/模型，想「一鍵換 harness/模型」且不改 agent 邏輯。
- 需要「分享一個活的 agent session」給同事評審、共駕、或 fork 後各自再跑。
- 想讓 agent 在雲沙盒持續跑（關筆電後仍可用手機追蹤），或需要每 session 一個隔離環境。
- 想要可審計的成本與安全護欄（每次花 $100 暫停、依上下文決定是否允許 push 等）。

**不適合：**
- 個人單機、單一 harness 已足夠，且不需協作/持久化 — 直接用原生 harness 更輕。
- Windows 原生且強依賴 FS/network 隔離 — 目前為降級模式，需改用 WSL/Linux/macOS。
- 追求完全無伺服器、零維運 — Omnigent 的 server 是必要組件（雖可跑在本地，但協作/持久化價值就打折）。
- 對 alpha 軟體容忍度低、需穩定 API 與長期支援保證 — 現階段為 0.11.0.dev0。

### 限制 / 已知問題
- **Alpha 成熟度：** API 與行為仍在變動，升級需透過 `omni upgrade`，source checkout 以 `git pull` 為準。
- **Windows 降級：** 無 bwrap/seatbelt 與 L7 egress proxy，僅 Job Object；官方建議 WSL。
- **依賴鏈重量：** 需 Python 3.12+、Node 22、tmux、（Linux 上）bubblewrap；滿血安裝還需對應的 sandbox/model provider extras。
- **託管治理仍在 beta：** Unity AI Gateway / Unity Catalog 的集中治理需待 GA。
- **Telemetry 預設開啟：** 雖稱匿名且可關閉（見 omnigent.ai/docs/deploy/telemetry），對隱私敏感團隊需主動 opt-out。

### 取捨總結
Omnigent 把「agent 的可攜性」從模型層往上提了一層，用一個可自託管的 server 換來跨 harness 複用、狀態化治理與即時協作。代價是多一個需要部署的組件與對上游 harness 變動的跟隨成本。若你的痛點是「工具多、協作難、治理落在 prompt 裡」，Omnigent 是目前最完整的開源解；若你只用單一 harness 且單機作業，它的價值就顯得間接。
