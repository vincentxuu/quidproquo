## 具體錯誤（批次 2）

18. `21-tool-registry-schema-validation/code/main.py:174,183,198…` — `path=path or "/"`：根層錯誤路徑回傳 `"/"`。依 RFC 6901（檔頭 `main.py:7` 自己引用），整份文件的 pointer 是 `""`，`"/"` 代表「根物件中 key 為空字串的成員」。測試 `tests/test_registry.py:81` 把這個錯誤釘死成預期值。
19. `21-tool-registry-schema-validation/code/main.py:180` — `if value not in schema["enum"]`：Python `True == 1`、`1 == 1.0`，故 `{"enum":[1]}` 會接受 `True`，與同檔 `_type_matches` 刻意區分 bool/int（`main.py:161-166`）的設計自相矛盾；JSON Schema 規定 boolean 與 number 不相等。
20. `21-tool-registry-schema-validation/docs/en.md:52` — 「pattern ECMA-262-compatible regex」：程式 `main.py:208` 用 Python `re.search`，語法與 ECMA-262 有差異（如 `(?P<name>)`、lookbehind、`\d` Unicode 範圍），講義未說明。
21. `22-jsonrpc-stdio-transport/docs/en.md:96` — 「The demo shows the pattern: a request comes in, the handler emits two progress notifications, then writes the final response」；`docs/en.md:102` 又說測試涵蓋「the asymmetric flow where a handler writes a notification mid-call」。實際 `main.py:220-229` 的 demo handler 沒有發任何 notification；`Handler = Callable[[str, Any], Any]`（`main.py:137`）不接收 transport，`_handle_one` 雖收 transport 卻沒傳下去，handler 無從寫 notification；`tests/test_transport.py` 只有單獨呼叫 `write_notification` 的測試（`:151-161`）。講義描述的功能不存在。
22. `22-jsonrpc-stdio-transport/code/main.py:192` — `text = line.decode("utf-8")...`：遇到非法 UTF-8 位元組會拋 `UnicodeDecodeError`，沒有被 catch，`serve` 直接中止。依規格應回 -32700 並繼續（講義 `docs/en.md:63,90`「The stream is not poisoned」）。
23. `22-jsonrpc-stdio-transport/code/main.py:79-81` — 信封不合法時 `rid = msg.get("id")` 直接回傳原 id，即使 id 本身就是不合法型別（例如 `true` 或物件）；規格要求無法取得有效 id 時回 `null`。測試 `test_boolean_id_rejected` 只檢查錯誤碼，沒檢查回傳的 id 是否為 `true`。
24. `22-jsonrpc-stdio-transport/docs/en.md:106` — 「a content-type negotiation handshake so the same socket can speak JSON-RPC and Streamable HTTP」：Streamable HTTP 是承載 JSON-RPC 的 MCP 傳輸層，兩者不是並列的替代協定；同段 `$/cancelRequest` 是 LSP 慣例，MCP 用的是 `notifications/cancelled`（概念混用，非致命）。
25. `23-function-call-dispatcher/code/main.py:180-194,210-212` — idempotency dedupe 競態：`dispatch` 先查 `_inflight`，再 `async with self._sem`，而 `_inflight[key]` 要到進入 `_run_with_retries`（已取得 semaphore）才登記。當 semaphore 已滿，第一個呼叫在 `acquire` 處掛起、尚未登記 future；第二個同 key 呼叫此時查不到 in-flight，也去排 semaphore → 兩者先後都會執行 handler。測試 `tests/test_dispatcher.py:157-180` 用 `max_attempts=1` 且 semaphore 有空位，所以沒抓到。修法：在取得 semaphore 前就登記 future。
26. `23-function-call-dispatcher/code/main.py:263-269` — `_invoke` 對同步 handler 直接 `handler(**args)`，阻塞 event loop；`asyncio.wait_for` 只能在 await 點取消，對同步阻塞 handler 的 timeout 形同無效。講義 `docs/en.md:45`「On timeout, the handler task is cancelled」只對 async handler 成立，且 `docs/en.md:41`/ToolRecord 明說 handler 可以是 sync。
27. `23-function-call-dispatcher/docs/en.md:69` — 「The harness derives it from the planner: `f"{step_id}:{tool_name}:{hash(args)}"`」：`args` 是 dict（`dispatch(name, args: dict)`），`hash(dict)` 會拋 `TypeError: unhashable type`；即使改成 tuple，Python `hash` 對 str 有跨行程隨機化，不能當跨重啟的 idempotency key。
28. `23-function-call-dispatcher/docs/en.md:133` — 「tests … do not depend on wall-clock timing」：`tests/test_dispatcher.py:77,80`（`asyncio.sleep(0.05)` 對 `timeout_ms=5`）、`:209`（`sleep(0.01)`）都依賴真實時間，只是時間差夠大。另 `docs/en.md:61`「The retry loop respects the budget」：程式只在入口檢查一次 `budget_tool_calls_remaining`（`main.py:175`），重試不扣預算。
29. `23-function-call-dispatcher/docs/en.md:83` — 「`schema` and `not_found` go to `on_error` and trigger a replan」：第 20 課的 HarnessLoop 根本沒有 replan 路徑（見錯誤 #14），跨課契約不一致。
