### 整體品質
- 程式品質普遍「乾淨、可讀、有型別、有測試」，工程衛生（atomic write、weights_only、path traversal 檢查、subprocess timeout）比一般教學 repo 好。但「乾淨」掩蓋了內容空洞：13 堂中有 8 堂（49–57）的核心智慧行為全是 mock（查表 LLM、模板語料、合成 reward、`"x"*80` 擴寫、`originality_tag` 旗標），學到的是「把 dataclass 串起來」，不是假說生成、文獻檢索、評測或審稿本身。
- 講義與程式不一致是系統性問題：本報告列出 81 條具體錯誤中，約一半屬「講義描述程式沒做的事」（51 的雙 API 聯集、52 的 OOM 測試、53 的 log improvement 數值、54/55 的 manifest 銜接、57 的測試名稱、59 的測試清單）。

### 沒有 outputs/ 是否合理？
- 宣稱的 Ship It 是「產出可重用 artifact」。47–49 有 outputs/（skill md + demo JSON），符合；但 49 的 `leaderboard.json` 中 `"adapter": "arithmetic"` 不是目前程式會產生的值，表示 outputs 不是由程式重新生成。
- 50–59 共 10 堂完全沒有 outputs/，講義也沒有 Ship It 段落（58、59 甚至有 Use It 卻無 Ship It）。就「artifact」承諾而言**不合理**：這些課的程式都把產物寫進 tempdir（54 的 paper.tex、57 的 demo report）或只印到 stdout，學員無從比對預期輸出。最低限度應提交 demo 的預期 JSON（如 56 的 SchedulerReport、57 的 DemoReport、58/59 的 shape/param 摘要）以及對應 skill 檔。
- 從整個 Phase 19 看（`ls */outputs` 只有 28 個目錄，20–45、50–81 大多沒有），outputs/ 的有無看起來取決於「哪一批生成流程」，而不是課程需要。

### Capstone 是否真的整合前面 phase？
- **對前面 phase（00–18）的整合：幾乎沒有。** 13 堂沒有任何一堂 import 或引用 phases/00–18 的程式；Prerequisites 只寫 Phase 19 內部的 20–29、30–37、42–45、50–53。47/48 依賴的是 PyTorch 本身而非 Phase 03/07/10 的手刻元件；58/59 重新手刻 attention/LayerNorm 流程，而不是沿用 Phase 07 或 Phase 19 lesson 33–34（multihead-self-attention、transformer-block）。
- **Phase 19 內部整合：部分、且多為宣稱。** 實際有 import 的只有 57（→54/55/56）與 59（→58）。50–53 宣稱以 Track A 20–29 為先修，但程式完全不使用 20–29（52 的 subprocess runner 與 26-sandbox-runner-denylist 主題重疊卻重新實作、且更弱——沒有 denylist/path jail）。57 自稱「end-to-end」卻把 50–53 換成 stub，等於承認介面無法組合。
- **重複而非整合：** 依目錄標題，47 與 80-checkpoint-sharded-resume、48 與 76–78（collective ops / DDP / ZeRO）、49 與 27-eval-harness、41-eval-pipeline、70–75（task spec / code-exec metric / leaderboard）主題高度重疊（我只看了標題與開頭摘要，未全文比對，交由負責該範圍的組確認）。同一 phase 內多次重做同一主題，顯示 capstone 是平行量產的 track，而非逐步累積的整合專題。

### 適合誰
- 適合：已懂 PyTorch 與 Python、想看「訓練基礎設施（checkpoint、DDP、ViT）怎麼寫得乾淨」的中階工程師——47、48（DDP 部分）、52、53、56、58、59 值得一讀。
