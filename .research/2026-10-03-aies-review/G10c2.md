### 具體錯誤（批次 1）
- **E1** `75-end-to-end-eval-runner/docs/en.md:115`「The leaderboard ranked the rule-based adapter strictly above the random adapter.」——程式沒有 random adapter，三個 adapter 是 rule_based / noisy / biased；`code/main.py:373-380` 實際檢查的是「rule_based 排第一且不在最後」。quiz.json 的 post 題照抄同一錯誤。
- **E2** `75-end-to-end-eval-runner/docs/en.md:117`「the runner exits non-zero with a structured error in the JSON envelope」——`EvalReport.error` 從未被設定（`main.py:84,94`），`demo()` 只 print 字串回傳 1/2/3，驗證失敗時 `_load_fixture_tasks` 直接 raise RuntimeError（`main.py:345`），不會有 JSON envelope。另 `docs/en.md:67`「worker count defaults to the smaller of eight and the task count」，程式是 `min(max_workers, len(work))`，work = adapters×tasks（`main.py:159`），demo 還傳 6。
- **E3** `76-collective-ops-from-scratch/docs/en.md:39`「Each rank owns chunk index equal to its rank … After N-1 steps, rank r owns the full sum for chunk r.」——依該段描述的排程（step s 送 (r−s) mod N、收 (r−s−1) mod N），N−1 步後 rank r 持有完整和的是 chunk (r+1) mod N。程式自己的 docstring 也承認：`code/main.py:176-178`「The underlying ring algorithm parks the full sum at index (r + 1) % W」，並因此在 `reduce_scatter` 先做 rotate 修正。講義與程式自相矛盾。
- **E4** `76-collective-ops-from-scratch/code/main.py:131-145` 樹狀 broadcast 只從持有者往「更大編號」擴散（`partner = h + (1 << round_idx)`），當 `src != 0` 時編號小於 src 的 rank 永遠不會加入 `has_value`，`while len(has_value) < w` 無窮迴圈（所有 rank 都在本地空轉、不會 timeout）。demo 與測試只用 src=0 所以沒抓到。應以 `(h - src) mod w` 的相對 rank 計算 partner。
- **E5** `76-collective-ops-from-scratch/docs/en.md:21`「Pipeline parallel needs broadcast for activations across stage groups」與 `:100`「Lesson 79 wires broadcast into pipeline activations」——pipeline parallel 的 activation 傳遞是相鄰 stage 的點對點 send/recv，不是 broadcast（疑似概念錯；79 實作待後批核對）。`:55,70` 宣稱「byte-equal comparison」，但不同求和順序的 float32 不會 byte-equal，程式也用 `1e-5`（`main.py:343`）。
- **E6** `77-data-parallel-ddp/docs/en.md:60`「a rank-specific seed for params means initial parameters disagree by float epsilon and gradient sync no longer makes the replicas identical」——兩處錯：(a) 不同 seed 產生的初始參數是完全不同的隨機值，不是「差 float epsilon」；(b) 本課 DDP 在建構時就從 rank 0 broadcast 參數（`code/main.py:72-74`），所以 param seed 不一致根本無所謂——這正是 broadcast 的用途。同段「A single shared seed means every rank sees the same batch order」也與程式不符：程式用 rank offset 切資料（`main.py:117`），不靠 seed。
- **E7** `77-data-parallel-ddp/docs/en.md:3`「install a backward hook on every parameter that issues an allreduce」、`:21`「We can do all three [bucketing, overlap, NCCL] on CPU with gloo」、`:56`「For the lesson's tiny model we group everything into one bucket」——程式 `sync_grads()`（`main.py:76-81`）是 backward 結束後逐參數同步呼叫 `dist.all_reduce`，無 hook、無 bucket、無 overlap。`:73` 提到的 `_reference_single_process_loop` 實名為 `reference_single_process`；`:13` 說用 `torch.multiprocessing.spawn`，實際是 `mp.get_context("spawn").Process`。

- 結論：Phase 19 的這段「capstone」整合度兩極：eval track（75）整合扎實；safety track（87）大致可信；distributed track（81）是以複製取代整合，最弱。整體而言 capstone 主要整合「同一 track 內的前幾課」，**幾乎沒有整合前面 phase 的內容**。

## 模板化／AI 量產跡象

- 76–81 六課：完全相同的骨架（Learning Objectives → The Problem → The Concept → Build It → 「Production patterns in the wild」＋固定句式「Three patterns harden X enough to ship.」→ Use It「Production patterns:」三點 → Ship It → 5 題 Exercises → Key Terms「What people say / What it actually means」），Prerequisites 與 Time 一字不差；`_loopback_iface`、spawn+file rendezvous+queue 回收的樣板程式在 76–81 重複 6 次；MiniMLP/make_dataset 在 77、78 逐字重複。
- 82–87 六課：另一套骨架（Problem/Concept/Build It/Use It/Ship It/3 題 Exercises/Key Terms「Common usage / Precise meaning」），每課開頭一句格言式引言，且 82、83、86 三課都用「Anything else is a vibe」「is a vibe, not a rule」同一句型；82 與 85 的 `_trigrams/_cosine` 逐字重複。
- 講義與程式不一致的模式反覆出現（講義描述不存在的類別/函式/輸出：77 的 hook/bucket、78 的 flatten_params、79 的 PipelineStage/Pipeline、81 的 NaN guard hook、83 的 CSV、86 的 JSON loader），典型的「先寫規格文、程式後改但沒回頭同步」或量產痕跡。
- 跨課「X 會被 Y 使用」的宣稱大量不實（E8、E14、E24、E30、E33、E39），像是依大綱預先寫好而非依實作。
- 測試中有湊數或套套邏輯（77 `SEED==7`、87 全集合 assertIn）。

## Phase 層級總評（本組 13 堂）

- **整體品質**：中等。程式大多能自圓其說、確實「從零」寫（純 Python／torch 張量當容器），沒有虛構 API 的程式碼；但講義品質明顯低於程式，常描述程式沒有的功能、數字前後矛盾，且「組合／驗證」類宣稱多數誇大。安全 track 的 mock 設計（用 `REDACTED_HARMFUL` 字面當判斷依據）讓 84、87 的評估數字幾乎沒有資訊量。
- **最強 3 堂**：86-constitutional-rules-engine（設計完整、手寫 YAML 子集、fix→recheck→diff 迴圈）、76-collective-ops-from-scratch（真的在 Queue 上手寫 ring allreduce 等四個 collective 並以 gloo 對照、量測 per-rank bytes；雖有 broadcast src≠0 bug 與講義錯誤）、80-checkpoint-sharded-resume（manifest+sha256+fsync+路徑穿越防護+rotation，工程細節扎實）。75 次之（真整合 70–74）。
- **最弱 3 堂**：81-end-to-end-distributed-train（號稱 capstone 卻複製貼上、4 個 invariant 只驗 1 個且是假 resume、隨機 token 訓練、違背 80 的設計原則）、79-pipeline-parallel（「measured bubble」是套套邏輯、「真 pipeline」沒有 pipelining、講義描述的類別不存在）、84-refusal-evaluation（mock 只對佔位字串反應，per-category 結果無意義；ECE 獨立性的論述錯誤）。
- **模板化程度**：高。兩個 track 各自一套固定骨架與固定句型，樣板程式大量重複，跨課宣稱不實。
- **適合誰**：已有分散式訓練或 LLM 安全基本概念、想看「最小可執行骨架」的工程師——拿 76/80/86 的程式當參考實作很有價值；**不適合**把講義數字與「生產實務」敘述當權威來源的初學者（需搭配官方文件查證，且應自行修正 broadcast、atomic rename、評估洩漏等問題）。
