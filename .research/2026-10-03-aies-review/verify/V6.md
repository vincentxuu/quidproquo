## 1. G10a #52 — speculative decoding 接受規則
- 指控：`14-speculative-decoding-server/code/main.py:63-69` 用 `dist[tok] >= 0.5*max(dist)` 接受、拒絕後從 p 原分布重抽，不是 `min(1,p/q)` + 殘差 `norm(max(0,p-q))`，失去「輸出分布等於 target」保證；講義 `docs/en.md:19` 講成 greedy。
- 覆核：讀 main.py:1-110。行號正確：`:64-69` 為 `# simple accept criterion: target prob on this token >= 0.5 * max prob` / `if dist[tok] >= 0.5 * max(dist)`；`:71-73` `dist = self.distribution(ctx); next_tok = sample(dist, rng)`（從 p 重抽）。檔頭 docstring 只說「scaffold … synthetic token probabilities」，註解自稱 simple criterion，但全課（docs、quiz）沒有任何地方說明正確的 rejection-sampling 規則或「這不保分布」；`docs/en.md:19`「any prefix accepted replaces the greedy path」。且此規則也不是 greedy 版（greedy 應為 draft==argmax 才接受、拒絕時取 argmax），兩種正確變體都不是。rubric `docs/en.md:102` 要求「2.5x+ throughput at matched quality」，程式卻無法保證 matched quality。
- 判定：✅ 成立
- 理由：引文、行號正確；課程主題核心演算法錯且從未標註為非無損近似。

## 3. G10a2 #41 — pass@k 有偏估計
- 指控：`27-eval-harness-fixture-tasks/code/main.py:132-138,405` 與 `docs/en.md:50` 用同一批 k 個樣本估 p 再算 `1-(1-p)^k`，會低估；Chen et al. 2021 的無偏估計是 `1-C(n-c,k)/C(n,k)`；quiz check 第 1 題把 3/5→0.99 當正解。
- 覆核：`main.py:131-138` `def pass_at_k(empirical_pass_rate, k): … return 1.0 - (1.0 - p) ** k`；`:398-405` `pass_rate = passes / self.k` → `pass_at_k(pass_rate, self.k)`（n=k）。`docs/en.md:50`「Pass@k is `1 - (1 - p)^k` where p is the empirical pass rate」。quiz check 題：「3 passes in 5 samples … pass@5 … correct: 0.99」。
  - 算式：python3 → n=5,c=1：plug-in 0.672、無偏 1.0；n=5,c=3：plug-in 0.98976、無偏 1.0。
  - 一手來源：Chen et al., arXiv 2107.03374（https://arxiv.org/pdf/2107.03374）：「One may be tempted to estimate pass@k with 1−(1−p̂)^k … but we show that it is biased in Appendix A」「results in a consistent underestimate」。
- 判定：✅ 成立
- 理由：引文與行號正確，數值與一手文獻皆支持；quiz 把有偏公式當正解，強化錯誤。

## 5. G10b #45 — loss scaling 講成防 overflow
- 指控：`45-gradient-clipping-amp/docs/en.md:21` 說 FP16 梯度 overflow 成 Inf，GradScaler 以放大 loss「solves this」；放大只會讓 overflow 更容易，loss scaling 的目的是防小梯度 underflow。
- 覆核：`docs/en.md:21` 原文：「A typical gradient that overflows in FP16 evaluates to Inf … PyTorch's GradScaler solves this by multiplying the loss by a large scaling factor before the backward pass …」行號正確。全課 grep `underflow`（docs、quiz、code）0 筆；`docs/en.md:3`「Mixed-precision training amplifies this by introducing FP16 overflow on the loss side」、`:13`「so FP16 forward and backward passes survive overflow」一路以 overflow 為主軸；quiz `:75` 亦只談 overflow。講義對 skip＋減半的機制描述正確，但「為何要放大」完全沒交代，且因果講反。
  - 一手來源：PyTorch 官方 AMP 文件 https://docs.pytorch.org/docs/stable/amp.html（Groundlane web_search 擷取該頁原文；web_fetch 全文逾時）：「Gradient values with small magnitudes may not be representable in float16. These values will flush to zero ("underflow") … To prevent underflow, "gradient scaling" multiplies the network's loss(es) by a scale factor」。
- 判定：✅ 成立
- 理由：講義把 loss scaling 的動機講反且全課未提 underflow；一手文件明確支持。

## 8. G10b2 #67 — 「150,528 tokens」「590,000x」
- 指控：`58-vision-encoder-patches/docs/en.md:19,38` 與 quiz Q1：224×224 RGB「150,528 tokens」、`150,528² = 22.6 billion`、「590,000x reduction」；150,528 是純量數，以像素為 token 應為 50,176，attention 50,176²≈2.52e9，相對 196² 為 65,536×。

Patches buy a 590,000x reduction」；quiz pre 題 explanation「A 224x224 image is 150528 pixel tokens」。python3：224·224=50,176；224·224·3=150,528；150,528²=2.266e10；150,528²/196²=589,824；50,176²/196²=65,536。講義自己的框架是「every pixel as a token」，同段又說每個 patch 是 (3,16,16)=768 個「pixel values」，可見 150,528 是 pixel value 數而非 pixel 數。講義的算術內部自洽，錯在 token 數多算 3 倍、加速比多算 9 倍；「patch 讓 attention 可負擔」的定性結論不受影響。
- 判定：✅ 成立
- 理由：數值錯誤確認（3×／9×），審閱者未誇大其影響。

## 9. G10c #48 — ECE 跨 bin 可抵消
- 指控：`73-perplexity-calibration/docs/en.md:56`「A model that is overconfident on half the bins and underconfident on the other half can have low ECE」錯：ECE = Σ(n_b/N)|conf_b−acc_b|，逐 bin 取絕對值，跨 bin 不抵消。
- 覆核：`docs/en.md:56` 原文：「ECE only cares about average gaps. A model that is overconfident on half the bins and underconfident on the other half can have low ECE while being poorly calibrated locally.」行號正確。講義自己的流程圖 `:45`「gap = abs avg conf - avg acc」、`:47`「ECE = sum of weighted gaps」；程式 `code/main.py:98` `total_gap += (size / n) * abs(avg_conf - avg_acc)`。逐 bin 的過/欠自信都以正值累加，不可能互相抵消；唯一可抵消的是同一 bin 內部的樣本（「locally」若指 bin 內才說得通，但原句明確說「half the bins」）。嘗試替講義辯護：若各 bin gap 都很小則 ECE 低，但那就不是 poorly calibrated，與句意不符。
- 判定：✅ 成立
- 理由：講義與自己的公式、程式矛盾，屬核心概念錯誤。

## 10. G10c #26 — N=K 時 reranker 無法重排
- 指控：`66-reranker-cross-encoder/docs/en.md:94`「If you set N = K, the cross-encoder cannot reorder; it can only reweight. The lift looks zero.」錯：N=K 仍會重排 K 筆（MRR/P@1 可提升），只是 top-K 集合不變（recall@K 不變）；quiz 第 4 題把此錯誤當正解。
- 覆核：`docs/en.md:94` 原文與行號吻合。程式 `code/main.py:157-171` `rerank()`：`out = sorted(zip(candidates, scores), key=lambda x: -x[1]); return out[:top_k]`——無論 N 是否等於 K 都依 cross-encoder 分數重新排序，故「cannot reorder」與本課程式直接矛盾。講義 `:88` 自己描述的收益正是「picking the answer that the bi-encoder ranked second or third」，這是 N=K 時也會發生的重排。quiz questions[3]（check）正解「If N equals K the cross-encoder cannot reorder, only reweight; rerank lift collapses to zero」，explanation「With N = K there is nothing to reorder」。只有 recall@K 型指標在 N=K 時 lift 為 0。
- 判定：✅ 成立
- 理由：被本課程式與講義他處推翻，且 quiz 強化錯誤。

## 11. G10c2 E9 — ZeRO 7B optimizer state 三種數字
- 指控：`78-zero-parameter-sharding/docs/en.md:3`「56 GB of optimiser state」、`:19`「14 GB params, 14 GB grads, 28 GB optimiser state」、`:58` 表格（master+m+v = 12P = 84 GB）同課三種數字；28 GB 只等於 fp16 兩個 moment，與 :3 的 fp32 假設與表格矛盾。
- 覆核：三處原文與行號吻合（`:3`「Adam stores two moment estimates per parameter, both in float32. A 7B-parameter model carries 56 GB」；`:19`；`:51-58` 表格 fp32 master/m/v 各 4P）。python3：7e9×8=56 GB（兩個 fp32 moment）、7e9×12=84 GB（含 fp32 master）、7e9×4=28 GB。替講義辯護：56 GB 與 84 GB 差在「是否把 fp32 master 算進 optimizer state」，各自在其定義下正確，不算錯；但 `:19` 的 28 GB 在講義任何定義下都對不上（`:49` 明說 mixed precision、moment 是 fp32），屬實錯。`:19` 的結論「optimiser state is the largest term」用 28 GB 仍成立，故不影響定性。
- 判定：✅ 成立
- 理由：28 GB 確為錯值、三處數字確不一致；審閱者已正確點出 28 GB 是錯的那個，未誇大。（備註：56 vs 84 屬定義差，非錯誤。）

## 12. G10c2 E12 — sharded checkpoint「單一 rename」原子性
- 指控：`80-checkpoint-sharded-resume/code/main.py:5-6`「a single rename moves everything … A crash mid-write leaves the previous checkpoint intact」；`:152-154` 實為逐檔 `os.replace`（N shard + 1 manifest）。對既有目錄覆寫時，在第 k 個 rename 後崩潰會讓舊 manifest 指向新 shard（sha 不符拒載），舊 checkpoint 被毀；講義 `:55` 同樣誤導。
- 覆核：docstring `:4-6` 原文吻合；`save_sharded`（`:105-158`）確為 `for tmp, final in tmp_paths: os.replace(tmp, final)` 後再 `os.replace(manifest_tmp, manifest_final)`，非單一 rename，`dest.mkdir(..., exist_ok=True)` 也允許覆寫既有目錄，該情境下指控的毀損路徑成立（會被 sha256 檢查擋下而非靜默載入）。但脈絡：本課所有呼叫端都寫到**每步獨立目錄**——demo `:254` `step_0100`、rotation `:283` `step_{s:04d}`；在此用法下 manifest 最後才 rename，崩潰只會留下缺 manifest 的新目錄（`load_sharded` 以「manifest missing」拒載），前一步目錄完全不受影響，docstring「previous checkpoint intact」在本課實際用法下成立。講義 `docs/en.md:55` 也是描述 per-file rename + 「previous checkpoint as the live one」，並在 `:106` 提到 DeepSpeed 的 `latest` 指標做法。
- 判定：⚠️ 部分成立
- 理由：「single rename」措辭確實不實，覆寫同目錄時的毀損路徑也成立；但本課的使用模式（每步新目錄）使宣稱的保證實際成立，審閱者沒提這點，嚴重度應降為「措辭不精確＋覆寫同目錄時不安全」。
