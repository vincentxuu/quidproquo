## SQ2：為什麼會發生（機制）

### 1. POSIX：父程序死亡 → 子程序被系統程序收養（不會連帶死）
- POSIX `_exit()`：子程序的 parent PID「shall be set to the process ID of an implementation-defined system process」。SIGHUP 只在「terminating process is a controlling process」時送給「foreground process group of the controlling terminal」；孤兒 process group 只有在「any member … is stopped」時才收到 SIGHUP＋SIGCONT。🟡（WebFetch 摘錄）https://pubs.opengroup.org/onlinepubs/9799919799/functions/_exit.html
- [推論] agent 的 tool shell 通常不是有控制終端的 session leader，且背景子程序沒被 stop，所以父死後**沒有任何信號**送到子程序，它們被 launchd／init／`systemd --user`（subreaper）收養繼續跑——與 #95821、#96625、#103658、Cursor WSL 案中觀察到的 PPID 1／`/init`／`systemd --user` 完全一致。

### 2. setsid／nohup／`&`：把程序移出可被一併殺掉的範圍
- setsid(2)：「creates a new session if the calling process is not a process group leader」，新 session「has no controlling terminal」。🟡 https://man7.org/linux/man-pages/man2/setsid.2.html
- GNU nohup：「runs the given command with hangup signals ignored」；「`nohup` does not automatically put the command it runs in the background; you must do that explicitly, by ending the command line with an ‘`&`’」。✅ https://www.gnu.org/software/coreutils/manual/html_node/nohup-invocation.html
- [推論] agent 常寫 `nohup uvicorn … > log 2>&1 &`：`&` 讓 shell 立刻返回、tool 呼叫結束；`nohup` 擋掉 SIGHUP；若再 `setsid` 則連 process group 都換掉，以 pgid 殺樹也打不到。Claude Code 官方文件特別說明 `/tasks` 停止與 exit 時會連「started under `setsid` or `timeout`」一起停，反過來說明這是已知逃逸路徑；但 #96625 證明 crash／shell 先死時沒有這層保護。Cursor staff 也點名 `&`、`nohup`、`> file 2>&1` 這幾種寫法。

### 3. Node child_process：殺父不殺孫
- Node docs：「On non-Windows platforms, if `options.detached` is set to `true`, the child process will be made the leader of a new process group and session. Child processes may continue running after the parent exits regardless of whether they are detached or not.」✅
- `subprocess.kill()`：「[On Linux, child processes of child processes will not be termi]nated when attempting to kill their parent. This is likely to happen when running a new process in a shell or with the use of the `shell` option」，範例註解「Does not terminate the Node.js process in the shell.」✅ https://nodejs.org/api/child_process.html
- [推論] Node 寫的 agent／IDE（Claude Code、Cursor、Codex 的 codex.js wrapper）若對 shell 的 PID 呼叫 `kill()`，`npm run dev` → `vite` → `esbuild`、`pytest` → xdist workers 這類孫程序就會被留下。#90672 的 Windows 實驗（殺 bash wrapper，兩個 python 孫程序存活）是同一現象的 Windows 版；Windows 沒有 process group，要靠 Job Object＋`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`。

### 4. MCP stdio 生命週期：規格把關閉責任交給 client，且是 SHOULD
- MCP spec 2025-06-18 Lifecycle › Shutdown › stdio：「the client **SHOULD** initiate shutdown by: 1. First, closing the input stream to the child process (the server) 2. Waiting for the server to exit, or sending `SIGTERM` if the server does not exit within a reasonable time 3. Sending `SIGKILL` if the server does not exit within a reasonable time after `SIGTERM`」；「No specific shutdown messages are defined」。✅ https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle
- 實際破口：
  - client 只對「connected」的 server 做這套流程，「connecting／queued」的漏掉（#93087，2.1.283 修）；連線逾時後不殺已 spawn 的程序，重連再 spawn 一個（#95821，OPEN）。
  - client 自己被 SIGKILL／crash → 沒有人送 SIGTERM，只剩 stdin EOF；server 若沒監聽 stdin close（Cursor staff：「Some MCP server authors added stdin POLLHUP handling」）就永遠活著。
  - 中間層：Playwright 維護者主張 npx／npm exec 以 `stdio: 'inherit'` 傳遞同一條 pipe，EOF 能傳到；只有「re-piping intermediary (stdio↔socket bridge like mcp-remote/supergateway)」會吞掉 EOF（#1634）。但信號不同：送給 `npx` wrapper PID 的 SIGINT/SIGTERM 不一定轉給真正的 server（#1935 sbking 的觀察）。[推論] 兩者不矛盾：EOF 走 fd 繼承能穿透，信號只打到 wrapper。
  - 每個 session／thread 各起一套 MCP server（Codex #30408：每 thread 一套；Cursor：每個 entry 2 個程序），平行 session 數直接乘上程序數。

### 5. Playwright MCP 的瀏覽器壽命
- 瀏覽器預設活到 MCP session 結束；`--idle-timeout`／`PLAYWRIGHT_MCP_IDLE_TIMEOUT` 可閒置關閉（#1806、#1769 維護者）。✅
- 若 MCP server 本身被直接殺死（未走 graceful close），Chrome 樹被收養到 PID 1（#1634 回報者的 kill -9 重現；維護者在其設定下無法重現）。
- 容器中 node 為 PID 1 時不會 reap Chrome 的孫程序 → `<defunct>` 累積，`--init`／tini 修正（#1769）。✅
- 每個 `mcp-chrome-*` user-data-dir 留在 `~/.cache/ms-playwright/`（#1568：11 個 ~1 GB）。

### 6. pytest-xdist／execnet
- xdist controller 以 execnet gateway 起 worker 子程序；teardown 走 `Group.terminate(EXIT_TIMEOUT=10)`，超時走 kill path 且「reports success anyway」（execnet #429，已關）。✅
- `pytest-timeout` 在 worker 內計時，controller 卡住時無效（unsloth PR #9530）。🔎
- Python 3.14 下 controller 在 `dsession.loop_once` 無限等待（#1313，OPEN）。✅
- [推論] agent 端看到的是「pytest 卡住／逾時 → 被移到背景或殺掉 shell」，controller 被殺而 worker（各自 import 整個 Django／app，記憶體大）留下；平行 worktree × `-n auto` 讓記憶體壓力成倍。

### 7. vite／esbuild／vitest
- vitest forks worker 在 Ctrl+C 非優雅退出時殘留（#9123，2025-12 修）。✅
- Cursor 案例：`npm exec vite` → `node vite` 兩層，Stop 只結束 shell wrapper（forum 171517）。🟡
- esbuild 以子程序服務模式運作的生命週期：⚪ 未找到官方文件或 issue（`gh search` esbuild orphan 無相關結果）。

### 8. agent 特有的放大因素 [推論，有回報佐證]
- 自動背景化：Claude Code 逾時改背景而非殺掉（官方文件）；Codex 背景 terminal 不逾時（#41841）——長跑程序的存活時間從「一次 tool call」延長到「session 壽命」，session 異常結束時就成了孤兒。
- model 自己用 `pkill -f` 殺 shell，反而把 pipeline 孫程序孤立（#96625 留言）。
- watch 模式（vitest watch、`tsc --watch`、dev server）本來就不會結束（Cursor 147911 的 `testOnce` 規避）。
- 平行 session／worktree：每個 session 一套 MCP＋Chrome＋dev server；port 衝突使 agent 再起一個新 port 的 server（boxes.dev、Kelpie、Cursor 134793）。
