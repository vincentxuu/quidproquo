## SQ4：OS 層解法與極限

### 4.1 Process group／`kill -- -PGID`（macOS 與 Linux 都有）

- ✅ macOS `kill(1)`（本機 man）：「Terminate the process group with PGID 117: `kill -- -117`」；`kill(2)`：pid 為負時「the signal is sent to all processes whose process group ID is equal to the absolute value of the process number. This is a variant of killpg(2).」
- ✅ process-compose 文件把這當預設停止方式：「The default behavior in this case: `SIGTERM` is issued to the process group of the running process.」逾時則「the process group will receive the `SIGKILL` signal」。<https://github.com/F1bonacc1/process-compose/blob/main/www/docs/launcher.md>
- 極限：
  - 只殺得到「還留在同一個 process group」的後代。子程序自己 `setsid`／daemonize／`nohup … &` 進新的 session 或 group 就脫離 [推論，依 POSIX 語意]。
  - ✅ 實例：Claude Code issue #102511（2026-10-15，Linux，open）——協調器對 CLI 的 process group 送 SIGTERM，但被自動移到背景的 Bash 指令「was reparented to `systemd --user`, in its own process group (pgid = its own pid)」，繼續跑了 1 小時 47 分。<https://github.com/anthropics/claude-code/issues/102511>
  - **macOS 沒有 `setsid(1)` 指令**（本機實測 `command -v setsid` 無結果），要開新 group 得用 `perl -e 'setpgrp'`、`python -c os.setsid()` 或 shell `set -m` [推論]。

### 4.2 Linux：`PR_SET_PDEATHSIG`／`PR_SET_CHILD_SUBREAPER`（Linux 限定）

- ✅ PR_SET_PDEATHSIG：「This is the signal that the calling process will get when its parent dies.」限制：「The parent-death signal setting is cleared for the child of a fork(2)」，而且 setuid 二進位與憑證變更時也會清掉；CAVEATS：「the signal will be sent when that thread terminates … rather than after all of the threads in the parent process terminate」。<https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html>
  - 意思是：只保護直接子程序。孫程序（例如 npm → node → chrome）不會繼承，要每一層都設 [推論]。
- ✅ PR_SET_CHILD_SUBREAPER：「When a process becomes orphaned … that process will be reparented to the nearest still living ancestor subreaper」；「not inherited by children created by fork(2)」。<https://man7.org/linux/man-pages/man2/PR_SET_CHILD_SUBREAPER.2const.html>
  - 用途：讓 agent 的外層 wrapper 收養所有孤兒，退出前一次清掉。限制：subreaper 自己被 SIGKILL 的話，孤兒還是會往上交給下一層 subreaper 或 init [推論]。
- **macOS 沒有對應的 prctl**。最接近的是用 kqueue `EVFILT_PROC` 搭配 `NOTE_EXIT` 監看父程序（✅ 本機 `man kqueue`：「NOTE_EXIT The process has exited.」），但這要子程序自己寫程式監看，不是 OS 自動處理 [推論]。

### 4.3 Linux：cgroups v2／`systemd-run --user --scope`（Linux 限定，最完整的解）

- ✅ systemd-run：`--scope`「Create a transient `.scope` unit」；scope 模式下指令「executed by systemd-run itself as parent process … processes of the command are managed by the service manager」。<https://www.freedesktop.org/software/systemd/man/latest/systemd-run.html>
- ✅ systemd.resource-control：
  - `MemoryHigh=`：「Specify the throttling limit … Memory usage may go above the limit if unavoidable, but the processes are heavily slowed down … This is the main mechanism to control memory usage of a unit.」
  - `MemoryMax=`：「absolute limit … If memory usage cannot be contained under the limit, out-of-memory killer is invoked inside the unit. It is recommended to use MemoryHigh= as the main control mechanism and use MemoryMax= as the last line of defense.」
  - `MemorySwapMax=`：「absolute limit on swap usage」。
  - 來源：<https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html>
- ✅ kernel cgroup-v2 文件：
  - `memory.high`：「Going over the high limit never invokes the OOM killer and under extreme conditions the limit may be breached.」
  - `memory.max`：「If a cgroup's memory usage reaches this limit and can't be reduced, the OOM killer is invoked in the cgroup.」
  - `memory.oom.group`：「all tasks belonging to the cgroup … are killed together or not at all」。
  - `cgroup.kill`：「Writing "1" … all processes located in the affected cgroup tree will be killed via SIGKILL. Killing a cgroup tree will deal with concurrent forks appropriately and is protected against migrations.」→ 這是唯一能可靠「整棵樹一起殺」的機制，不怕 setsid／double-fork。
  - 來源：<https://docs.kernel.org/admin-guide/cgroup-v2.html>
- 典型用法 [推論]：`systemd-run --user --scope -p MemoryHigh=6G -p MemoryMax=8G -p MemorySwapMax=0 -- claude …`；session 結束時 `systemctl --user stop <scope>` 或寫 `cgroup.kill`。
- 極限：
  - 需要 cgroup v2 與 user manager 的 delegation。
  - OOM 殺掉 pytest-xdist worker 時，xdist 可能整組卡住：✅ pytest-xdist #658（open）「sometimes the kernel kills one of the pytest workers … the test suite never recovers … the whole setup hangs」<https://github.com/pytest-dev/pytest-xdist/issues/658>。也就是說 MemoryMax 會把「爆記憶體」換成「測試卡住」，要配 `timeout` 一起用。
  - macOS 完全沒有 cgroups。

### 4.4 `timeout`（GNU coreutils）

- ✅ timeout(1)：「Start COMMAND, and kill it if still running after DURATION」；`-k, --kill-after` 補送 KILL；`--foreground`「in this mode, children of COMMAND will not be timed out」。<https://man7.org/linux/man-pages/man1/timeout.1.html>
- 極限：
  - 預設會把訊號送到它建立的 process group [推論，依 coreutils 實作；man page 沒寫明]，但用 `--foreground` 就不管孫程序。
  - **macOS 預設沒有 `timeout`／`gtimeout`**（本機實測都找不到），要 `brew install coreutils`。

### 4.5 ulimit／setrlimit：為什麼 RLIMIT_AS／RSS 在 macOS 沒用

- ✅ macOS SDK `sys/resource.h`（本機）：`#define RLIMIT_AS 5 /* address space (resident set size) */`、`#define RLIMIT_RSS RLIMIT_AS /* source compatibility alias */`，兩者在 macOS 是同一個值。
- ✅ macOS `setrlimit(2)`（本機 man）對 RLIMIT_RSS 的說明：「if memory is tight, the system will prefer to take memory from processes that are exceeding their declared resident set size」。這是回收時的偏好，不是硬上限。launchd.plist 的 `ResidentSetSize` 也是一模一樣的文字。
- ✅ **本機實測（macOS 26.5.2）**：
  - zsh `ulimit -m` →「bad option: -m」。
  - `ulimit -v 1048576` →「setrlimit failed: invalid argument」。
  - Python `resource.setrlimit(RLIMIT_AS/RLIMIT_RSS, 512MB/1GB)` → `ValueError: current limit exceeds maximum limit`。
  - 原因：一個 zsh 的 VSZ 就已經約 415 GB（`ps -o vsz` = 435308096 KB，大部分是共享快取的虛擬保留區），任何合理的 AS 上限都低於現值 [推論：VSZ 與共享區的關聯]。
- 結論：macOS 沒有任何可用的「單程序記憶體硬上限」。Linux 的 RLIMIT_AS 雖然能設，但 Chromium、V8、Go 這類會大量保留虛擬位址的程式一設就啟動失敗，所以實務上也該用 cgroup [推論]。

### 4.6 macOS launchd（LaunchAgents）

- ✅ launchd.plist(5)（本機 man）：
  - `AbandonProcessGroup`：「When a job dies, launchd kills any remaining processes with the same process group ID as the job. Setting this key to true disables that behavior.」→ 用 LaunchAgent 跑 dev server，預設就有「主程序死了，整組一起清」的效果。限制同 4.1：出了 process group 的就管不到。
  - `StartInterval`：「causes the job to be started every N seconds. If the system is asleep during the time of the next scheduled interval firing, that interval will be missed」→ 適合拿來跑「定期清孤兒」的掃描器，但睡眠期間會漏跑。
  - `ExitTimeOut`：SIGTERM 到 SIGKILL 之間的等待時間。
  - `SoftResourceLimits/HardResourceLimits`：「These adjust variables set with setrlimit(2)」→ 一樣受 4.5 的限制，`ResidentSetSize` 不是硬上限。
  - `ProcessType`：「The system will apply resource limits based on what kind of job it is … preferable to using the HardResourceLimits, SoftResourceLimits and Nice keys」。Background 類只限 CPU／IO，不限記憶體 [推論]。
- ✅ `launchctl limit` 只是印出或調整 launchd 本身的 getrlimit 值。

### 4.7 macOS 記憶體壓力與 swap 為什麼一直長

- ✅ Apple《About the Virtual Memory System》（archive 文件，舊但仍是官方說法）：「Unlike most UNIX-based operating systems, OS X does not use a preallocated disk partition for the backing store. Instead, it uses all of the available space on the machine's boot partition.」<https://developer.apple.com/library/archive/documentation/Performance/Conceptual/ManagingMemory/Articles/AboutMemory.html>
  - 意思是 swap 沒有固定上限，會隨需求增加 swapfile。
- ✅ 本機觀察（18 GB RAM 機器）：`/System/Volumes/VM` 有 swapfile0–12 共 13 個檔案；`vm.swapusage` total = 13312 MB、used = 11695 MB；`memory_pressure` 顯示 System-wide memory free 38%。
  - 這跟題目描述的「swap 一直長」吻合：孤兒程序的閒置頁被換出，不會讓系統死，只會讓 swap 一直累積，等到有人要用時就整台變慢 [推論]。
- ✅ `memory_pressure(1)`（本機 man）：可以施加真的或模擬的壓力（`-S -l warn|critical`），也能讀出系統可用百分比。可以拿來當「高壓就暫停開新 agent／測試」的訊號來源，但它不是限制器 [推論]。
- 極限：
  - macOS 沒有提供使用者層的記憶體上限或 OOM 控制。jetsam 主要作用在 iOS，macOS 上一般 CLI 程序不會被主動殺掉，只會被壓縮、被換出 [推論，未找到 Apple 一手文件，⚪ 缺口]。

### 4.8 容器／devcontainer／Docker Desktop（macOS 上唯一的「硬上限」）

- ✅ Docker 引擎：「By default, a container has no resource constraints」；`-m/--memory`：「The maximum amount of memory the container can use」；另有 `--memory-swap`。<https://docs.docker.com/engine/containers/resource_constraints/>
- ✅ Docker Desktop 設定：Memory limit「RAM allocated to the Docker VM … Defaults to 50% of your host's memory」；Swap「1 GB default」；Resource Saver「automatically turning off the Linux VM when Docker Desktop is idle」。<https://docs.docker.com/desktop/settings-and-maintenance/settings/>
  - 在 macOS 上這等於所有容器加起來的總上限（VM 大小）。容器裡的程序 OOM 只會在 VM 內被殺，不會拖垮主機 swap [推論]。
- ✅ devcontainer `hostRequirements.memory`：「A string indicating **minimum** memory requirements」→ 這是最低需求，不是上限，常被誤用。要限制得在 `runArgs` 加 `--memory`。<https://containers.dev/implementors/json_reference/>
- 極限：
  - Docker Desktop VM 會預先切走主機一半記憶體 [推論：VM 實際佔用會隨使用長大，平常不一定吃滿]。
  - bind mount 檔案 IO 慢，見同頁 File sharing 的說明「Sharing too many files can lead to high CPU load and slow filesystem performance」。
  - Playwright／Chromium 進容器要另外處理（headless、`--no-sandbox` 等）[推論]。

### 5.2 程序管理器（給 dev server 用）

- ✅ process-compose：預設送 SIGTERM 給整個 process group，逾時改送 SIGKILL，另有 `parent_only`、`ordered_shutdown`、`shutdown.command`。一個 worktree 一份 `process-compose.yaml`，用它統一起停 uvicorn／celery／vite 很合適。限制：process-compose 自己被 SIGKILL 時，子程序會不會被清掉文件沒有說明 [⚪ 缺口]。
- 🟡 overmind：tmux 底層，「assigns the port base (5000 by default) to `PORT` … increases `PORT` by port step (100 by default)」，支援 Linux、BSD、macOS。最後更新 2025-04。
- 🔎 mprocs：「Process manager for dev and prod」，README 沒寫 group-kill 細節。
- ✅（README）portless（vercel-labs）：「Each app gets a random port from 4000 to 4999」，會偵測 worktree 給子網域（`fix-ui.myapp.localhost`），並有 `prune`、`clean`「Prune orphans」指令。它解決的是 port 撞號與「測錯分支」，不管記憶體。
- 未查：foreman／honcho、pm2（⚪ 缺口，優先度低）。

### 5.3 一手經驗文章（2025 年以後）

- 🟡 Oshri Cohen（2026-06-09）：同時跑 6–10 個 agent，每個 worktree 一套 compose stack「~4 GB memory per worktree stack」，在 32 GB 的 M1 Pro 上用了 16 GB；建議共用有狀態的服務、用 namespace 分資料、把 stack 搬到遠端。<https://www.oshricohen.me/blog/ten-coding-agents-one-laptop/>
- 🟡 whattheport.dev 指南：「A Next.js dev server commonly uses 500 MB to 2 GB. Multiply by five and a 16 GB Mac starts swapping」；「Servers outlive their worktrees」；建議 Vite 設 `strictPort: true`。<https://whattheport.dev/guides/parallel-coding-agents-git-worktrees-ports>（無日期，像 SEO 導購文，權威性低）
- 🟡 Steamfield（2026-11-05）：「A suite configured to use every core (`pytest -n auto` …) assumes it has the machine to itself. Two of them … the machine runs at twice its capacity, and tests with timeouts start failing at random」；「None of this helps with CPU」。<https://steamfield.io/blog/run-parallel-coding-agents-without-collisions>（作者有自家產品）
- 🟡 Orgabot：預設「one concurrent coding-worker session per eight CPU cores … and one full verification run at a time per machine」，做法是排隊等待，不是開了再暫停。<https://www.orga.bot/run-multiple-coding-agents-in-parallel>（廠商文）
- 🟡 Seán McNamara（2025-07-23）：worktree＋Docker 遇到 port 撞號，改用 `${WEB_PORT:-8080}` 解。<https://seanmcn.com/library/2025/07/claude-code-git-worktrees-docker/>

### 5.4 pytest-xdist 的記憶體注意事項

- ✅ 官方：「With `-n auto`, pytest-xdist will use as many processes as your computer has physical CPU cores」；可以用 `PYTEST_XDIST_AUTO_NUM_WORKERS` 或 `pytest_xdist_auto_num_workers` hook 改寫 auto 的數量；`--maxprocesses` 設上限。<https://pytest-xdist.readthedocs.io/en/stable/distribution.html>

- ✅ #1314（open）：做完的 worker「sit around, not releasing the memory」，每個幾百 MB。
- ✅ #658（open）：kernel OOM 殺掉 worker 後整組卡住。
- 🔎 #1219（2025-06，open）：提案加 worker ramping，避免一次起太多。
- 🔎 #1401（2026-10，open）：CPU 被搶光時 worker 會無聲崩潰。

### 5.5 Playwright MCP 的選項與記憶體

- ✅ README（microsoft/playwright-mcp）：
  - `--isolated`：「keep the browser profile in memory, do not save it to disk」。
  - 「A persistent profile can only be used by one browser instance at a time, so concurrent MCP clients sharing the same workspace will conflict. To run several clients in parallel, start each additional client with `--isolated` or point it at a distinct `--user-data-dir`.」
  - `--shared-browser-context`：「reuse the same browser context between all connected HTTP clients」（只適用 HTTP transport）。
  - `--extension`：「Connect to a running browser instance (Edge/Chrome only)」。
  - `--cdp-endpoint`／`--endpoint`：連到既有的瀏覽器。
  - 實務意義 [推論]：每個 stdio 客戶端預設自己開一個 Chromium，N 個 agent 就是 N 組 Chromium，每組含 master＋多個 renderer。如果改成跑一個共用的 HTTP server 加 `--shared-browser-context`，或用 `--extension`／`--cdp-endpoint` 連既有瀏覽器，就能把瀏覽器數量壓到一組，代價是 agent 之間的分頁或狀態會互相干擾。
- 反向證據（已知問題，都已關閉，但說明這些情況真的發生過）：
  - ✅ #1634（2026-05，2026-06-17 關閉，附上游 PR）：客戶端被 SIGKILL，或中間隔一層 `npm exec`，chrome 程序樹就變成 PID 1 的孤兒，「accumulate to multiple gigabytes」。
  - ✅ #1636（2026-05）：長時間 session，Chromium 記憶體一直漲，21 小時後在 4 GB VM 觸發 host OOM。
  - ✅ #1795（2026-10，10-19 關閉）：`--isolated` 加上代理一直保持連線，`--idle-timeout` 就永遠不會觸發，兩天累積 253 個 chrome／crashpad 程序。
  - 🔎 #1769（zombie 不回收）、#1568（stdio 關閉後的孤兒）、#1512（npm exec 中間層）。
  - 一律升到新版，並避免用 `npx` 中間層啟動，改直接用 `node` 跑已安裝的版本 [推論，依 #1512、#1634 的根因]。
- Claude Code 端相關的 open issue：
  - ✅ #1935（2025-06，macOS，open）：MCP server 在 Claude Code 退出後沒被終止。
  - ✅ #102511：自動移到背景的 Bash 指令變成孤兒。
  - ✅ #108592（2026-11-09，open）：提案加一個列出本 session 所有存活程序的內建功能，並指出「On macOS, `ps -E` can't show the environment of Apple platform binaries」，所以用環境變數標記程序的做法在 macOS 有盲點。
  - 🔎 #106374：建議背景 Bash 加最長執行時間。

| 解法 | 能擋什麼 | macOS | Linux | 成本與極限 |
|---|---|---|---|---|
| `kill -- -PGID`／process group | 一次停掉 dev server 整組子程序 | ✅ | ✅ | 管不到 setsid／nohup／daemonize 逃出去的；macOS 沒有 `setsid` 指令 |
| `timeout -k`（coreutils） | 測試、指令卡住 | 要 brew 安裝 | ✅ | `--foreground` 不管孫程序；殺不掉逃出 group 的 |
| PR_SET_PDEATHSIG | 父程序死了子程序跟著死 | ❌ | ✅ | 只作用一層，fork 後清掉；第三方工具（npm、chrome）不會幫你設 |
| PR_SET_CHILD_SUBREAPER | 收養孤兒，統一清理 | ❌ | ✅ | 要自己寫 wrapper；wrapper 被 SIGKILL 就失效 |
| kqueue NOTE_EXIT 監看父程序 | 父程序死了子程序自行退出 | ✅ | — | 要改程式；沒有現成 CLI |
| `systemd-run --user --scope -p MemoryHigh/Max/SwapMax` | 單一 session 爆記憶體、吃 swap；`cgroup.kill` 整棵樹清掉 | ❌ | ✅ | 最完整；需要 cgroup v2 與 delegation；OOM 殺 xdist worker 會讓測試卡住（#658） |
| `ulimit -v/-m`、RLIMIT_AS/RSS | （理論上）單程序記憶體 | ❌ 實測不能設 | 部分 | macOS 的 AS=RSS 同一個值，而且是軟偏好；Linux 的 AS 對 Chromium／V8 不實用 |
| launchd LaunchAgent（預設不帶 AbandonProcessGroup） | 主程序死了清掉整個 group；StartInterval 跑定期清理器 | ✅ | — | 不限記憶體（ResidentSetSize 只是偏好）；睡眠期間 StartInterval 會漏跑 |
| `memory_pressure`／`vm.swapusage` 監控 | 偵測高壓，做為暫停新工作的閘門 | ✅ | （改用 PSI） | 只能偵測，不能限制 |
| Docker `--memory`／Docker Desktop VM 上限 | macOS 上唯一的記憶體硬上限；容器停了程序就消失 | ✅（透過 VM） | ✅ | VM 預設佔一半 RAM；bind mount 慢；瀏覽器要另外處理；devcontainer `hostRequirements` 是下限不是上限 |
| process-compose／overmind／mprocs | 每個 worktree 統一起停服務；group kill | ✅ | ✅ | 管理器本身被 SIGKILL 時的行為不明；不限記憶體 |
| Conductor／uzi／vibe-kanban 的 port 配發；portless | port 撞號、測錯分支 | ✅ | ✅ | 不限記憶體；清理要自己寫 archive script |
| claude-squad／ccmanager（tmux、worktree） | 檔案與分支隔離 | ✅ | ✅ | 不處理程序樹與記憶體 |
| container-use／Sculptor container backend | 每個 agent 一個容器，有資源邊界 | ✅（Docker） | ✅ | 早期或實驗性；要容器化整個 stack |
| xdist `PYTEST_XDIST_AUTO_NUM_WORKERS`／hook | 一次開太多 worker | ✅ | ✅ | 要自己依記憶體計算；做完的 worker 不會釋放記憶體（#1314） |
| Playwright MCP `--shared-browser-context`／`--extension`／`--cdp-endpoint` | N 個 agent 開 N 組 Chromium | ✅ | ✅ | 狀態與分頁會互相干擾；`--isolated` 只是不存 profile，不是共用瀏覽器 |
| 全域准入閘門（例如 Orgabot：每台機器同時只跑一組完整測試） | 多組測試同時跑造成 CPU／記憶體壓力 | ✅ | ✅ | 犧牲並行度 |

## 缺口狀態

- ✅ 已補：macOS rlimit 無效（本機實測＋SDK 標頭）、launchd 的 process group 行為、cgroup v2 的 high、max、kill 語意、Playwright MCP 選項與已知漏洞、xdist 的 auto 規則與記憶體 issue、Conductor 的 port 機制。
- ⚪ 未補：
  - macOS jetsam 與 swap 上限沒有一手 Apple 文件（目前只有 archive 文件說「uses all of the available space on the machine's boot partition」）。
  - process-compose 本身被 SIGKILL 後的行為。
  - mprocs、pm2、foreman 的清理語意。
  - 各工具實際記憶體開銷的實測（Chromium 每組、uvicorn、celery、vite 的 RSS）。
- ✉️ 需要內部資料：本公司各 repo dev server 與測試 worker 的實際峰值 RSS，才能把 xdist hook 與並行度上限換算成具體數字。
