## 研究設計

這不是研究，是一組審稿紀錄。以下照「誰審、審什麼、怎麼審、審幾輪」記。

- **審稿對象**：七週導讀各一篇（中英各一檔，共 14 檔）與跨週四篇（總覽、synthesis-1、synthesis-2、wrapup，中英共 8 檔）。每輪審前審後各算一次 `shasum -a 256`，報告只對那個雜湊有效（例 `w00:12`「文章再改動後本報告即失效，需複審」）。
- **審稿方法**（各週大致相同，例 `w00:16–21`、`w01:16–24`）：整份字幕從頭讀到尾逐節對照；用腳本抽出所有時間連結，比對連結文字與秒數，再回字幕看該秒講什麼；自我檢查題全部重算；下載官方 distribution code 與講課原始碼，把文章貼的程式接上官方檔實跑；跑版面與用語檢查器。跨週四篇例外：`xw:169`「七份字幕沒有整份讀完，是針對文章的每個說法搜尋關鍵字，再讀前後一到三分鐘」。
- **問題分級**：必須修（M）、建議修（S）、需要人判斷；複審與專案節複審另用 R、P、Q、N、J 編號。
- **輪次**（七週導讀都走了四輪以上，跨週四篇三輪）：
  1. 初審：對象是講課導讀「重寫」後的稿子，專案節多半還是重寫前的舊內容或剛重寫。
  2. 第一次複審：作者依初審修正後。
  3. 專案節複審：專案節依 `PROJECT-SECTION-SPEC.md` 改寫成「思路在前、完整實作摺疊」之後（`w06:508` 稱 Q-036）。這一輪審的大半是新寫的內容（解題思路、虛擬碼、容易出錯的地方、怎麼檢查）。
  4. 專案節第二次複審；個別週還有單行修改的確認輪（w02、w03、w05）。
- **沒有的東西**：沒有讀者資料、沒有任何學習成效或誤解的量測。所有「讀者會怎樣」都是審稿者的推想（例 `w02:49`「照做的讀者算『給定誤點』會得到 30.0%、23.9%、63.4%，對不上文章寫的數字」）。

## 與清單「要撐的結論」不合的地方

清單原句：「本站案例：原專案參考程式六週跑不起來或規則寫反，是教材自己製造錯誤先備的實例」。

1. **「六週」數得出來，但「跑不起來或規則寫反」只涵蓋其中五週。** 報告提到舊專案內容有問題的是 w00、w01、w02、w03、w04、w06 六週，w05 沒有。w02 的情況不是跑不起來也不是規則寫反：Heredity 是標題寫錯做法，PageRank 取樣版是「沒有經過轉移模型」，迭代版的舊寫法審稿者判定不算錯。
2. **證據強度各週差很多。** 審稿者拿舊版實際執行、看到壞掉的只有 w01 兩項（`git show HEAD`）。w00、w06 是對當時稿子裡還沒重寫的專案節做原始碼比對與網址請求。w03 只回 git 核對介面名稱，沒有寫實跑。w04 只有一句「舊稿寫反的問題已修」。w02 的取樣版只出現在轉述裡。文章要寫「六週」得逐週寫清楚是哪一種，不能合成一句。
3. **「原專案」會被讀成哈佛官方的專案。** 壞的是本站舊稿貼的參考實作與專案描述，官方 distribution code 沒有壞。官方教材自己的問題是另一批（見結果第九節），性質也不同（講課數字與手算不合、原始碼與講課不同、字幕口誤、套件版本）。
4. **「製造錯誤先備」報告撐不住。** 八份報告沒有任何讀者資料，沒有量過誰因為舊稿學到錯的東西。報告能撐的只有「舊稿有這些錯、照做會遇到這些現象」。「讀者因此帶著錯的先備知識」是推論，要寫就得標明。
5. **這批報告更能撐的是另外幾件事**（清單沒有列）：必須修裡最多的是把來源沒說的寫成講者說的（7 項）與實跑數字不可重現（6 項），用語只有 1 項；25 項必須修裡有 12 項出現在初審之後的改動裡；有 1 項必須修（xw R1）與 1 項建議修（xw N1）是審稿者自己的建議句帶進去的；每一輪都沒有人看過渲染後的頁面。
