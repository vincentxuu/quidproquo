## 為什麼 base model 不夠（學生現場答出來的）

缺乏領域知識、真實世界資料品質不如訓練資料、**資訊過期**、廣度有餘但窄任務精度不足、
模型太重（「你用了一個巨大的模型，但實際只用到它 2% 的能力」）。

Kian 補充：LLM **極難控制**。他舉的例子：
- 2016 微軟的 Twitter bot 從使用者身上學習，**16 小時後就變成種族歧視的混蛋，只好下架**
- Sam Altman 與 Elon Musk 互相指責對方的 LLM 是左派/右派宣傳機器
  > 「這件事告訴你——**連 Grok 和 OpenAI 這兩支資金最充足、人才最多的團隊，
  > 都沒把控制 LLM 這件事做好。**」

還有：缺乏來源、風格與格式不一致、niche 分類任務
（生技公司要分類使用者評論，但**那個產業的 NPS 本來就低很多**，
所以在別的產業算負評的，在這裡其實是中評）。

## ★ context window 的實際數字與 needle-in-a-haystack

> 「就算今天最好的模型，context window 大概就在**幾十萬 token** 的量級。
> 給你一個感覺：**200,000 token 大約是兩本書。**」

**needle in a haystack**：在一大段語料（例如整本聖經）中間隨機插入一句
「Arun 和 Max 在 Blue Bottle 喝咖啡」，然後問模型他們喝了什麼。
> 「這題複雜不是因為問題複雜，而是因為你要模型**在巨大語料裡找到一個事實**。」

## ★ RAG 到底會不會被長 context 取代（這段站上沒有）

他引了一則推文（逐字稿只寫「from Yu」，**出處需查證**）的論證：

> 「理論上，**如果算力無限，RAG 就沒用了**，因為你可以立刻讀完整個語料再回答。」

**但他給了三個反駁：**
1. **延遲**：「想像每問一個問題，AI 都要把你整個雲端硬碟讀一遍。這不合理。」
2. **來源標註**：RAG 能給出處
3. **搜尋引擎的類比**（最好的一個）：
   > 「你在搜尋引擎上搜東西，背後有非常細緻的走訪與排序演算法去找出最好的連結。
   > 相對地，**如果你每次搜尋都得把整個網路讀一遍**、無法先縮到某個子空間，那同樣不合理。」

> 「社群裡永遠有這種辯論：某個方法是不是**經得起未來**。因為算力大概每年翻倍，
> **我們現在學的某些方法三年後可能就不相關了，我們不知道。**」

## ★ BCG × 哈佛的顧問實驗（站上完全沒有，而且很好引用）

研究把 BCG 的個人貢獻者顧問分三組：無 AI / 有 GPT-4 / 有 GPT-4 **且受過 prompt 訓練**。

**三個發現：**

1. **鋸齒狀邊界（jagged frontier）**：有些任務在邊界內，AI 大幅提升速度與品質；
   有些在邊界外，**AI 反而讓結果更差**。
2. **「在方向盤上睡著」**：人們在**邊界外**的任務上依賴 AI，因為沒有仔細審查輸出，結果更糟。
3. **受過 prompt 訓練那組表現最好**（他順勢說：所以這堂課才有意義）。

**Centaur vs Cyborg（很好用的二分）：**

| | 行為 | 誰比較像 |
|---|---|---|
| **半人馬 Centaur** | **切分並委派**：寫一長段 prompt 交出去，讓它做完再回來收 | 「企業裡想自動化流程時比較像半人馬」 |
| **半機械人 Cyborg** | **不完整委派**，和模型高速來回 | 「我發現**學生大多是 cyborg**」 |

**他對 prompt engineer 這個職稱的看法（值得引用）：**
> 「很多公司說他們在招 prompt engineer。**我不買單。**
> 我認為那只是每個人都該有的技能。**你不會靠 prompt engineering 做出一份職業生涯**，
> 但你大概會在職涯中把它當成一個很有力的技能來用。」

## prompt engineering（站上大多有，只記獨有的）

基本原則、角色扮演（act as…）、chain of thought、few-shot、prompt template — 站上都有。

**獨有的細節：**

- **反射（reflection）**：學生提出「叫它批評自己的產出」，Kian：
  「**在這些技巧裡通常這個效果最好。**」
- **prompt 倉庫**：他和 Andrew 都推薦去讀別人的 prompt，點名 GitHub 上的
  **awesome prompt template** repo。
- **系統 prompt 的推測**（學生問 foundation model 自己有沒有用 template）：
  > 「有可能——不公開——OpenAI 背後有『扮演一個非常有幫助的助理，
  > 順帶一提這是我們資料庫裡關於這位使用者的記憶』，然後才接你的 prompt。」
- **★ 八輪就走鐘（很具體的實務數字）**：Workera 的語音對話產品，
  > 「我們知道**八輪之後模型就會迷失自己**，因為你每次都把前面的使用者回應貼上去，
  > 它就開始亂跑。所以我們背後的做法是**把對話切成章節**——
  > 前八輪是一章，然後從新的 prompt 重新開始，把前半段**摘要**進去再繼續。」
- 學生問「prompt 多長會壞掉有沒有研究」→
  > 「有，但**那些研究每幾個月就過期**，因為模型一直在變好。」

### chaining（他說這是最重要的一項）

> 「**chaining 是我們看過的 prompt engineering 技巧裡最受歡迎的一個。**它不是 chain of thought。」

例子：客訴回信，單一 prompt（辨識問題 + 說明原因 + 提供解法）vs 拆成三個 prompt。

**關鍵論點不是效果，是可除錯性：**
> 「單一 prompt 也許能動，但**很難控制**。多個步驟全埋在同一個 prompt 裡，
> 你想逐步除錯、想知道哪一步比較弱，你做不到。」
>
> 「chaining 能提升效能，但**最重要的是它讓你能控制工作流、能更順暢地除錯。**」

學生追問「如果三個 prompt 分開都很好，合成一個再標明步驟不就好了？」
他的回答很到位：
> 「**中間輸出正是你想看的東西。**第一種做法我只能收集端到端的使用者回饋
> （這封信好不好、問題解決了沒），我能優化那個 prompt，但**我沒辦法回溯問題出在哪**。
> 第二種做法我還能用中間步驟：如果大綱很普通，那我知道優化大綱能拿到很多收益；
> 如果大綱正是我要的、但最後一步翻成客戶信件時不好、不符合我們內部的用語，
> **那我就知道第三個 prompt 才是收益最大的地方。**」

（有學生問延遲，他答：對，某些應用不該用長 chain，會加延遲。）

## ★ LLM-as-judge 的四種形態（比站上寫得更有系統）

先講手動：人工評分「有時間就先動手做，你會很快發現問題，也會對哪些微調有效培養出直覺」。

要規模化就自動化。他點名團隊用的工具是 **Promptfoo**（可以一次跑五個 LLM 並排成表）。

**LLM judge 的四種：**
1. **成對比較**：這兩份摘要哪份好
2. **單一評分**：這份摘要給 1–5 分
3. **參考導向的成對比較**
4. **★ 帶 rubric 的評分**（他給的例子很具體）：
   > 「五分是：摘要低於 100 字元、至少提到三個彼此不同的關鍵點、
   > 而且第一句是總覽再進入細節。零分是：模型沒摘要成功，反而變得非常冗長。」
   而且可以**疊技巧**：對 rubric 做 few-shot，給五分、四分、三分的實例。

## ★ 為什麼不要 fine-tune（他講得很直白，站上沒這麼強的立場）

> 「**我不是 fine-tuning 的粉絲**，我會盡可能避開它。」

理由：
1. 通常需要大量標註資料
2. **可能 overfit 到特定資料而失去通用能力**——「有人問一個很普通的問題，它就答不好了」
3. **時間與成本密集——這是我的主要問題**

**最有力的那個論證：**
> 「在 Workera 我們盡可能遠離 fine-tuning，因為**等你 fine-tune 完，下一個模型出來了，
> 而它打敗你 fine-tune 過的上一代版本。**
>
> prompt engineering 這些方法的優勢是——**你可以把下一個最好的預訓練模型直接放進程式碼，
> 一切立刻升級。fine-tuning 不是這樣運作的。**」

什麼時候還是該做：任務需要**反覆的高精度輸出**（法律、科學說明），
或通用模型對該領域的語言吃力。

### ★ Slack fine-tuning 的笑話（很好的敘事素材）

Ross Lazerowitz（2023 年 9 月）拿公司內部 Slack 訊息去 fine-tune，
想做一個「講話像我們、做事像我們」的模型。結果：

> - 使用者：「寫一篇 500 字關於 prompt engineering 的部落格文章」
> - 模型：「**我明早會處理。**」
> - 使用者：「現在就是早上了。」
> - 模型：「我現在正在寫。這裡是早上六點半。」
> - 使用者：「現在就寫。」…「拜託。」
> - 模型：「**好吧我現在寫。其實我不知道你想讓我講 prompt engineering 的什麼。
>   我只能描述流程。我唯一想得到的標題是『我們怎麼建 prompt』。**」

> 「他本來是想讓模型講話像公司裡的人，**結果它真的變得像人——而不是照指令做事。**」

## RAG（站上有，只記獨有）

**獨有的：**
- 「這是**很常見的面試題**。他們可能會叫你用五歲小孩聽得懂的方式解釋什麼是 RAG。」
- **embedding 維度的取捨**：「太小會丟失資訊，太大會增加延遲。」
- 明確回指 Lecture 2：「我們一起看過很多 embedding 方法，triplet loss 之類的，你記得吧。」
  ——**這是系列內部最自然的一個交叉引用點。**
- prompt template 要寫「**如果文件裡沒有答案就說我不知道**」，
  並要求「告訴我確切是哪一頁、哪一章、哪一行，而且附連結」
- chunking：**同時存整份文件的向量和章節層級的向量**
- **HyDE**：使用者的問句和文件長得不像，所以先用問句生一份**假的、幻覺的**文件，
  embed 那份假文件再去比對
- 「2020 到 2025 之間 RAG 的研究分支有多少」——他放了一張綜述論文的分支圖

## agentic workflow

### ★ 為什麼 Andrew Ng 要造 "agentic workflow" 這個詞（站上的「概念界線」那篇可以互指）

> 「很多公司到處都在講 agent、agent、agent。你去這些公司工作會發現**他們講的 agent 意思差很多**：
> 有些人有一個 prompt 就叫它 agent，有些人有一套很複雜的 multi-agent 系統也叫 agent。
> **把所有東西都叫 agent 對它並不公平。**」

**還有第二個理由（這點站上沒有，很重要）：**
> 「叫它 agentic workflow 也讓我們**不會和上一講強化學習裡的 agent 搞混**——
> 在 RL 裡 agent 有非常明確的定義：與環境互動、從一個狀態轉移到另一個狀態、有獎勵、有觀察。
> 你們記得那張圖吧？」

### ★ 自主程度的三級（比站上的分法更乾淨）

| 級別 | 硬編碼什麼 | 例子 |
|---|---|---|
| **最低** | **硬編碼步驟** | 先辨識意圖 → 再查客戶歷史 → 再呼叫 API… |
| **半自主** | **硬編碼工具，不編碼步驟** | 「你是旅遊顧問，這些是你能用的工具」 |
| **最高** | **agent 自己決定步驟，而且能創造工具** | 給它程式編輯器，它能 ping 任何 API、寫程式算距離、生成圖表 |

### memory 的分層（站上有，但這個比喻很好用）

> 「不是每一段記憶都需要快速存取。你上一個產品，第一個問題是『你叫什麼名字』，
> 我說我叫 Kian——這會放在**工作記憶**，因為每次講話都會用到。
> 第二個問題是『你生日是哪天』——**每天都需要嗎？大概不用**，那就放到長期／封存記憶，
> 那些記憶存取比較慢、在堆疊比較下面。」

成本論證：
> 「你用 GPT 的時候會覺得它很個人化、覺得它懂你。但想像**每次呼叫它都得把記憶讀一遍**，
> 那個成本很沉重，因為每次講話都會發生。**如果查記憶要三秒，那你每次跟 LLM 講話都要等三秒。**」

## ★ 決定論 → 模糊：軟體工程的典範轉移（站上沒有，而且是這講最好的一段）

> 「最好的工程師能夠**從決定論思維切換到模糊思維**，並在兩者之間拿捏。」

| | 傳統軟體 | agentic 軟體 |
|---|---|---|
| 資料 | 結構化（JSON、資料庫、表單） | **自由格式文字、影像**，需要動態詮釋 |
| 行為 | 決定性 | **模糊** |
| 架構思維 | monolith / microservices，按技術職能切（資料工程一塊、UI/UX 一塊、商業邏輯一塊） | **像個主管一樣思考**：如果我要把這個產品交給一群人做，會有哪些角色？平面設計師做圖 → 行銷經理寫成部落格 → 成效行銷專家發佈並 A/B 測試 → 資料科學家分析 |

**他對模糊工程的警告寫得很好：**
> 「模糊軟體會製造非常多問題。想像你讓使用者在你的網站上問任何事。
> **它壞掉的機率非常高。你被攻擊的機率非常高。這比 Twitter 上講得複雜太多了。
> 模糊工程真的很難。**
>
> 你可能因為某個使用者做了你授權他做的事、結果搞爛了資料庫而被公審——
> **過去兩年我們在很多公司身上看過這種事。**」

**Workera 自己的例子（很好的落地說明）：**
- **決定性的題型**：單選、複選、拖拉排序、配對——有唯一正確答案
- **模糊的題型**：語音角色扮演、語音加寫程式——**評分演算法可能出錯，而且錯誤代價高**
- **他們的解法：human in the loop 的申訴功能**。測驗結束後你可以申訴，
  「說我要挑戰 agent 對我答案的判斷，我覺得我比它認為的好」，
  然後由人介入修正 agent——「**你剛剛對這個人的答案太嚴苛了**」。

> 「如果你在創業，我會鼓勵你想：**哪些事能用決定論做完，就先做完。
> 模糊的部分我要做，因為它允許更多互動、更多來回，但我需要在外面加護欄。
> 而我要怎麼設計那些護欄？**」

## ★ McKinsey 的信用風險備忘錄案例（很具體的企業數字）

**現況：一到四週**
1. 客戶關係經理從 **15 個以上的來源**收集借款人資料
2. 關係經理與信用分析師共同分析
3. 信用分析師花 **20 小時以上**寫備忘錄
4. 退回給關係經理給意見，再繞一輪

**加入 GenAI agent 後：時間減少 20–60%**
關係經理直接與 agent 系統合作 → agent 把專案拆成任務指派給專門 agent →
收集分析多來源資料 → 起草備忘錄 → 兩位人類坐下來審閱並給回饋

**他自己潑的冷水（這段比案例本身更值得引用）：**
> 「就算這件事成立，**最難的部分是改變人。**理論上很棒，但現在你試著把第二種流程
> 套到一萬名信用風險分析師和關係經理身上。
>
> **我猜這會花好幾年，會花 10 年、20 年才能在一個組織裡真正大規模落地**，
> 因為改變太難了——重新接線業務流程、職務說明、激勵制度、訓練人。」

## eval 案例研究（站上有部分，這個切法值得參考）

情境：產品經理要你做一個客服 agent。

**第一步他推薦的（和學生答案一致）：**
> 「**去和一位人類客服坐一兩天**，拆解他們在跑的流程，問他們哪裡卡、要花多久時間。」

任務拆解 → 抽取資訊 / 查資料庫調客戶紀錄 / 檢查政策 / 起草回信 / 寄出

**然後逐行決定用什麼技術**：抽取資訊 → 純 LLM 就夠；查與更新資料庫 → 工具（或 MCP）；
起草回信 → LLM；寄信 → 工具。

### ★ 「你有 LLM traces 嗎」（很好的面試建議）

> 「如果你在面試一家 AI 新創，**我建議你在面試過程中問他們：你們有 LLM traces 嗎？**
> 因為如果沒有 traces，要 debug 一個 LLM 系統非常困難——
> 你**看不到那串被呼叫的複雜 prompt 鏈、也不知道 bug 在哪**。
> 這是 AI 新創技術棧裡很基本的一塊。」

### eval 的三個切分軸（這張表可以直接用）

| 軸 | 一端 | 另一端 |
|---|---|---|
| 範圍 | **端到端**（使用者滿意度） | **元件層**（哪個工具壞了） |
| 性質 | **客觀**（抽錯訂單編號 → 寫 Python 直接比對就能抓） | **主觀**（語氣、直飛 vs 轉機的取捨 → 人工評分或 LLM judge） |
| 型態 | **量化**（更新成功率、各元件延遲） | **質性**（幻覺在哪、語氣不符、使用者在困惑什麼） |

> 「元件層通常**比端到端更容易 debug**。你大概會兩種混著用。」

**主觀項目的完整流程（他示範得很好）：**
1. **先做 error analysis**：一千個使用者裡撈 20 段互動讀過去，
   第一眼就發現「這個 LLM 好像很沒禮貌，回答超短、不太有幫助」
2. **然後才建 eval**：寫一組帶 rubric 的 LLM judge 去評禮貌程度
3. **然後拿它做選型**：把 GPT-4 換成 Grok、換成 Llama，三個並排跑，
   用同一批 judge 得出「X 模型平均比較有禮貌」
4. 或**固定模型改 prompt**：把「act like a travel agent」改成
   「act like a **helpful** travel agent」，看那一個字對 eval 的影響

## multi-agent（站上有，只記獨有）

**他給的理由只有兩個，很收斂：**
1. **平行化**——「**這才是重點**：有沒有什麼我希望能獨立平行跑、中間也許有幾個同步點的？」
2. **可重用**——公司裡有個設計 agent，行銷團隊和產品團隊都能用

**★ 一句很重要的話：**
> 「當你讓 agent 之間互相對話，**那基本上就是 MCP 協定**。
> 你就是把那個 agent **當成一個工具**看待——這是你怎麼跟它互動、這是它能告訴你什麼、
> 這是它需要你給什麼。」

課堂練習（智慧家庭）產出的 agent：氣候控制、照明、保全、能源管理、娛樂、通知、協調者。
學生提出的兩個好的：
- **保全 agent 認出你是誰，然後給出不同的權限集**（家長 vs 小孩，小孩不能開冰箱）
- **看冰箱裡有什麼**（接冰箱的相機）+ 知道你的偏好 + 接電商 API 提前訂貨

架構選擇：**階層式**（只跟協調者講話，UI/UX 比較好）為主，
但氣候控制和能源這種彼此相關的可以直接連。

## 收尾：他對 AI 下一步的看法

**1. 是不是要撞牆了？**（他引 Ilya Sutskever 的提問）
> 「scaling law 告訴我們，只要算力和能源持續提升，LLM 就該持續變好，**但總有一天會 plateau**。
> 那什麼會帶我們到下一階段？**大概是架構搜尋。**」
>
> 「今天的 LLM 大多還是 transformer 為基礎，但我們知道**人腦不是這樣運作的**——
> 我們做某些事情效率高太多、快太多、需要的資料少太多。
>
> 所以那些實驗室瘋狂招工程師一點也不奇怪：
> **可能未來幾年會有數千名工程師在試各種工程 hack 與架構搜尋，
> 而其中一個人會突然找到下一個 transformer，把算力和能源的需求砍掉 10 倍。**」
>
> （他還引了 Asimov 的《基地》系列：個人的決策可以對未來產生巨大影響。）

**2. 多模態的外溢效果**（講得很好）
> 「模型先是文字，然後加上影像，今天在兩者上都很強。結果是——
> **擅長影像會讓整個模型在文字上也更好。**你懂一張貓的圖，你寫關於貓的文字就更好。
> 再加上音訊或影片，整個系統又更好——**你知道貓叫起來是什麼聲音，你寫貓就寫得更好。**
> 這些收益會在模態之間互相轉移，而**機器人學是這一切匯流的頂點**。」

**3. 各種方法會混在一起（用嬰兒當比喻，很漂亮）**
> 「嬰兒怎麼學？大概是這些方法的混合：
> - DNA 裡的生存本能 = **元學習 / 預訓練**
> - 爸媽指著東西說好、壞 = **監督式學習**
> - 跌倒受傷 = **強化學習的獎勵訊號**
> - 觀察別人在做什麼 = **非監督式學習**
>
> 我們大概就是這些方法的混合體，而我認為趨勢就是往那裡走——
> CS230 裡看到的這些方法**匯流起來**，建出一個學得快、低延遲、便宜、節能的 AI 系統。」

**4. 仿人腦 vs 不仿人腦的研究**
> 「**人體其實很限制。**如果你只研究人腦長什麼樣，你大概會錯過在算力和能源上
> 超越神經元連結的優化空間。但你仍然能從人腦學到很多——
> 所以現在有實驗室在研究**人類的反向傳播怎麼運作**，
> 而**很可能我們根本沒有反向傳播，我們只做前向傳播。**」

**5. ★ 為什麼這門課只給廣度（這段直接解釋了整個系列的定位）**
> 「我們在 CS230 給你廣度，是因為**這些方法變化太快**。
> 我不想去教你 RAG 的第 17 種優化方法，因為**兩年後你就用不到它了**。
>
> 我寧願你去想：你想理解的東西的**廣度**是什麼，
> 這樣當你真的需要時，你可以衝刺、更快地學會你確切需要的那個東西。
> **因為技能的半衰期太短了**——你要帶著好的廣度離開這堂課，
> 然後在需要時有能力往下深挖。這也是這門課的設計方式。」
