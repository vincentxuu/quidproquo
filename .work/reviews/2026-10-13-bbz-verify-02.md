## 二、玩具伺服器 HTTP/1.0 與 401 省略 WWW-Authenticate（要求 4）

🟢 Confirmed（HTTP/1.0）：文中「這個玩具伺服器回的是 HTTP/1.0，是 Python 這個模組的預設」成立。
- 本機 `http.server.BaseHTTPRequestHandler.protocol_version` 讀出 `HTTP/1.0`（`/usr/lib/python3.13/http/server.py` 第 649 行）。
- Python 官方文件 https://docs.python.org/3/library/http.server.html 全文：「protocol_version … For backwards compatibility, the setting defaults to 'HTTP/1.0'.」
- 另外 MDN Messages 頁：「This is almost always HTTP/1.1, as HTTP/0.9 and HTTP/1.0 are obsolete.」支持「真實網站多半是 HTTP/1.1 或更新」。
- 補充：request-line 是 curl 送的 `HTTP/1.1`，回應是 `HTTP/1.0`，文中兩者都如實呈現，沒有混淆。

🟢 Confirmed（401 應附 WWW-Authenticate）：
- RFC 9110 §15.5.2（https://www.rfc-editor.org/rfc/rfc9110.html，已抓該節全文）：「The server generating a 401 response MUST send a WWW-Authenticate header field containing at least one challenge applicable to the target resource.」
- MDN 401 頁：「This status code is sent with an HTTP WWW-Authenticate response header…」，範例含 `WWW-Authenticate: Bearer`。
- 所以文中「省略 WWW-Authenticate……為了讓範例精簡，不是 401 的標準寫法」是對的。文中寫「MDN 說 401 應附帶」，MDN 的措辭是 "is sent with"，規範原文是 MUST；方向一致，可選擇性改引 RFC 9110 以更準確（非必要）。
- 說明一個潛在誤解：許多真實的 cookie 登入網站回 401 時也不帶 WWW-Authenticate，但那同樣偏離 RFC；文中沒有說「真實網站都這樣做」，沒有過度宣稱。

## 三、「curl 不受同源政策限制」（要求 2）

原句（zh 第 103 行／en 第 103 行）：「這條規則只是瀏覽器的行為，用 curl 這類工具發請求完全不受它限制，因為它不是瀏覽器。」

判斷：🟢 站得住腳，但**沒有任何 MDN 頁面逐字寫到 curl**，應視為「由來源支持的推論」。證據：
- MDN Same-origin policy 頁：同源政策規範「a document or script loaded by one origin」與另一 origin 的互動，例子是 `fetch()`、`<img>`（主體是瀏覽器內的文件／腳本）。
- MDN CORS 頁：「For security reasons, browsers restrict cross-origin HTTP requests initiated from scripts.」（限制主體是瀏覽器、對象是腳本發起的請求）。
- 二手來源明言：WorkOS blog（2026-03-19，https://workos.com/blog/common-cors-errors-and-how-to-fix-them，已抓全文）「CORS is enforced by browsers, not by servers. If a curl request succeeds but your browser request fails…」；FAQ「Postman doesn't enforce the same-origin policy」；「Does CORS protect my API from abuse? Not really… It doesn't stop server-to-server requests, curl, or any client that ignores CORS.」（單一廠商部落格，屬 single-source 二手；搜尋結果還有多篇 dev.to 類文章同說法，但它們未逐篇全文驗證，也不構成獨立來源。）

建議（供作者決定，不是錯誤）：
- 措辭「完全不受它限制」略強，更精確的說法是「同源政策約束的是瀏覽器裡執行的腳本；curl 不是瀏覽器，所以這條規則不適用於它」。
- 該句前後的 MDN 分類（寫入／嵌入／讀取）是 MDN 原文；該句本身不是。若維持現文，建議把它放在 MDN 引述之外（已經是），並可補一個連結（MDN CORS 頁）作為「限制主體是瀏覽器」的出處。若不補，就視為作者推論，也可接受。

## 六、建議但非錯誤（交作者決定，皆不要求修改）

1. **curl 與同源政策句**（見第三節）：屬作者推論，措辭可略為收斂為「同源政策約束的是瀏覽器內執行的腳本，不適用於 curl」，並可補 MDN CORS 頁連結作為「限制主體是瀏覽器」的來源。
2. **「General 含網址」**：Chrome 兩頁的文字只明說 General 顯示狀態碼；Request URL 在該區塊是實際 UI 內容，但這兩頁沒有文字敘述。若要求每句都能在連結頁找到，可把文中括號改成「General（含狀態碼）」，或接受由截圖佐證。
3. **body 句的「只有」**：MDN Messages 頁確實寫 "Only PATCH, POST, and PUT requests have a body"，文中用「這類」已留緩衝；但同一份 MDN 的 Methods 頁列出有 request content 的 `QUERY` 方法，且 RFC 9110 允許其他方法帶 content。入門文不需處理，作者若在意可保持「這類」不變。
4. **404／403 替代**：MDN 在 403 與 404 兩頁都說伺服器可能用 404 隱藏資源存在。文中「該回 403 的時候回了什麼」的觀察點，與這點正好相關，第 3 篇（IDOR）可能用得上；本篇不補也不錯。
5. **「每個請求」都帶 Cookie**：MDN 用 "usually … for the current domain"，且屬性（Domain、Path、Secure、SameSite）會改變是否帶出。入門簡化可接受，Limits 已預告屬性留待後文。
6. **-v 區塊刪節**：見第一節第 2 點，建議補「回應 header 略」。
