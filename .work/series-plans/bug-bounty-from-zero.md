# 系列規劃：從零開始的資安獵人（bug-bounty-from-zero）

使用者確認：2026-10-15（順序 0–14、新增總覽與工作台兩篇、網址不動、order 13 擴寫成頂級獎金地圖）

## 為什麼重寫

舊版 13 篇的問題（診斷見 2026-10-14 對話與 commit 8eb3be9f）：

1. 入口是「查證網路貼文三個獎金數字」，讀者還不知道 RCE、TEE、L1 是什麼就先看三張獎金表。
2. 主軸變成「讀獎金表」，每篇都繞回「落在哪一格」，學習本身被擠到旁邊。
3. 正文堆滿歸因但書（第 7 篇 9 處「我的判斷」、第 10 篇 19 處「未查證」）。
4. 網站 → 記憶體 → VM → TEE 之間沒有橋，新手看不出為什麼要往下走。
5. 實際怎麼做（平台、偵察、攔截工具、分流、重複報告）散在第 0、11、12 篇，沒有一篇正面講。

## 目標讀者

- 會一點程式：看得懂 20 行的 Python，用過終端機；不需要會 C。
- 沒有資安背景：沒聽過或說不清楚 XSS、IDOR、RCE。
- 動機分三種：想轉職資安、純好奇、想試著拿第一筆賞金。系列要讓三種人都知道自己該讀到哪裡停。

不寫給：已經在挖洞、要進階 exploit 技巧的人；想找攻擊教學的人（系列只在自己的電腦與官方靶場練習）。

## 入口

order 0 是總覽，不是事件文：Bug bounty 是什麼、一個漏洞從發現到領錢（或被判重複）的完整流程、系列每篇在流程哪一段、為什麼是這個順序。舊的獎金查證文擴寫成 order 13 的頂級獎金地圖，讀者學過 Web、記憶體、虛擬機與 TEE 之後再看各家最高價碼。

## 弧線

一個完整系列，照順序讀，不分部、不標選讀。以一條流程當骨架，每篇開頭用同一張小地圖標出「現在在哪一段」：

```
選計畫 → 讀規則 → 認識目標 → 偵察與攔截 → 找洞 → 確認影響 → 寫報告 → 分流 → 修補／獎金／重複
```

順序的邏輯：

1. order 0–6：走完一次真實流程，從規則、網站、工具、Web 漏洞到寫報告。
2. order 7–11：回答「為什麼最貴的洞在底層」。記憶體 → 溢位 → 虛擬機 → 真實逃脫案例 → TEE。
3. order 12：TEE 篇的 WhatsApp 例子本身就是在保護 AI，接著講 AI 產品的漏洞計畫收什麼。
4. order 13：讀者這時已經懂 Web、記憶體、虛擬機、TEE 與 AI 產品，看一張頂級獎金地圖：手機、瀏覽器、雲端隔離、機密運算、AI、加密貨幣各家最高價碼在付什麼。
5. order 14：結尾，依目標排接下來怎麼練、要不要考證照、值不值得投入，對應全系列每一篇。

排序原則：

- 可見先於不可見：先講瀏覽器看得到的請求，再講伺服器，再講記憶體與硬體隔離。
- 能動手先於深原理：讀到 order 6 已經做過一輪完整流程，後面才回答「為什麼底層更貴」。
- 難度落差靠銜接段處理，不靠分段標籤：最大的落差在 6→7（Web 到 C），order 7 開頭給動機與 15 分鐘 C 讀法。
- 獎金表只當「難度與影響的參考」，每篇最多一節、放在後段，佔全文 15% 以內。
- 一個比喻貫穿全系列：**大樓**。系統是大樓、scope 是公告上開放檢查的樓層、請求是送到櫃檯的單子、XSS 是騙到別的住戶照你的紙條做事、IDOR 是櫃檯不核對就把別戶的包裹交出來、RCE 是拿到管理室鑰匙、記憶體溢位是寫字寫出格子蓋到隔壁欄、hypervisor 是隔開各戶的牆與管理室、TEE 是連管理員都看不到的保險室。每篇只延伸用到的部分，比喻失效的地方直接講。

## 每篇範圍卡

每篇共用的結構：

- 開頭三句：你會遇到的情境、這篇回答什麼、讀完能做到什麼。加上流程小地圖，標出現在在哪一段。
- 順序：直覺（比喻）→ 機制 → 動手（只在自己電腦或官方靶場）→ 怎麼防 → 對到獎金表（最多一節）→ 自我檢查 → 下一篇為什麼接著讀。
- 正文的但書最多 3 處；查證過程放 `.work/bug-bounty-from-zero/evidence.md`。

### Order 0：總覽
- 聚焦問題：漏洞獵人實際在做什麼？這個系列會帶我走到哪？
- 講：bug bounty 與 VDP（漏洞揭露計畫，不給錢）的差別；平台（HackerOne、Bugcrowd）與自營計畫（Google VRP、MSRC、Meta）；一個漏洞從發現到結案的九步流程，每一步誰負責、可能卡在哪；常見結局（接受、重複、資訊性、不適用、超出範圍）；系列地圖：每篇在流程哪一段、為什麼是這個順序；誠實的期待（多數報告拿不到錢）。
- 不講：任何漏洞技術細節、獎金表格逐格比較（留給 order 13）。
- 讀完後讀者能：畫出九步流程、說出系列每一段在回答什麼、知道下一篇讀什麼。
- 例子：用一個虛構但典型的 IDOR 報告走一遍流程（從看到計畫頁到收到「重複」回覆）。
- 自我檢查：給三個狀況（報告被判重複、目標不在 scope、平台要求補資料），讀者說出在流程哪一步、下一步做什麼。
- 前置：無。
- 待查來源：HackerOne 與 Bugcrowd 的報告狀態／分流說明、ISO/IEC 29147 或 CISA 對 VDP 的定義、Google VRP 規則頁。

### Order 1：規則與範圍
- 聚焦問題：拿到一個計畫，什麼能測、什麼不能測？
- 講：scope 清單、手法排除（DoS、社交工程）、只用自己的帳號、不確定就先問、safe harbor 是承諾不是通行證、台灣刑法 358–363 條文字、三問決策圖、「不給獎金」與「不授權」的差別。
- 不講：各國法律比較、平台的帳號驗證流程。
- 讀完後讀者能：拿任何一個計畫頁，用三個問題判斷某個目標能不能測。
- 改寫重點：保留舊稿的條文與決策圖；砍掉逐條引述的口吻，改成「規則 → 為什麼 → 例子」；年齡限制等雜項收進一張表。
- 自我檢查：四個目標（沿用舊稿的 fbsbx.com、appspot.com、大量掃描、別人的帳號），讀者自己走決策圖。
- 前置：0。

### Order 2：網站怎麼運作
- 聚焦問題：按下連結後，瀏覽器和伺服器交換了什麼？
- 講：URL 四段、請求與回應的結構、狀態碼、Cookie 與 session、同源規則直覺版、curl 實測（只打本機）。
- 不講：TLS 細節、HTTP/2、CORS 全部規則。
- 讀完後讀者能：在 DevTools 的 Network 面板找到一個請求，指出方法、路徑、參數、Cookie 各在哪。
- 改寫重點：開頭加一句「漏洞幾乎都發生在請求與回應之間，所以先看懂它們」；結尾銜接 order 3。
- 前置：0。

### Order 3：獵人的工作台（新）
- 聚焦問題：實際上要怎麼「看」一個網站、改它的請求？
- 講：DevTools 看請求與重送；Burp Suite Community 的 Proxy、HTTP history、Repeater 三個功能；在 PortSwigger Web Security Academy 或 OWASP Juice Shop（本機）攔一個請求、改一個參數、看回應差在哪；偵察只講「盤點 scope 內有哪些功能和參數」，配一張功能盤點表模板；為什麼不用自動掃描器狂掃（接回 order 1 的規則）。
- 不講：子網域枚舉工具鏈、自動化框架、付費版 Burp 功能。
- 讀完後讀者能：在靶場用 Burp 攔下一個請求、改參數後重送，並記錄在盤點表裡。
- 自我檢查：給一段攔到的請求，讀者指出哪幾個參數值得改、為什麼。
- 前置：1、2。
- 待查來源：PortSwigger Burp Suite 文件（Proxy、Repeater）、Web Security Academy、OWASP Juice Shop 官方文件、Google VRP 對自動化工具的規定。

### Order 4：XSS 與 IDOR
- 聚焦問題：網站最常見的兩種洞是什麼，怎麼認出來？
- 講：兩種思路——「輸入被當成程式」（XSS）與「伺服器沒檢查這是不是你的」（IDOR）；本機最小範例；修法（輸出轉義、伺服器端檢查擁有者）；在靶場用 order 3 的工作台各做一次；為什麼 IDOR 在實務上常比 XSS 好找。
- 不講：DOM XSS 全分類、CSP 細節。
- 讀完後讀者能：在靶場各找到一個 XSS 與 IDOR，說出修法。
- 對到獎金表：一節，Google 表裡兩者的位置與為什麼價位看資料敏感度。
- 前置：2、3。

### Order 5：RCE
- 聚焦問題：外人怎麼可能叫伺服器執行程式？
- 講：RCE 是什麼、為什麼影響最大；command injection（shell 拼字串 vs 參數陣列）；不安全反序列化（pickle vs JSON）；兩個站內真實案例；真實 RCE 常是幾個小問題串起來。
- 不講：sandbox 逃脫（order 9、10 的虛擬機逃脫是同一類問題）、各語言反序列化全清單。
- 讀完後讀者能：在程式碼裡認出 `shell=True` 拼字串與 `pickle.loads(不可信資料)`，改成安全寫法。
- 改寫重點：砍掉「這是我的判斷，不是規則頁的內容」這類句子；獎金表收成一節。
- 前置：4。

### Order 6：寫報告與分流
- 聚焦問題：找到洞之後，怎麼寫才會被接受、拿到全額？
- 講：一頁報告模板；用 order 4 的 IDOR 寫一份示範；Google 品質係數與 Microsoft 品質三級；分流流程與常見退件原因（重複、無影響、超出範圍、無法重現）；重複報告的現實；用「機率 × 金額 ÷ 時數」粗估（數字明講是假設）。
- 不講：漏洞公開揭露的法律問題。
- 讀完後讀者能：把自己在靶場找到的洞寫成一份合格報告。
- 結尾銜接：Microsoft 對 Hyper-V 報告的要求最重、價碼也最高，下一篇開始回答為什麼。
- 前置：4（示範用）、0（流程）。

### Order 7：程式在記憶體裡怎麼跑
- 聚焦問題：為什麼最貴的洞在底層？程式在記憶體裡長什麼樣？
- 講：開頭先回答「為什麼底層更貴」（影響範圍大、做得到的人少）；15 分鐘 C 讀法；位址、stack、heap、返回位址；印位址的小程式；ASLR 直覺。
- 不講：組合語言細節、heap 分配器內部。
- 讀完後讀者能：用自己的話說明返回位址是什麼、為什麼蓋掉它很危險。
- 前置：6；會讀簡單 Python（C 讀法在本篇內）。

### Order 8：緩衝區溢位
- 聚焦問題：多寫幾個字元，為什麼可能讓別人控制程式？
- 講：溢位定義與教學範例；為什麼蓋到隔壁危險；修法；canary、ASLR、NX 是補強；為什麼常見在 C／C++、Rust 改變了什麼。
- 不講：exploit 撰寫、ROP。
- 讀完後讀者能：讀一段 C 指出哪一行會溢位、怎麼修。
- 改寫重點：5 處「我的判斷／推測」收斂；ASan 的實測結果直接寫成結果。
- 前置：7。

### Order 9：虛擬機與 hypervisor
- 聚焦問題：一台機器怎麼切給很多人用，牆破了會怎樣？
- 講：開頭接回 8（hypervisor 也是程式，它的溢位就是牆上的洞）；VM、host、guest、hypervisor；巢狀虛擬化與 L1、L2；guest 與 host 之間的溝通路徑（虛擬裝置、VMBus、hypercall）就是攻擊面；為什麼雲端最怕這種洞。
- 不講：Type 1／Type 2 細節辯論、各家 hypervisor 架構比較、沙盒指令輸出解讀（可縮成一個小方塊或刪掉）。
- 讀完後讀者能：向別人解釋 guest 逃脫是什麼、L1 與 L2 差在哪。
- 改寫重點：9 處「我的判斷」與 6 處「依 Learn／Red Hat」重寫成直接敘述；獎金表收成一節。
- 前置：8。

### Order 10：Hyper-V 逃脫案例
- 聚焦問題：一個真實的逃脫漏洞從頭到尾長什麼樣？
- 講：CVE-2021-28476 的封包旅程（guest 送封包 → vmswitch 照著讀 → 沒檢查 → host 當機）；公開展示的結果與宣稱的差別（一句話講清楚）；修補與防守方學到什麼。
- 不講：利用細節。
- 讀完後讀者能：用一張圖說明這個漏洞跨過了哪道牆、為什麼公開 PoC 只算 DoS 那格。
- 前置：9。

### Order 11：TEE 與機密運算
- 聚焦問題：怎麼讓連機器主人都看不到裡面在算什麼？
- 講：VM 隔離 vs TEE 對照表；遠端證明的直覺；WhatsApp Private Processing 為什麼用它；外部審查找到的問題類型；TEE 不是萬能。

- 讀完後讀者能：說出 TEE 防的是誰、遠端證明證明了什麼。

### Order 12：AI 產品的漏洞
- 聚焦問題：AI 產品的獎金計畫收什麼、不收什麼？
- 講：開頭接回 11（推論環境保護好了，AI 產品還有另一類問題）；核心區分——「模型說了什麼」（越獄、幻覺，多半不收）vs「模型被叫去對別人做了什麼」（間接 prompt injection 造成的動作與資料外洩，收）；各家劃線對照表；兩個真實案例；拿到 AI 獎金頁的四步讀法。
- 不講：模型安全研究、紅隊方法論。
- 讀完後讀者能：看一個 AI 產品的問題，判斷它屬於哪一類、可能在哪個計畫收。

### Order 13：頂級獎金地圖
- 聚焦問題：哪些漏洞值幾十萬到上百萬美元？為什麼是這些？
- 講：
  - 依「被打穿的是什麼」分類整理各家最高價碼，每類一段：先講要打穿什麼、為什麼這麼貴，再列代表計畫與上限，最後連回系列對應篇。
  - 候選類別與計畫（寫稿時逐一回官方頁查證現行金額與條件；查不到現行官方數字的不寫）：
    | 類別 | 候選計畫 | 系列對應篇 |
    |---|---|---|
    | 手機作業系統（零點擊、完整攻擊鏈） | Apple Security Bounty、Google Mobile VRP／Android、Samsung Mobile Security | 7、8 |
    | 瀏覽器（從網頁內容打穿到系統） | Chrome VRP、Mozilla、Microsoft Edge | 7、8 |
    | 虛擬化與雲端隔離 | MSRC Hyper-V、Azure、Google Cloud／kvmCTF、AWS | 9、10 |
    | 機密運算與 AI 基礎設施 | Meta Private Processing、Apple Private Cloud Compute | 11 |
    | 大型網站與帳號系統 | Google VRP、Meta、Microsoft 線上服務 | 4、5 |
    | AI 產品 | Google AI VRP、OpenAI、Anthropic、Microsoft Copilot | 12 |
    | 加密貨幣與智慧合約 | Immunefi 上的協議（以鎖倉資金比例計） | 不在系列範圍，一段帶過 |
    | 漏洞競賽 | Pwn2Own（現場打穿，獎金加獎品） | 7–10 |
  - 讀價目表的四個前提：上限要什麼條件（完整 exploit、零點擊、報告品質）；是哪個計畫哪一欄；是否受邀或限時；寫的是基準還是上限。
  - 原貼文的三個數字（Hyper-V 25 萬、Meta 30 萬、Google 9 萬）收成其中一段當實例，示範用四個前提拆一個說法。
  - 頂級價碼與一般收入的差距：平台公開的整體獎金分布或年度報告（例如 HackerOne、Google VRP 年度回顧），讓讀者知道多數獎金落在哪個量級。
  - 白市與灰市的界線：漏洞掮客的收購價常被拿來比，一段說明為什麼本系列不討論、為什麼不能拿來比（合法性、用途、買方）。
  - 上限高是因為難、人少；期望值看法連回 order 6。
- 不講：逐計畫完整價目表、灰市價格細節、任何利用技術。
- 讀完後讀者能：看到任何「某某漏洞值 X 萬」的說法，知道它屬於哪一類、要問哪四個前提，以及跟一般獎金差多少。
- 改寫重點：從三個數字的對帳改成一張依類別整理的地圖；舊稿已查證的 Hyper-V、Meta、Google、Chrome、Mobile VRP 數字沿用前要重查現行版本；每個金額旁寫明計畫與條件，查證過程放 evidence.md；這篇不再是「查證一則貼文」，不加 process-leak topic 豁免。
- 篇幅：預計是全系列最長的一篇，靠類別小標與一張總表讓讀者能跳讀。
- 前置：5、6、9、10、11。
