## 1. 一句話

**賣一個包裹，讓不會寫程式的人在一個下午做出自己的部落格，之後每天用講話的方式產出文章。**

## 2. 顧客旅程

### 第一次（目標：60 分鐘內看到自己的網址）

| 步驟 | 他做什麼 | 卡關風險 |
|---|---|---|
| 1 | 註冊 GitHub 帳號 | 中——很多人沒有，介面是英文 |
| 2 | 在你的範本頁面按「Use this template」，取個名字 | 低 |
| 3 | 註冊 Cloudflare，選剛才那個 repo，按部署 | 中——選項有點多 |
| 4 | 拿到一個 `xxx.pages.dev` 的網址，打開看到部落格 | — |
| 5 | 下載 Claude 桌面版，登入（需付費方案） | 低 |
| 6 | 在 Customize → Plugins 貼上你的 GitHub 網址，按安裝 | 低 |
| 7 | 連接 GitHub connector（按授權） | 中 |
| 8 | 說「幫我寫一篇自我介紹，發布上去」 | — |

## 3. 產品的三個零件

### 零件 A：部落格範本（一個 GitHub repo）

顧客按一個按鈕就複製走。

**技術選擇與理由**

| 選什麼 | 為什麼 |
|---|---|
| Astro，**純靜態輸出** | 不需要伺服器，Cloudflare 免費額度綽綽有餘 |
| Cloudflare Pages | 從網頁 dashboard 就能接 GitHub，不用開終端機。免費方案每月 500 次建置、頻寬不計費 |
| 文章用 Markdown 檔 | AI 讀寫沒有摩擦，而且檔案是顧客自己的，隨時能搬走 |
| **不用** 資料庫、不用 D1、不用 Vectorize | 你自己的站有這些，但那是給你的。顧客多一個零件就多一個壞掉的地方 |

**這是重要的自我克制**：不要把 quidproquo 整套搬過去。顧客要的是能動，不是強大。

**範本裡要有什麼**

- 首頁、文章頁、分類、標籤、關於我
- RSS、sitemap、OG 圖自動生成
- 站內搜尋（Pagefind，建置時產生，不需伺服器）
- 深色模式
- 一份 `AGENTS.md`＋一份 `CLAUDE.md`（內容是「這個部落格的規矩」，兩邊都吃）
- **簡化過的 frontmatter**：只留 `title` / `date` / `description` / `tags` / `draft`。你自己的站有十個欄位，顧客用五個就夠
- 三篇範例文章（讓他一打開就看到成品，不是空站）

**範本裡的護欄**（做不出壞東西比做出好東西重要）

- 建置時檢查：frontmatter 齊不齊、內部連結會不會斷
- 缺欄位就建置失敗，而且錯誤訊息要是**人話**，不是堆疊追蹤

### 零件 B：AI 設定檔（一個 plugin）

**怎麼交付**：把 plugin 放在一個 GitHub repo，顧客在 Claude 的 Customize → Plugins → 「+」→「Add marketplace」→ 貼上你的 repo 網址 → 按 Install。

**全程不用開終端機**，這是官方支援的路徑（[官方說明](https://support.claude.com/en/articles/13837440-use-plugins-in-claude)）。付費方案（Pro 以上）都能用。

**裡面五個技能**

| 技能 | 顧客怎麼叫它 | 它做什麼 | 來自 |
|---|---|---|---|
| 研究 | 「幫我研究 X」 | 把題目拆成幾個小問題 → 每個至少查兩個來源 → 標出哪些查證過、哪些只有單一來源 → 存成一份筆記 | 改寫自 `deep-research` |
| 寫作 | 「寫成文章」 | 筆記變文章，自動補 frontmatter，引用寫成內文連結 | 改寫自 `post` |
| 審稿 | 「幫我看一下」 | 檢查標題階層、摘要是不是廢話、標籤有沒有亂長 | 改寫自 `post-review` |
| 查證 | 「幫我查證」 | 把文章裡的數字、版本、日期、引言全抽出來，逐條對回原始來源，標成「確認 / 過期 / 查不到 / 有衝突」 | 改寫自 `post-verify` |
| 發布 | 「發布」 | 存檔 → 透過 GitHub connector 推上去 → 等建置 → 回報網址 | 新做 |

**你已經有其中四個，而且是在 671 篇文章上磨出來的。** 這是別人抄不走的部分——檔案能抄，判準抄不走。

**移植時的硬限制**：你現有的 skill 假設本機有 `pnpm`、有 shell script、有 git working tree。**產品版一律不能依賴這些**，因為顧客沒有。所有檢查要嘛在 Cloudflare 建置時跑，要嘛在 Cowork 的沙箱裡用純檔案操作完成。

**兩個設計原則**

1. **AI 不寫「我」的部分。** 研究、結構、查證交給 AI；第一人稱的經驗與看法必須是顧客自己的。這要寫死在技能裡，不是建議。
2. **每一步都要讓他看見。** 查了哪些來源、哪些沒查證到，要攤開給他看，不要只丟一篇完稿。

### 零件 C：教學

- **一份圖文教學**：就是部落格系列的第 1–4 篇，寫的時候直接用要賣的範本。
- **一份「壞掉了怎麼辦」清單**：GitHub 註冊、Cloudflare 部署失敗、connector 授權、建置紅字，這四個是預期的卡關點。
- **一支 10 分鐘影片**（選配，但轉換率差很多）：從零到看見自己的網址，完整錄一遍。

## 4. 技術架構

```
顧客的電腦                     Anthropic 雲端                 GitHub / Cloudflare
─────────────                 ──────────────                ──────────────────
Claude 桌面版        ←→        Cowork（跑在遠端沙箱）
  · 存取本機檔案               · 執行研究、寫作、查證
  · 開瀏覽器                   · 裝了你的 plugin
                                      │
                                      │ GitHub connector
                                      ↓
                                              文章推進 repo
                                                    ↓
                                              Cloudflare 自動建置
                                                    ↓
                                              網站更新
```

**關鍵設計決定：發布走 GitHub connector，不走 git 指令。**

理由：Cowork 的工作實際跑在 Anthropic 的遠端沙箱，[shell 指令是在那個隔離環境裡執行的](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)。要在那裡設定 git 認證，對顧客來說太複雜。而 connector 是點一下 OAuth 授權就好，這是不懂技術的人做得到的事。

**備案**（照可行性排序）：
1. GitHub connector（首選）
2. Claude 開 Chrome 操作 GitHub 網頁上傳檔案——慢，但官方支援瀏覽器操作
3. 檔案存本機，顧客自己拖到 GitHub 網頁上傳——體驗差，但一定能動

## 5. 動工前唯一要驗的事

裝 plugin 那條路已經確認（官方文件寫得很清楚）。**剩下沒把握的只有發布那一步。**

### 一天的實測

拿一個乾淨的環境，**全程不開終端機**，照 §2 的九個步驟走一遍。重點在第 7–9 步。

| 結果 | 意思 | 怎麼辦 |
|---|---|---|
| ✅ GitHub connector 能推檔案 | 產品成立，體驗最好 | 照計畫做 |
| ⚠️ 要先設定授權才行 | 產品仍成立 | 把「代設定」變成賣點，那正好是收 $300–800 的地方 |
| ⚠️ 只有瀏覽器操作能動 | 體驗打折但可行 | 發布時間會拉長，教學要說清楚 |
| ❌ 都不行 | 退回半自動 | AI 寫檔案，顧客自己上傳。仍可賣，但價格要下修 |

**在這個測試做完之前，不要寫任何產品程式碼。**

## 6. 里程碑

| 階段 | 做什麼 | 時間 | 完成的標準 |
|---|---|---|---|
| **M0 驗證** | §5 的實測 | 1 天 | 知道發布走哪條路 |
| **M1 範本** | Astro 靜態範本 + 護欄 + 三篇範例 | 1 週 | 你自己按「Use this template」複製一份，30 分鐘內上線 |
| **M2 設定檔** | 五個技能，包成 plugin repo | 1–2 週 | 從乾淨帳號裝起來，能跑完研究→寫作→查證→發布 |
| **M3 真人測試** | 找 3 個真的不懂技術的朋友，**你在旁邊看，不出手幫忙** | 2 週 | 3 人中至少 2 人在 60 分鐘內看到自己的網址 |
| **M4 教學** | 部落格系列第 1–4 篇，用要賣的範本寫 | 邊寫邊修 | 文章寫完＝範本驗證完 |

**M3 是真正的關卡，不是 M1 或 M2。** 你自己跑得動不代表什麼——你寫了 671 篇文章。找真人測，而且**忍住不要幫忙**，卡住的地方就是要修的地方。

M4 和 M5 之間可以停下來，看有沒有人真的想買，再決定要不要上架。

## 7. 定價

| 層 | 內容 | 價格 |
|---|---|---|
| 免費 | 教學文章（系列第 1–4 篇） | $0 |
| 產品 | 範本 + 設定檔 + 圖文教學 + 影片 | 一次性 **$49** |
| 服務 | 一對一幫他裝好 + 一小時教學 | **$500** |

**顧客自己還要付的**：Claude 或 ChatGPT 月費約 $20；網域一年約 $8（選配）。網站主機免費。

### 這兩個數字是怎麼來的

先說最重要的一件事：**這是用比較基準和成本推出來的，不是從顧客資料算出來的。目前沒有任何人付過錢。** 下面是推導過程，你可以不同意任何一步。

**產品層的天花板**（兩條，取低的）

1. 顧客真正的替代方案是 Wix / Squarespace，一個月約 $16–29，**一年 $200–350**。一次性付費必須明顯便宜過人家一年，這個比較才成立 → 上限遠低於 $200。
2. 他已經要付 Claude 月費 $240/年。你的東西是「配件」，配件收超過本體三個月的錢會讓人覺得不對勁 → **上限約 $60–80**。

**產品層的地板**（兩條，取高的）

1. 免費的 Astro 佈景主題到處都是。定在 $9–19 是在跟免費競爭，而且會傳達「沒有售後」的訊號。**太便宜會主動傷害轉換**，因為買家會猜沒人在維護。
2. 客服成本：假設每三個買家有一個來問問題、每次花你 20 分鐘，平均每個買家約 7 分鐘。低於 $25 光客服就虧 → **地板約 $29**。

**同類參考**

| 東西 | 價格 |
|---|---|
| 付費部落格佈景主題 | $29–99 |
| 目前有人在賣的 Claude skill pack | $99（賣家自陳，未經查證） |
| 你的產品 = 佈景 + 設定檔 + 教學 | 應該高於單純佈景 |

**→ 區間夾出 $29–79，落點取 $49。**

為什麼是 $49 而不是區間：**上架只掛一個價格，不要給選單。** $49 在「這是不是沒人維護」的線之上，在「我要考慮一下」的線之下，而且留了做 $29 開學優惠的空間——**永遠不需要漲價**。

**服務層**

- 實際要花你多少時間：1 小時設定 + 1 小時教學 + 兩週內的零星回覆 ≈ **3–5 小時**。
- 技術顧問的合理時薪抓 $75–160 → $300–800。
- 另一個條件：必須是產品價的 **10 倍左右**，才會被當成不同的東西，而不是加購。
- **→ 取 $500。**

### 三個誠實的但書

1. **這些數字沒有顧客資料支撐。** 唯一真正的定價方法是拿去賣。
2. **不要做付費意願問卷。** 你自己整理過，WTP 問卷有雙向偏誤，問到的是意見不是行為。
3. **開高不開低。** 降價很容易，漲價幾乎不可能——對同一批看過舊價格的人尤其不可能。$49 賣不動，降到 $29 你學到東西；一開始就 $29，你永遠回不去 $49。

另外：**不要用「我做了多久」來定價。** 那是沉沒成本，買家不在乎。

### 不做月費訂閱

你自己整理過的數字：AI 產品月費低於 $50 的，一年後只剩 23% 的人還在付。而且訂閱要你扛主機和客服，跟「檔案是你自己的」互相矛盾。

### 營收的現實

主要利潤在服務層。產品層的作用是**篩選**——會買 $49 的人，才是會買 $500 服務的人。

粗算：$49 × 100 人 = $4,900；$500 × 10 人 = $5,000。**十個服務客戶等於一百個產品客戶**，而且服務客戶會給你最好的產品回饋。

## 8. 怎麼讓人知道

1. **部落格系列第 1–4 篇**是主要入口。寫的時候不藏私，把整套方法完整寫出來——照著做得起來的人自然會有一批想直接買包裝好的。
2. **第 4 篇底部放一句**「想要整套裝好的版本，留個信箱」。這是最便宜的方式，看有沒有人真的想買。
3. **plugin repo 本身就是曝光**。放在 GitHub 上公開，做 skill 的人會找到。
4. **不要投廣告。** 這個東西需要信任，而信任來自 671 篇文章，不是廣告。

**開始賣的標準要事先訂死**：建議「第 4 篇發布後 6 週內，收到 10 個信箱或 3 個直接問價」。訂死才不會自己騙自己。

## 10. 命名

### 先講判準

| 判準 | 為什麼 |
|---|---|
| 中英文都念得出來 | 你的讀者是中文的，但 GitHub、網域是英文世界 |
| 搜尋得到 | 太通用的詞（「開站」「落筆」）搜尋結果會被淹沒 |
| 不要框死在「部落格」 | 之後可能擴到電子報、個人網站，名字裡有 blog 就綁死了 |
| 網域拿得到 | `.com` 多半沒了，`.cc` / `.tw` / `.blog` 比較實際 |

### 十個候選

| # | 名字 | 意思 / 由來 | 好在哪 | 弱在哪 |
|---|---|---|---|---|
| 1 | **有據** | 「有所依據」 | 直接命中查證這個差異點，兩個字好記，中文語感好 | 英文要另想寫法（Youju / Grounded） |
| 2 | **初稿** / Firstdraft | AI 給你的是初稿，不是成品 | **跟產品哲學一致**——誠實說明 AI 的角色。中英都通 | Firstdraft.com 幾乎確定被佔 |
| 3 | **一人報社** | 一個人的編輯台 | 畫面感最強，一聽就懂成果是什麼 | 四個字偏長，且「報社」框在新聞感 |
| 4 | **落筆** | 開始寫的動作 | 優雅，中文圈很吃 | 常用詞，搜尋度低 |
| 5 | **Groundwork** | 打地基 ＋ 做功課的雙關 | 英文好念，含意剛好是「研究先行」 | 中文市場要另取名，等於兩個品牌 |
| 6 | **慢寫** / Slowrite | 反內容農場的立場寫進名字 | 立場鮮明，會吸引到對的人 | 「慢」對想要快的人是負面訊號 |
| 7 | **PostCraft** | 做文章這件手藝 | 好拼、好註冊、意思清楚 | 平庸，記不住 |
| 8 | **自己的房間** | 吳爾芙《A Room of One's Own》 | 呼應你說的「**自己的**」部落格，文學感強 | 太長，且有作品聯想的包袱 |
| 9 | **有本** | 「有本事」＋「有一本自己的東西」 | 雙關漂亮，兩個字 | 意思要解釋才懂 |
| 10 | **Quidproquo Kit** | 直接掛在你既有品牌下 | **繼承 671 篇文章的信任，零品牌成本** | 綁死在你的個人品牌，之後難分割出售 |

### 我的建議

真正該選的是這兩個之一，取決於你想不想另外養一個品牌：

**如果不想多養一個品牌 → 選 10（Quidproquo Kit）。** 你在前面的評估裡自己得出的結論是：護城河不在檔案，在判準和你累積的內容。掛在既有品牌下，第一天就繼承那個信任，而且省下所有品牌建立的力氣。缺點是這條路走下去，產品跟你個人是綁在一起的。

**如果想要一個能獨立長大的東西 → 選 1（有據）。** 它把產品最難被抄的那件事（查證）直接寫進名字，兩個字、好記、中文語感好，而且不含「部落格」所以不會框死未來。英文可以用 `youju` 或直接不取英文名。
