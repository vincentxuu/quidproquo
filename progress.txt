  **schema 擴充**：新增 `additionalSeries`，一篇文章可從屬多個系列（主 `series` 仍是卡片徽章唯一來源）。
  **這輪最大的錯：翻新未經獨立查證就 commit 並 push。** 五個寫作 agent 全部只發 idle、沒交回報，
  我只抽看三個 diff 就發佈。被使用者問「內容有再次查證嗎」之後補跑五個乾淨 context verifier，修掉 31 項。
  **四組的錯誤型態各不相同，這比個別錯誤更值得記**：
  ①Cloudflare＝**把合理推論寫成「官方直接說了」**（最糟一條：官方原文是 not advised to rely on，
  文章寫成官方保證）②Browser＝**查了但收斂太用力**（把 7 月的資安報告憑印象填成 8 月，
  即 commit 前兩天）③AEO＝**把「我沒查到」寫成肯定句**，並**用狀態碼冒充營運確認**——
  宣稱「逐家確認網站仍在運作」，實際兩家已收掉的公司都還回 HTTP 200
  ④RAG＝**把多資料集自行平均後當成論文原文**（3.3×/1.9× 論文裡不存在）。
  **查證員本身也會收斂太用力**：兩輪對 OpenAI reasoning 的 CoT 段落給出相反結論，我實抓頁面全文
  才發現兩邊各讀一半（小標 Avoid…、內文 unnecessary、概述段 may not/can sometimes），
  因此照第一輪誤改過一次再改回——**agent 的查證結論同樣要抽驗，不能照單全收**。
  **可重用做法**：明確要求 agent 誠實回報覆蓋度有效——RAG 第一輪主動說「45 篇只深查 27 篇」，
  才能派第二輪補完剩下 18 篇；否則會拿到一份假裝覆蓋全部的報告。
  **後續共跑九輪、修 110+ 條**（commit dce1e59→d9c9bbc）。查證範圍分三階段推進，每階段的發現不同：
  ①只驗翻新的**新增行** ②驗**原稿殘留內容**（錯誤密度明顯更高，因為那些從發文後就沒人再驗過）
  ③補四個缺口（未驗的 code block、跨篇數字對表、假限制掃描、英文版獨立查證）。
  **第②階段冒出兩個新型態**：**API 形狀腐爛**（翻新只改 frontmatter 的檔案，主體 code block
  從沒被重對過文件——Cloudflare 有一篇四組方法裡兩組是壞的，`gateway().run()` 根本不存在）、
  **上游能力擴張後舊「限制」變假**（文章寫「仍要自備 API key」，官方早已代管憑證）。
  單一影響最大的錯是截圖 token 數：把 base64 的 KB 推成 token，錯一個數量級且複製在三處
  （官方按 28×28 patch 計，1920×1080 是 1,560 個 visual token）。
  **第③階段四組有三組推翻了我的假設**：我以為最可能出事的英文版，46 對只有 3 個問題且限定語
  翻得比中文更保守；我點名的四個「假限制」高嫌疑檔三個是誤報，它們反而主動寫了「上游現在有 X」；
  我以為沒對過文件的 code block，其實那三篇根本沒有函式庫 code（全是手刻示意），
  **腐化面積被寫法本身壓住了**。真正的弱點不在 benchmark 數字（抽查全中）而在**值域與引用元資料**：
  「分數範圍 0.0–1.0」複製到 6 處且與同系列專篇正面衝突、同一份 survey 年份 16:16 對半分裂。
  **教訓**：①**先驗新增行、再驗原稿殘留**，後者才是主要風險區；②zh/en 機器化數字對表證實翻譯忠實，
  但這也代表**錯誤自動加倍**，一律成對修；③**我自己也越界過一次**——補回連的 regex 動到 23 個範圍外
  檔案（雖然改對了格式），已還原；跨 session 期間任何 repo-wide 的 sed/regex 都要先框好檔案清單。
