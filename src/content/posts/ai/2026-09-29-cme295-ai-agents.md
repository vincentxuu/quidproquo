[錄影 00:00–05:11](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=0s)

講者用寫程式的變化開場（投影片第 3–6 頁）：2023 年把程式碼複製貼上到聊天視窗，2024 年在 IDE 裡按 tab 自動補完，2025 年交出整個任務，2026 年變成 agent 自己寫程式、寫測試、跑測試、部署。這一講要講的就是中間這段差距。

1. **知識停在訓練資料**。講者拿 GPT-6 Astra 的模型卡舉例，知識截止日是 2026 年 4 月 30 日；那週剛辦完的美國期中選舉，它不會知道。你的私有程式碼它也沒看過。

**自我檢查**：「把訓練結束後發生的事全部貼進 prompt」為什麼行不通？講者列了三個理由。

<details>
<summary>答案</summary>

一、context window 有上限，GPT-6 Astra 約 100 萬 token，遠不夠裝下訓練後發生的所有事。二、就算裝得下，輸入越長模型表現越差（needle in a haystack 測試）。三、輸入按 token 計價，越長越貴。判準：三點都要有，第二點要講出「長了會變差」而不只是「裝不下」。

## 檢索：只把相關的東西放進 prompt

[錄影 05:11–15:54](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=311s)

### 為什麼不全塞

上面的三個理由在投影片第 10–12 頁各配一張圖。第二點用的是 Kamradt 2023 年的 [needle in a haystack](https://github.com/gkamradt/needle-in-a-haystack) 圖：橫軸是輸入長度，縱軸是「針」放在文件中的位置。講者的讀法是，短輸入時模型幾乎都找得到；輸入一長，放在文件前段的事實就開始找不回來。

結論是只放跟任務相關的東西，這就是 **RAG**（retrieval-augmented generation，[Lewis 等人 2020](https://arxiv.org/abs/2005.11401)）：retrieve 撈出相關文件、augment 把它們加進 prompt、generate 產生回答。

課堂問答補了兩件跟成本有關的事：撈進來的文件一樣算輸入 token；推理模型的 reasoning token 就算沒顯示給你看，也照樣計費。所以檢索要盡量精準。另一個學生問模型怎麼知道哪些是撈進來的內容，講者說通常用特殊標籤包起來。

三步裡最關鍵的是第一步：撈錯了，後面再好也沒用。難處在自然語言可以換句話說，同一件事不一定用到 query 裡的那幾個字，所以單純比對字面不夠。

### 先建知識庫

[錄影 12:36](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=756s)

收集文件、切成小塊（chunk）、每塊算一個 embedding 向量。投影片第 25 頁列了三個超參數，講者給的數量級：

| 超參數 | 常見大小 | 講者的考量 |
|---|---|---|
| embedding 維度 | 幾千 | 文件越難懂、越細膩，維度可以越大 |
| chunk 大小 | 幾百個 token | 太大就違背「輸入不要太長」的初衷 |
| chunk 重疊 | 約 10% | 避免句子被從中間切斷、看不出在講什麼 |

有學生問 chunk 會不會隨每次請求改變。講者說 chunk 是固定的，變的只有 query；但知識庫本身不是固定的，可以隨時加新文件，例如每天新增的內部文件，唯一要注意的是**用同一個 embedding 模型**，相似度比較才是同一把尺。

## 兩階段檢索：先求撈得到，再求排得準

[錄影 15:54–35:02](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=954s)

| | 第一階段：撈候選 | 第二階段：重排 |
|---|---|---|
| 目標 | 最大化 recall | 最大化 precision |
| 面對多少文件 | 幾千到幾百萬 | 約 100 個候選 |
| 方法 | 便宜的相似度比對 | 比較貴、比較細的模型 |

### 第一階段：bi-encoder、BM25 與混合

**語意搜尋**。query 和每個 chunk 各自過 encoder 得到向量，再算相似度（投影片引 [Sentence-BERT](https://arxiv.org/abs/1908.10084)），這叫 **bi-encoder**。便宜的原因是 chunk 的向量可以事先算好；推論時只要算 query 的向量，再用近似最近鄰演算法找最像的幾個。

講者用一個例子說明它的盲點。query 是「Where is Cuddly?」（Cuddly 是一隻泰迪熊），知識庫有四塊：

1. Huggy likes to work downstairs
2. Where is Paris located?
3. he was in a cuddly mood
4. Cuddly spends most days surrounded by books

語意搜尋可能撈到前兩塊：Huggy 跟 Cuddly 意思接近（抱抱、摟摟），「Where is Paris located?」也是一個問「在哪」的問句。但答案在第 4 塊。

**BM25** 比對的是 query 跟文件共有的字，這個例子會撈到第 3、4 塊，因為都有 Cuddly。講者也說，一樣舉得出只靠 BM25 不夠的例子：只比對關鍵字，換個說法就撈不到。實務上兩者並用，把語意排名和關鍵字排名合成一個**混合排名**，多數情況比單用任何一種好。

**縮小 query 與文件的差距**。query 多半是問句，文件多半是陳述句，用同一個 encoder 編出來的向量可能不在同一個「區域」。[HyDE](https://arxiv.org/abs/2212.10496)（hypothetical document embeddings）先請 LLM 依 query 寫一份假的答案文件，再拿假文件去比對。講者也提到另一類做法：query 裡塞了好幾個問題時，先改寫拆成幾個子問題分別檢索。

**contextual retrieval**。重疊切塊還是可能切出一塊單獨看不懂的內容。Anthropic 的 [contextual retrieval](https://www.anthropic.com/research/contextual-retrieval) 請 LLM 讀整份文件，替每一塊補一句「這塊在整份文件裡講什麼」，再拿補過的塊去做 embedding。投影片第 36–37 頁把那段 prompt 秀出來，講者特別指出它的排法：整份文件放最前面、要處理的 chunk 放後面，這樣同一份文件的每一塊都共用同一段開頭，可以吃到上一講講過的快取價格。投影片第 38 頁截的 OpenAI 價格頁上，GPT-6 Astra 的輸入是每百萬 token 10 美元、快取輸入 1 美元，差 10 倍。站上的 [contextual retrieval 專文](/posts/ai/2026-03-12-contextual-retrieval)有完整做法。

### 第二階段：cross-encoder 重排

[錄影 28:36](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=1716s)

候選只剩約 100 個，可以用貴一點的模型。**cross-encoder** 把 query 和 chunk 接成一個序列（中間用特殊 token 隔開）一起送進 encoder，讓兩邊的 token 透過 self-attention 互相看，最後拿 CLS token 的輸出投影成 0 到 1 的相關分數，跟第 2 講的 BERT 是同一個做法。訓練資料是標好「相關／不相關」的 query–chunk 配對。

講者的例子：「找一隻戴紅圍巾、穿藍襪子的泰迪熊」跟「戴藍圍巾、穿紅襪子」，各自壓成一個向量時可能非常接近；放進同一個 encoder，「紅」「藍」才有機會對上文件裡的對應位置。每個候選各跑一次，依分數排出最終順序。

檢索段最後（42:46 起）的問答有三點：

- **向量資料庫用在哪**：只用在第一階段，存 chunk 與它們的向量。第二階段的分數必須 query 跟 chunk 一起算，沒辦法預先存。
- **前 k 個要全部放進 prompt 嗎**：常見做法是全放；也可以再設一個分數門檻。
- **要告訴模型哪塊比較相關嗎**：看實作，通常依相關程度由高到低排。

### 怎麼知道撈得好不好

[錄影 35:15](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=2115s)

需要一份標好「哪些 chunk 跟哪個 query 相關」的資料集，拿系統排出的前 k 名去比。投影片第 45–48 頁的四個指標，$\text{rel}_i \in \{0, 1\}$ 表示第 i 名是否相關：

$$
\text{DCG@}k = \sum_{i=1}^{k} \frac{\text{rel}_i}{\log_2(i+1)}, \qquad \text{NDCG@}k = \frac{\text{DCG@}k}{\text{IDCG@}k}
$$

IDCG@k 是排序完美時的 DCG@k。除以它是因為 DCG 本身沒有固定上限，不好解讀；正規化以後落在 0 到 1，越接近 1 越好。分母的 $\log_2(i+1)$ 讓排在後面的相關文件得分打折。

$$
\text{RR} = \frac{1}{\text{第一個相關 chunk 的名次}}, \qquad
\text{Recall@}k = \frac{|\text{前 } k \text{ 名中相關的}|}{|\text{全部相關的}|}, \qquad
\text{Precision@}k = \frac{|\text{前 } k \text{ 名中相關的}|}{k}
$$

講者問全班誰聽過 NDCG，沒有人舉手，所以這段講得比較慢。

<details>
<summary>本文的例子：一組排序算四個指標</summary>

某個 query 共有 3 個相關 chunk。系統排出的前 3 名是：不相關、相關、相關（第三個相關的排在第 5 名）。k = 3：

```
DCG@3  = 0/log2(2) + 1/log2(3) + 1/log2(4) = 0 + 0.631 + 0.5 = 1.131
IDCG@3 = 1/log2(2) + 1/log2(3) + 1/log2(4) = 1 + 0.631 + 0.5 = 2.131
NDCG@3 = 1.131 / 2.131 ≈ 0.531

RR          = 1/2 = 0.5        （第一個相關的在第 2 名）
Recall@3    = 2/3 ≈ 0.667      （3 個相關的撈到 2 個）
Precision@3 = 2/3 ≈ 0.667      （前 3 名有 2 個相關）
```

把第 1、2 名對調，NDCG@3 升到 $1.5 / 2.131 \approx 0.704$、RR 升到 1，Recall 與 Precision 不變。這就是 NDCG 和 RR 會看順序、Recall 和 Precision 不看的意思。

</details>

### 寫程式時，改用 grep

[錄影 41:00](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=2460s)

講者回到開頭的 coding agent。問程式碼的問題時，你通常要找的是某個函式，語意相近的程式碼用處不大，要的是**完全符合**。所以 coding agent 用的是 grep（global regular expression print）：給一個字串，列出它在 codebase 裡出現的所有位置。前面的語意與關鍵字搜尋，主要適用於自然語言的問題。

**自我檢查**：一個 query 有 4 個相關 chunk，系統前 5 名的相關性是（1, 0, 0, 1, 0）。算 RR、Recall@5、Precision@5。如果把 bi-encoder 換成 cross-encoder 直接對 100 萬個 chunk 打分，會發生什麼事？

<details>
<summary>答案</summary>

RR = 1（第 1 名就相關）；Recall@5 = 2/4 = 0.5；Precision@5 = 2/5 = 0.4。cross-encoder 必須把 query 和每個 chunk 一起過一次模型，不能預先算，100 萬次前向傳播太慢太貴，這正是要先用 bi-encoder 縮到約 100 個候選的原因。判準：指標算對，並講出「cross-encoder 不能預先算」。

</details>

## Tool calling：讓模型做事

[錄影 44:28–57:01](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=2668s)

### RAG 也解決不了的問題

Shervine 接手後把兩個問題並排（投影片第 51–54 頁）：「Cuddly 在哪？」可以靠 RAG，因為 Cuddly 不太移動，每天更新的知識庫裡有「Cuddly 大部分時間待在書堆裡」。但「幫我找附近的熊」就不行：它需要**即時**的資料（現在哪裡有熊），也需要知道**你在哪**（得在你的裝置上查 GPS）。RAG 撈到的只會是過時的靜態資料，例如「Cuddle Bear 整天在圖書館讀波斯詩」，模型只能回「不確定，去圖書館看看」。

### 三個步驟

投影片第 56–58 頁：

1. **LLM 預測要呼叫什麼**：給它可用的 function API，它不直接回答，而是寫出「用 `my_position()` 取得位置，再呼叫 `find_teddy_bear()`」
2. **後端執行**：真的去打 API，回傳 `{"name": "Teddy", ...}`。這一步跟 LLM 無關
3. **LLM 讀結果、寫回答**：「一隻開心的 Teddy 就在隔壁房間！」

講者說把這三步完全內化，工具就沒什麼好怕的了。學生問呼叫工具時是不是要等：要等，但多數情況下這不是主要延遲，取得 GPS 幾乎是瞬間，網路搜尋使用者感覺得到，但通常還是比產生回答本身快。

### 工具長什麼樣

[錄影 50:48](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=3048s)

投影片第 59–61 頁是一支完整的 `find_teddy_bear.py`。講者標出三件事：

- **模型看得到的只有 API 描述**：函式名稱、參數與型別、docstring、回傳型別。函式內部的程式碼（打哪個 API、怎麼算距離）不會給模型看，所以 docstring 寫得清楚很重要。
- **輸入要好懂**：參數名稱叫 `location`，型別寫明是 `(緯度, 經度)`。
- **輸出也要好懂**：回傳一個有 `name`、`distance_meters`、`mood`、`message` 欄位的 dataclass。結果要回填給模型讀，所以工具常用 enum 這類結構化型別。

常見的工具（投影片第 63–67 頁）分三類：

| 類別 | 例子 | 講者的說明 |
|---|---|---|
| 即時資訊 | 網路搜尋、天氣、股價、codebase 查詢 | 介面上的「正在搜尋網路」就是一次工具呼叫，順便讓使用者等得住 |
| 計算 | 計算機、執行程式（常是 Python） | 下一個 token 預測不擅長算數，交給確定性的程式最可靠；你在對話裡看到的圖表就是執行程式的結果 |
| 行動 | 寄信、傳訊息、其他電腦操作 | 把你的意圖寫成信，再代你送出 |

**自我檢查**：如果 `find_teddy_bear` 的 docstring 寫得很好，但回傳的是一串沒有欄位名稱的 tuple，例如 `("Teddy", 12.3, "happy")`，哪一步會出問題？

<details>
<summary>答案</summary>

第三步。模型要讀懂後端回傳的結果再寫成自然語言，沒有欄位名稱時它得猜 12.3 是距離還是別的東西。判準：指出「輸出要能被模型解讀」是第三步的需求，跟第一步的 API 描述是兩回事。

</details>

## 怎麼教模型用工具

[錄影 57:01–1:02:49](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=3421s)

學生問：模型能用哪些工具，是不是訓練時就定死了？講者說一兩年前會回答「是」：當時的做法是 **SFT**，準備兩種訓練例子，一種教模型從 query 和 API 清單預測出工具呼叫與參數，另一種教模型把後端回傳的結果轉回自然語言（投影片第 68–69 頁）。

現在不是這樣。訓練流程會教模型一般性的使用工具能力（例如怎麼用 Python），但具體的工具不寫進權重，改用 **prompting**：在 docstring 這類地方寫清楚怎麼用。講者也說，隨著這些變成模型原生的能力，只要工具的輸入輸出設計得好懂，需要額外說明的地方越來越少。

那說明要怎麼寫？講者問全班。有人說「叫另一個模型寫」，講者說可以。有人說「用 MCP」，講者說那是另一件事：MCP 規定說明寫在哪裡，但沒告訴你該寫什麼。他給的答案（投影片第 70–71 頁）：

1. 準備一組你在意的 query，以及**期望的回答**（最難取得的部分，需要專家寫；LLM 生成的合成答案常常不夠貼近你要的）
2. 用目前的 prompt 跑出**實際的回答**
3. 讓一個推理模型同時看期望與實際的回答，反覆修改工具說明，直到實際回答接近期望

這等於拿前面 SFT 用的那種輸入／輸出配對當評估集，只是改的不是權重，是 prompt。

## 工具一多：衝突、tool selection 與 context 膨脹

[錄影 1:02:49–1:12:56](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=3769s)

LLM 服務商的動機是盡量多提供有用的工具。講者問這會有什麼問題，學生答「衝突」。

**無害的衝突**。「給我看我的泰迪熊的早晨例行公事」，`get_drive` 和 `get_doc` 都可能接下這個任務，兩者能力重疊，但結果差不多，叫 benign。

**有問題的衝突**。「幫我找我的泰迪熊」，`list_files` 會在你電腦裡找到 `teddy-profile-pic.jpg`，`find_teddy_bear` 會告訴你它在隔壁房間。同一句話兩種解讀，答案完全不同。

學生追問兩點：

- **這不是使用者沒講清楚嗎？** 講者說有一部分是，但使用者往往不知道有哪些工具開著，而且定義工具的人和提供服務的人常常是不同團隊。看到回答跟使用者意圖對不上，可能代表工具開太多了。
- **把 temperature 設成 0 求確定性呢？** 會有幫助，但品質通常會下降；而且確定性也可能讓這個模糊的問題「每次都錯」。

### Tool selection

[錄影 1:08:21](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=4101s)

不讓模型面對全部工具，先挑一個子集。投影片第 84–85 頁（引 Robert 等人 2024 年的 *Automatic Tool Selection to Reduce Large Language Model Latency*）列了 router 可以參考的四種訊號：

| 訊號 | 講者的例子 |
|---|---|
| 對話 | 前面一直在聊實體泰迪熊在哪，「找我的熊」就該用 `find_teddy_bear` |
| 記憶 | 使用者過去講得比較具體的類似問題，可以當這次的參考 |
| 使用者資料 | 企業裡財務人員常用財務工具，工程師常用另一組 |
| 設定 | 使用者自己開關了哪些工具；沒開的工具要不要問他開，是產品取捨 |

所以 tool selection 是兩步：router 先挑出子集放進 context，主模型再在子集裡選。router 通常是很輕的 LLM，因為任務不難但需要低延遲；它也有自己的 prompt，例如規定「選了 A 就不要選 B」來處理重疊的工具。

**context 膨脹**。就算沒有衝突、預測完美，工具太多仍然有害：上一節的 needle in a haystack 說明 context 越長越容易漏，講者稱這個現象 context rot。服務商因此很在意什麼東西放進 context，不想在第一個問題就讓使用者背一大包工具定義。

## MCP：工具寫一次，到處能用

[錄影 1:12:56–1:16:18](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=4376s)

沒有標準時，同一個工具要給三個 LLM 用，就得照三家的格式各寫一次。**MCP**（Model Context Protocol，Anthropic 2024 年提出）把這件事標準化。全班都聽過 MCP，所以這段講得很快。

- **MCP server**：放工具的實作與商業邏輯
- **MCP client**：去呼叫 server 的那一端；使用者面對的是 client（投影片第 89 頁還畫了包住 client 的 host，例如 Claude Desktop）
- server 提供三類東西：**tools**（標準化的參數與輸出格式）、**prompts**（用工具完成特定流程的捷徑）、**resources**（應用層可以提供給工具的資料）

講者的例子（投影片第 90 頁）：一個推薦詩集給泰迪熊的書商 server，tools 有「找書」「推薦」，prompts 有「找某本書名」「依泰迪熊的口味推薦」，resources 有泰迪熊既有的藏書與暢銷書單。

## 成本：固定的東西放最前面

[錄影 1:16:18–1:22:54](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=4578s)

講者自己提出質疑：一直往 prompt 裡塞工具說明，帳單不會爆嗎？學生答 prompt caching。投影片第 91 頁截了 Gemini、Claude、OpenAI 的價格頁，標題寫快取輸入「10–40x cheaper」，講者口頭說是 10 倍的數量級。他另外指出價格頁開始出現「5 分鐘寫入」「1 小時寫入」兩欄：第一次送出時付一筆寫入費把 prompt 存進快取，存活時間內再送同樣的開頭就能重用。每分鐘都會重用的高流量流程，選 5 分鐘就夠。

接著是一個小練習（投影片第 92–101 頁）。prompt 由三部分組成：

- **使用者 prompt**：你這次問的問題
- **工具定義**：tool selection 挑出來的，或固定提供的那一組
- **使用者 context**：服務商自動塞進去、你看不到的東西，例如「使用者 IP 大約在 Stanford, CA；今天是 2026-11-06；現在是太平洋時間下午 4:55」。問今天幾號不需要工具，讀這段就知道

講者輪流擺出三種順序，問哪一種好。前兩種都是「Bad」，因為固定的部分不在最前面；正確答案是**工具定義 → 使用者 context → 使用者 prompt**。投影片第 101 頁的結論：「Frontload all fixed parts to the beginning of the prompt!」使用者 context 帶著時間，每次都會變；使用者 prompt 當然也會變；工具定義如果是固定的一組，或同一批請求剛好選到同一組，就是可以重用的前綴。

學生問改了工具說明怎麼辦：快取就失效了，要重新「加熱」。講者說這不是大問題，工具說明頂多一天改一次，而請求是每分鐘幾百個。

**自我檢查**：一個 agent 的 prompt 依序是「系統規則（固定）→ 現在時間 → 工具定義（固定）→ 使用者問題」。快取能重用到哪裡？要怎麼改？

<details>
<summary>答案</summary>

只能重用到系統規則為止，因為現在時間每次都變，後面的工具定義就算一樣也不再是相同前綴。改成「系統規則 → 工具定義 → 現在時間 → 使用者問題」，把兩段固定的東西都放到變動的部分之前。判準：講出快取只認「完全相同的開頭」。

</details>

## Harness：模型以外的一切

[錄影 1:22:54–1:33:33](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=4974s)

講者說前面花這麼多時間在 tool calling，是因為它是 agent 系統的地基。接著問誰聽過 harness，全班都舉手，他說這是「2026 年的流行詞」。

### 定義與比喻

投影片第 103–105 頁引 Databricks 2026 年的 *What is an AI Agent Harness?*：agent 由**模型**和 **harness** 組成，harness 是模型以外的一切，列了六項：

- 工具
- 動作的先後順序
- compaction 策略
- 記憶
- 所有外圍的 prompt
- guardrails

比喻是車子：模型是引擎，harness 是其餘部分。兩者互補，弱模型配強 harness 不行，反過來也不行。

### ReAct：觀察、計畫、行動

[錄影 1:24:41](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=5081s)

[ReAct](https://arxiv.org/abs/2210.03629)（Yao 等人，2023）把很多人各自在做的事寫成一個框架：拿到輸入後，**observe**（整理目前已知的狀態）→ **plan**（決定要做什麼、呼叫哪個工具）→ **act**（執行）→ 再 observe，直到滿意才輸出。投影片第 108–122 頁一步一步走溫度計的例子：

| 輪 | Observe | Plan | Act |
|---|---|---|---|
| 1 | 泰迪熊冷，可能跟室溫有關，但室溫未知 | 先查室溫 | `get_current_room_temperature()` |
| 2 | 現在 65°F，比一般舒適溫度低約 5°F | 調高 5°F | `increase_temperature(value=5)` |
| 3 | 恆溫器已設為 70°F，應該夠暖了 | — | 輸出：「恆溫器已設為 70°F，你的泰迪熊很快會暖起來」 |

輸入不一定是使用者打的字，也可以是外部事件，例如某個指標超過門檻。

學生問：這三步是訓練出來的嗎？是，主要在訓練中學會用工具，變成模型原生的能力。另一個問題：這裡面有推理嗎？講者說每次執行工具後都要有一段回顧剛剛發生什麼，這是**必要的**推理，跟推理模型（見 [order 6](/posts/ai/2026-09-29-cme295-llm-reasoning)）那種額外的思考層不同；不是推理模型也會做這三步。

### A2A

[錄影 1:28:47](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=5327s)

溫度計 agent 之外，還可以有占用偵測、能源管理、空氣品質 agent，它們之間也要溝通。工具有 MCP，agent 之間有 Google 2025 年的 **A2A**（Agent2Agent）。投影片第 127 頁的結構：每個 agent 有一張 `AgentCard`（名稱、網址、版本、skills 清單），每個 `AgentSkill` 有 id、描述與範例，另外有 `AgentExecutor` 負責執行與取消。講者說要講快一點，這段不到一分鐘。

### Context compaction：騰出空間

[錄影 1:29:24](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=5364s)

一直呼叫工具，總會碰到 context window 的上限，那時候不處理就不能繼續。投影片第 130–132 頁的三種做法，可以混著用：

| 做法 | 依據 | 講者的說明 |
|---|---|---|
| 刪除 | 內容還有沒有用 | 很多工具輸出只有下一輪需要，之後可以刪 |
| 滑動視窗 | 時間 | 越久以前講的越不重要，只留最近的 |
| 摘要 | 生成 | 最常見。把目前為止的內容整理進固定欄位，用這份短摘要接著對話 |

摘要的欄位，投影片引的是 coding agent Pi 文件中的格式：**目前進度、限制條件、剩下的工作、參考資料**。

學生問：推理過程會留在摘要裡嗎？講者說看它對各欄位有沒有貢獻，但通常不會是主要內容，摘要比較像「使用者想做什麼」的高層描述，不會原樣留下推理過程。

### Memory：讓資訊活得比一段對話久

[錄影 1:31:12](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=5472s)

compaction 處理的是一段對話之內。要跨對話保留資訊，就是記憶：

- **短期記憶**：講者說這只是 context window 的花俏說法，就是目前為止講過的內容。
- **長期記憶**：例如你某次跟模型討論節日禮物，說了「泰迪熊可能是好禮物」，下次問「節日送什麼好」時希望它記得。

長期記憶的兩種做法（投影片第 135–136 頁）：

1. **RAG**：對過去的對話做檢索，撈出跟現在話題相關的部分，跟本講開頭的方法一樣
2. **memory tool**：用類似 compaction 摘要的結構化方式，模型察覺到「這要記住」的訊號時呼叫記憶工具存起來，存的地方可以是每次都會放進 context 的一段

**自我檢查**：一個 agent 跑了 200 輪工具呼叫，context 快滿了。分別說明刪除、滑動視窗、摘要各會丟掉什麼樣的資訊，哪一種最可能丟掉「使用者一開始說不能改資料庫 schema」這種限制？

<details>
<summary>答案</summary>

刪除丟的是被判定不再需要的工具輸出，限制條件通常不在其中；滑動視窗只留最近的內容，第一輪講的限制最先被丟掉，風險最高；摘要若有「限制條件」這個固定欄位（如 Pi 的格式），就會被刻意保留。判準：指出滑動視窗按時間丟，和「重要性不隨時間遞減」的資訊衝突。

</details>

## Coding agent：把前面全部用上

[錄影 1:33:33–1:38:58](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=5613s)

投影片第 138–143 頁用的是 [Liu 等人 2026 年分析 Claude Code 架構的論文](https://arxiv.org/abs/2604.14228)裡的總覽圖。講者說 coding agent 的核心就是 ReAct：中間那個 agent loop 是一連串工具呼叫與觀察結果。跟一般聊天最大的不同是它直接碰你的系統，有一個**執行環境**。他在圖上圈了四個地方：

**auto-approval**。agent 要執行的動作安不安全，是一般聊天不會遇到的問題。講者說大約一年前每一步都要人按允許或拒絕，現在多半不是了：由一個比較輕的模型看過目前為止的所有內容，獨立判斷這個動作安不安全。

**agentic retrieval**。呼應 Afshine 那段：coding agent 幾乎不用傳統 RAG。猜幾種你要找的寫法再用 grep 搜，效果好又快，能直接餵給推理步驟，所以你會看到 grep 到處都是。

**AGENTS.md：agent 該怎麼做事**。前面說使用者 context 是服務商塞的、你控制不了；coding agent 則讓你用 [AGENTS.md](https://agents.md/) 寫下每次 session 都要遵守的規則，把偏好固定下來。

**skills：可重用的做法**。重複的工作流程，不想每次重新描述，就寫成 skill（[Agent Skills](https://agentskills.io/)）：一個資料夾，裡面是 prompt，需要時附上要執行的工具呼叫或腳本。講者特別說 skill 通常不是從零手寫的：比較有效的做法是先把一件事從頭做到尾，再請 coding agent 把剛剛的流程整理成 skill。

### 主要的 coding agent

[錄影 1:37:40](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=5860s)

投影片第 145 頁把它們分成開源與閉源：

| 開源 | 閉源 |
|---|---|
| Codex、Pi、Hermes Agent、DeepSeek Harness（DSH） | Claude Code、Cursor、Antigravity |

講者特別推薦 **Pi**：它的 harness 很精簡，ReAct 各步驟周圍的 prompt 壓到最少，你看到的接近模型最原始的表現；也因此常被拿來在同一個 harness 下比較不同模型，他說下週（第 7 講 LLM evaluation）會看到。

**computer use**（投影片第 146 頁）：讓 agent 操作你的電腦。講者說目前效率很差，因為它要截圖、再從截圖預測下一個動作，用過的人可能會很挫折；兩講之後會看到一些可能的下一步。

**自我檢查**：同樣是「找某個函式在哪裡被呼叫」，為什麼 coding agent 用 grep 比用本講前半的語意檢索好？反過來，什麼樣的問題 grep 會失手？

<details>
<summary>答案</summary>

要找的是精確的識別字，grep 給出所有完全符合的位置，又快又不漏；語意檢索會撈到「意思相近」但不是那個函式的程式碼。grep 失手的是用自然語言描述、不知道確切名稱的問題，例如「處理使用者登入失敗的地方在哪」，這時 agent 得先猜幾種可能的寫法再搜。判準：講出「精確比對 vs 意思相近」的差別。

</details>

## 討論：多個 agent，成果與風險

[錄影 1:38:58–1:40:43](https://www.youtube.com/watch?v=nU2a2lm6vDE&t=5938s)

投影片第 148–149 頁引 Claude Code 文件裡的兩種編排方式：

- **subagent**：每個 subagent 有特定任務、彼此不溝通。用來分出不需要太多推理、可以委派的工作。講者說它有成本：每開一個都要給它自己的 context，等於多跑一整個 agent loop；所以像 Pi 這種精簡的 harness 標榜不支援或只做最小支援。
- **agent team**：subagent 變成「隊友」，有溝通管道，可以分享進度、分組合作。講者口頭稱這類多個 agent 協作的做法為 agent swarm，說它正在變多。

最後兩頁是對照。「Wins」放的是 OpenAI 2026 年 9 月 8 日的公告〈On the Navier–Stokes Millennium Prize Problem〉，講者說最近有一些數學進展就是這樣做出來的。「Vulnerabilities」放的是 OpenAI 2026 年 7 月 21 日的公告〈OpenAI and Hugging Face partner to address security incident during model evaluation〉，講者稱之為 Hugging Face 被駭事件，推薦 Black Hat 2026 年 8 月的演講與 METR 同月的報告。他用這兩頁收尾：給 agent 越多權力，能做到的事越多，暴露的弱點也越多。

## 連回你用的模型

- **做 RAG 時**：先建一份標好相關性的小評估集，算 Recall@k 和 NDCG@k，再決定要不要加 BM25 混合、HyDE 或 reranker。沒有評估集，調 chunk 大小只是猜。
- **寫工具時**：docstring 與參數名稱就是模型看得到的全部；輸出用有欄位名稱的結構。工具數量多到回答開始對不上意圖時，先考慮 tool selection，而不是再寫更長的說明。
- **組 prompt 時**：系統規則、工具定義這些固定的放最前面，時間、使用者資料、問題放後面。開頭只要多一個會變的時間戳，快取就沒了。
- **用 coding agent 時**：AGENTS.md 放每次都要遵守的規則，重複的流程做完一次後請 agent 整理成 skill；subagent 每開一個就多一份 context 成本。

## 綜合自我檢測

第 1–8 題改寫自 [2025 期末考](https://cme295.stanford.edu/exams/fall25-cme295-final.pdf)第 III 大題「Agentic LLMs」，答案在[解答 PDF](https://cme295.stanford.edu/exams/fall25-cme295-final-solutions.pdf)。第 6 題（不存在的工具）與第 8 題後半（工具回傳錯誤）2026 課堂沒有直接講，要從工具說明、router 與 ReAct 的 observe 步驟推；其餘考點這一講都有講。第 9、10 題是本文針對 2026 新段落自擬。2026 版的期末考在 12 月 9 日。

1. RAG 主要解決凍結的 LLM 的哪一個限制？（第 III.1 題）
2. RAG 裡的「contextual retrieval」指的是什麼？（第 III.2 題）
3. ReAct 框架是什麼？（第 III.3 題）
4. LLM 輸出 `find_teddy_bear(loc='Stanford')` 後，這個函式由誰執行？（第 III.4 題）
5. MCP 要標準化的是哪兩端之間的連線？（第 III.5 題）
6. 工具執行時，agent 叫了一個不存在的工具，常見的修法是什麼？（第 III.7 題）
7. 模型已有 100 萬 token 的 context window，為什麼還可能用 RAG？說出一個 RAG 特有的挑戰。（第 III.9 題）
8. 描述工具執行迴圈的三個步驟；工具回傳錯誤時會怎樣？（第 III.10 題）
9. 用本講的 harness 定義，把「tool selection 的 router」「compaction 的摘要欄位」「AGENTS.md」各歸到六項中的哪一項。
10. 一個服務每個請求都帶 3,000 token 的工具定義，快取輸入是一般輸入價格的 1/10。工具定義放在 prompt 開頭與放在使用者問題之後，這 3,000 token 的成本各大約是多少（以一般輸入價格為 1）？

<details>
<summary>第 9、10 題的判準</summary>

- 第 9 題：router 屬於「工具」（決定這次給模型哪些工具），也可以說是外圍 prompting 的一部分；compaction 的摘要欄位屬於「compaction 策略」；AGENTS.md 屬於「所有外圍的 prompt」，它也扮演跨 session 的記憶。答案不唯一，要講出理由。
- 第 10 題：放開頭且命中快取時約 3,000 × 0.1 = 300；放在每次都不同的使用者問題之後，前綴不同、吃不到快取，就是 3,000。這裡忽略第一次寫入快取的費用。
