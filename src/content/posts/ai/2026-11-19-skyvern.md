> 🌏 [English version](/posts/ai/2026-11-19-skyvern-en)

[AgentQL](/posts/ai/2026-08-21-agentql-semantic-web-extraction) 讓你用查詢描述要哪些資料，靠的是 DOM。[Midscene](/posts/ai/2026-05-23-midscene-vision-ui-automation) 走另一個極端，只看截圖。Skyvern 介在兩者之間：每一步同時看截圖和頁面上的可互動元素。它也是這一層裡少數同時給你三種用法的工具：寫程式的 SDK、一句話交代的任務，以及非工程師也能拖拉的流程編輯器。

這篇回答：**要在很多陌生網站上跑同一套流程時，Skyvern 換到什麼、付出什麼；它的 AGPL-3.0 授權對你有什麼影響。**

## Skyvern 怎麼看頁面

[官方文件](https://github.com/Skyvern-AI/skyvern/blob/main/docs/concepts.mdx)描述的迴圈是四步，這是 1.0 和 2.0 的做法（3.0 的改變在下一節）：

1. 截圖，並讀出頁面上的可互動元素：輸入框、按鈕、連結、下拉選單。每個元素標一個 ID。
2. 模型同時看截圖、元素清單和你的目標，挑下一個動作：點擊、輸入、選擇、捲動、上傳或擷取。它回傳的是清單裡的元素 ID。
3. Playwright 在 Chromium 裡執行這個動作。
4. 檢查目標達成了沒有，沒有就帶著新頁面再走一圈。

早期版本會在截圖上把每個元素框起來編號再送給模型，目前的版本已經把這個功能[標成 deprecated](https://github.com/Skyvern-AI/skyvern/blob/main/skyvern/webeye/scraper/scraper.py)。模型不能看圖時，Skyvern 只靠元素清單運作，[官方建議](https://github.com/Skyvern-AI/skyvern/blob/main/docs/developers/self-hosted/overview.mdx)複雜頁面還是用能看圖的模型。

所以「視覺型」只說對一半。Skyvern 自己在 2026 年 10 月的[部落格](https://www.skyvern.com/blog/deleting-rag-from-our-web-agent-made-it-2-3x-faster/)承認，早期的版本卡在 DOM 解析：Shadow DOM、iframe、Canvas 和各種 UI 元件庫都要逐一處理，「agent performance did not improve with better LLMs. Instead, it was bottlenecked by this DOM parsing logic」。換更強的模型也沒用，因為模型拿到的元素清單本身就不完整。

### 3.0 改成讓模型自己讀 HTML

同一篇文章介紹了重寫的 Skyvern 3.0。它不再每一步都送截圖和元素清單，而是給模型幾個工具：寫一段 JavaScript 掃 HTML、在頁面上執行動作、需要時截圖、宣告完成。廠商的數字是，截圖只占所有模型呼叫的 2.7%（原本 27%）；在約 10 萬次正式 run 的 A/B 裡，平均執行時間從 593 秒降到 262 秒，每次 run 的成本從 $0.039 降到 $0.0302。這些都是廠商自己的量測。

要注意預設值：在 Skyvern Cloud 新建的 agent 預設跑 3.0，但從 API 或 SDK 呼叫 `run_task`，[預設引擎](https://github.com/Skyvern-AI/skyvern/blob/main/docs/concepts.mdx)仍是標成 Legacy 的 1.0，要自己指定才會用 3.0。

## 三個入口

**SDK：在 Playwright 腳本裡加 AI 步驟。** [README](https://github.com/Skyvern-AI/skyvern) 的自我定位是「a Playwright extension that adds AI-powered browser automation」。`page` 物件多了 `act`、`extract`、`validate`（回傳布林值）、`prompt` 幾個方法，原本的 Playwright 動作也能加上 `prompt`：

```python
await page.click("#submit-button")                       # 一般 Playwright
await page.click(prompt="Click the green Submit button")  # 交給模型
await page.click("#submit-btn", prompt="Click the Submit button")  # 先試 selector，失敗才用模型
```

第三種寫法最實用：穩定的步驟照樣用 selector，selector 壞掉時才付一次推論的錢。這跟 [Stagehand v4](/posts/ai/2026-11-18-stagehand-v4) 鼓勵的寫法是同一個方向。Python 要裝 `pip install "skyvern[local]"` 才有這些 page 方法；只裝 `pip install skyvern` 是呼叫 Cloud API 的 client。

**任務：一句話加一個網址。** `skyvern.run_task(prompt="...")` 交給 agent 自己完成，可以附上要回傳的資料格式和錯誤代碼。

**Agent（流程）：用 block 串起來。** API 和舊文件把它叫 workflow。[block](https://github.com/Skyvern-AI/skyvern/blob/main/docs/reference/blocks.mdx) 涵蓋瀏覽器動作（任務、擷取、登入、前往網址）、資料（檔案解析、Google Sheets 讀寫）、流程控制（迴圈、條件、AI 驗證、等待）、檔案（下載、填 PDF）和通訊（寄信、HTTP 請求、等人介入）。前一個 block 的輸出可以餵給下一個。網頁介面 Studio 裡有一個 Copilot，你用白話描述工作，它幫你組出 block。這是 Skyvern 跟這一層其他 SDK 最不一樣的地方：流程可以交給不寫程式的同事維護。

agent 還有一個功能值得一提：**跑過一次就存成程式碼。** agent 成功跑完後，Skyvern 可以把它做過的動作[產生成程式碼](https://github.com/Skyvern-AI/skyvern/blob/main/docs/developers/browser-automation.mdx)，之後直接執行程式碼、不再每步問模型（`run_with="code"`）。頁面改版導致程式碼失敗時，預設會退回 agent 重新產生。這跟 Stagehand 的 observe 重播是同一個想法：推論只在第一次和出錯時付。

## 自架和 Cloud 差在哪

Skyvern 可以用 `pip install "skyvern[server]"` 加 `skyvern quickstart` 在本機跑，也可以用 Docker Compose 起完整的介面。但[官方文件](https://github.com/Skyvern-AI/skyvern/blob/main/docs/developers/production.mdx)和[定價頁](https://www.skyvern.com/pricing)寫得很清楚，有些東西只在 Cloud：

| | 自架 | Cloud |
|---|---|---|
| 帳密保管（模型只看到佔位符） | 有，也能接 Bitwarden／Vaultwarden | 有，Pro 方案起可接 1Password |
| TOTP 兩步驟驗證 | 可設 TOTP 金鑰 | 有，Pro 方案起 |
| CAPTCHA | 不解，看到就等 30 秒讓你手動解 | 會解常見的（Hobby 是 basic、Pro 是 advanced），「Solving is not guaranteed」 |
| Proxy 與地理定位 | 自己準備 | 有，Pro 方案起是住宅 proxy |
| Anti-bot 措施 | 沒有，這部分沒有開源 | 有 |

自架時有三個預設值要自己改（見 [self-hosted 文件](https://github.com/Skyvern-AI/skyvern/blob/main/docs/developers/self-hosted/overview.mdx)）：

- **遙測預設開啟**，送出的使用事件包含每個任務的起始網址，用 `SKYVERN_TELEMETRY=false` 關掉。
- **預設不擋內部網址**，agent 可能被頁面引導去連你內網的服務，要開 `ENABLE_URL_VALIDATION=true`。
- **Kubernetes manifest 沒有驗證**，文件明說不要把 cluster 暴露在網際網路上。

Cloud 按[動作](https://github.com/Skyvern-AI/skyvern/blob/main/docs/cloud/account.mdx)計費：1 credit 是 $0.001，一個 AI 動作（一次點擊、一次輸入、一次擷取）30 credits，也就是 $0.03；從程式碼重播的動作 15 credits；瀏覽器開著每小時 200 credits。[月費方案](https://www.skyvern.com/pricing)是 Hobby $29（30,000 credits）、Pro $149（150,000 credits）。粗算 Hobby 大約是一千個 AI 動作。一個流程如果在最後一步被網站擋下，前面的步驟照樣計費。不過定價頁的 FAQ 寫的是按 run 計費、不按步驟，跟文件的 credit 表對不上，實際怎麼扣要看帳單頁的用量明細，或直接問廠商。

## AGPL-3.0：先分清你是哪一種用法

Skyvern 的 repo 是標準的 [AGPL-3.0](https://github.com/Skyvern-AI/skyvern/blob/main/LICENSE)，沒有附加例外條款。README 說核心邏輯都在開源 repo 裡，只有 anti-bot 留在 Cloud；有授權問題就「contact us」，沒有公開說明能不能另外買商業授權。

AGPL 跟 GPL 的差別在[第 13 條](https://www.gnu.org/licenses/agpl-3.0.en.html)，它把「透過網路使用」也算進來：

> if you modify the Program, your modified version must prominently offer all users interacting with it remotely through a computer network (if your version supports such interaction) an opportunity to receive the Corresponding Source of your version

以下是依條文整理的事實，不是法律意見。三種常見用法的處境不同：

1. **透過 API 呼叫 Skyvern Cloud**：你沒有拿到、也沒有改 Skyvern 的程式碼，第 13 條的前提是「you modify the Program」，碰不到。
2. **自架、不修改，當成一個獨立服務，你的產品用 HTTP API 呼叫它**：第 13 條只約束修改版。你自己的程式算不算衍生作品，要看兩者結合得多緊，這是 AGPL 一般的解釋問題，Skyvern 沒有發過官方說明。
3. **修改 Skyvern，或把它的程式碼放進你的服務**：修改版讓使用者透過網路互動時，要提供對應的原始碼。注意 `pip install skyvern` 的 Python SDK 也在同一個 AGPL repo 裡，`import skyvern` 進你的閉源 SaaS 之前要先想清楚。

如果你要把它嵌進閉源產品，先問律師，或直接聯絡 Skyvern 談授權。社群也有人[在 issue 裡要求](https://github.com/Skyvern-AI/skyvern/issues/8757)改成寬鬆授權，截至 2026 年 11 月沒有官方回覆。

## 成績怎麼讀

README 和官網最常出現兩個數字，都要看條件：

- **WebVoyager 85.85%**（2025 年 1 月，Skyvern 2.0）：[廠商自測](https://www.skyvern.com/blog/skyvern-2-0-state-of-the-art-web-navigation-with-85-8-on-webvoyager-eval/)，在 Skyvern Cloud 上跑，用 GPT-4o 和 GPT-4o-mini。他們刪掉 8 個「結果已經失效」的任務，也把訂機票、訂飯店任務裡的過期日期改新。文章自己承認 WebVoyager「only captures 15 hand-picked websites」。這個 benchmark 本身的問題，例如[只會搜尋的 agent 就能拿到五成](https://arxiv.org/abs/2504.01382)，留到下一篇比較時講。
- **WebBench 64.4%**（2025 年 5 月）：README 寫成「SOTA performance」，但在 [WebBench 的排行榜](https://webbench.ai/)上，Anthropic 的 Sonnet 3.7 computer use 是 66.0%，比 Skyvern 2.0 高；Skyvern 只在需要寫入的任務（填表、送出）拿到全自動 agent 裡最高的 46.6%。而且這份 benchmark 是 [Halluminate 跟 Skyvern 合作](https://halluminate.ai/blog/benchmark)做的，作者群裡有 Skyvern 的兩位創辦人，Skyvern 和兩家 computer use agent 也都跑在 Skyvern 的基礎設施上，不算獨立評測。

使用者端的回報則提醒你速度：GitHub issue 裡有人在本機用 1.0.2 版的套件跑「登入、導航、填表」的流程，[約五分鐘](https://github.com/Skyvern-AI/skyvern/issues/4375)；2024 年也有人回報[填一張表要四分鐘](https://github.com/Skyvern-AI/skyvern/issues/1271)。3.0 和程式碼重播可能改善了這一點，但目前只有廠商自己的數字。

## 什麼時候適合

- **適合：同一套流程要在很多陌生網站上跑。** 例如到幾十家供應商的入口網站下載發票、在不同政府網站填同一份申請。每個網站各寫一支 Playwright 腳本太貴，Skyvern 的「看截圖、挑元素」不需要事先知道頁面結構。
- **適合：流程要交給非工程師維護。** block 編輯器和 Copilot 是其他 SDK 沒有的。
- **適合：要寫入、送出表單的任務。** 這是它在 WebBench 裡相對強的一塊，雖然那份評測有 Skyvern 自己參與。
- **不適合：只有一兩個你熟悉的網站。** 直接寫 Playwright 比較快、比較便宜，也比較穩。
- **不適合：需要 Firefox 或 WebKit。** 它[只支援 Chromium](https://github.com/Skyvern-AI/skyvern/blob/main/docs/developers/self-hosted/overview.mdx)。
- **不適合：每一步都在意延遲。** 一個 AI 動作就是一次模型呼叫，要等好幾秒，selector 只要幾毫秒。
- **先想清楚：** 自架版沒有 CAPTCHA 處理和 proxy，常被擋的網站等於要用 Cloud；要嵌進閉源產品，先處理 AGPL。
