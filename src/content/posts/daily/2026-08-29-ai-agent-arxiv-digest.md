## 今日總覽

今天三篇論文從三個不同角度戳破同一件事:我們用來量測與防護 agent 的工具,可能根本沒有測到、擋到它們宣稱在測、在擋的東西。Safety Does Not Compose 用形式化證明說明,只要安全監控只看單一 trajectory,面對跨多輪的攻擊,偵測率在數學上就等於瞎猜;The Guard That Cried Wolf 則從另一端證明,現有護欄機制對「合法」操作的誤拒,竟然可以只靠換一個聽起來嚇人的物件名稱操弄,跟真正的授權情境無關;BekchiAI 進一步指出,連我們拿來排名 agent 能力的準確率排行榜,量到的也不是真正決定風險的行為細節。三篇合起來是一記警鐘:評測與護欄本身,可能也需要被評測。

## 讀這篇前該知道的詞

| 詞 | 白話解釋 |
|---|---|
| Agent(智能代理) | 可以自己規劃步驟、呼叫工具、迭代執行的 AI 系統,不是一問一答的聊天機器人 |
| 護欄(Guardrail) | 在 agent 執行動作前先做核准/拒絕判斷的檢查機制,目的是擋下危險操作 |
| Trajectory(軌跡) | Agent 從接到任務到完成的一連串行動與觀察紀錄,通常是安全監控與評測的觀察單位 |
| 過度安全 / 過度拒絕(Over-safety) | 護欄把明明合法、安全的操作誤判成危險而擋下來,是護欄的假陽性 |
| ReAct Agent | 一種讓 LLM 交替「推理(Reason)」與「行動(Act)」的 agent 設計模式,是目前最常見的 agent 執行框架之一 |
| 組合性(Composability) | 把多個獨立驗證安全的元件組合起來後,整個系統是否還保有原本的安全保證;這篇證明「不一定」 |

## 論文一｜安全機制不會組合:自主 LLM Agent 的不衰減迴圈狀態

**Safety Does Not Compose: Non-Decaying Loop State for Autonomous LLM Agents**
Chenhao Wu, Haoxuan Jia, Yang Liu et al.（14 位作者，機構未在論文標明）　·　arxiv: 2608.27141

連結: [arxiv](https://arxiv.org/abs/2608.27141) · [alphaxiv](https://www.alphaxiv.org/abs/2608.27141)

### TL;DR

只要安全監控只看單一 trajectory,面對證據被拆成好幾輪的攻擊,偵測率(TPR)在數學上就等於誤判率(FPR)——形同瞎猜;作者提出 LoopHarness,讓安全狀態跨迭代持續存在,把未授權不可逆操作的期望次數壓到一個不隨迭代次數增長的常數上界。

### Read Priority

必讀 — 如果你的 agent 允許長時間背景運行、跨多輪迭代做事,這篇直接證明你現有的單輪安全監控在數學上就會被繞過,不是「還不夠嚴」的問題。

### 領域背景

目前業界主流的 agent 安全機制(從內容過濾器到軌跡監控)幾乎都預設攻擊的證據會出現在一次對話或一次 trajectory 的觀察視窗內。但 agent 現在越來越常被部署成自主迴圈:接到一個目標後,反覆探索工作、規劃、執行工具呼叫、驗證結果,並跨許多次無人值守的迭代持續累積狀態。安全狀態卻往往在下一輪 trajectory 開始時被重新初始化,這個落差過去被當成實作細節,這篇論文證明它是結構性的組合失敗。

### 中階導讀

- **問題**:想像一個 agent 被授權連續執行任務,單次看都無害的操作,但攻擊者把惡意證據拆成好幾輪、每輪都藏在監控視窗之外——就像保全每次只檢查一個人的隨身包,卻沒人記得「這個人今天已經進出七次,每次都拿走一點點」。
- **方法**:論文證明,只要監控器只看單一 trajectory,面對跨迭代分散的攻擊,不管監控器設計得多精密,偵測率在數學上就等於誤判率;而「讓風險分數隨時間衰減」這個直覺修法也不夠,因為攻擊者只需要等一個不隨迭代次數 N 增長的固定冷卻期,分數就會重置。作者提出 LoopHarness,在迴圈層級維持一個不衰減的安全狀態,並在 mediated commits 與仲裁偵測門檻下,證明未授權不可逆操作的期望次數有一個不隨 N 增長的常數上界。
- **為什麼重要**:如果你的 agent 平台允許長時間、跨多輪迭代運作,現有的單輪安全監控可能只是「看起來有防護」,實際上對這類分散式攻擊完全無效。

### 深入要點

- 核心結果:面對「證據分散在多輪」的攻擊,任何只看單一 trajectory 的監控器,TPR 在數學上等於 FPR
- 常見補救方式(風險分數隨時間衰減)也被證明不夠:攻擊者只需等待一個不隨迭代次數 N 增長的固定冷卻期
- LoopHarness 的理論上界:未授權不可逆操作的期望次數 ≤ B+m-1+m/δ_M,是不隨 N 增長的常數
- 評測協定:在 Agent-SafetyBench 上做乾淨 vs. 攻擊的配對實驗,搭配專門設計的 outer-state 攻擊套件(決定性證據只跨迭代出現)、逐模組消融實驗、自適應白盒紅隊
- Limitation:目前是形式化證明加受控評測論文,尚未有真實產品長期部署的觀察數據 ⚠️
- 落地門檻:導入 LoopHarness 需要重新設計安全監控的狀態管理層,不是換一個更強的分類器就能解決

### Reviewer 一句話評

用形式化分離定理把「trajectory-scoped 監控注定失效」講清楚是這篇最紮實的貢獻;但論文未揭露作者機構,也還沒看到工業界真實 agent loop 的落地驗證,理論優雅程度領先實務驗證進度。

### 給你的 take-away

- 如果你的 agent 允許長時間背景運行、跨很多輪迭代做事:先假設你現有的安全監控是單輪視角,重新盤點有沒有「攻擊證據被拆成好幾輪」的破口
- 如果你在設計 agent 安全架構:LoopHarness 的「狀態不隨時間衰減 + 常數上界證明」是目前最具體的修法藍圖,值得研究它的 mediated commits 設計

## 論文二｜BekchiAI:一鍵測量、觀察、控制 LLM Agent

**BekchiAI: Measuring, Observing, and Controlling LLM Agents in One Click**
Mesut Toruk（機構未在論文標明）　·　arxiv: 2608.26867

連結: [arxiv](https://arxiv.org/abs/2608.26867) · [alphaxiv](https://www.alphaxiv.org/abs/2608.26867)

### TL;DR

用 2,057 個「可驗證答案」的任務(答案來自真跑 SQL、算 DAG 排程或算封閉形式 lambda,不靠另一個 LLM 打分)證明:四個模型家族的準確率排行榜看起來接近,真正的差異藏在家族內部的行為分佈裡,聚合分數量不到。

### Read Priority

略讀 — 如果你在做 agent 評測或選型,這篇提供了一組可以直接借用的行為指標設計思路;如果你只關心研究方法論本身,單一作者、四模型的驗證規模有限,不必深讀。

### 領域背景

Agent 評測長期依賴「準確率排行榜」:任務做對就加分,不管過程。但 agentic 技能——正確排序工具呼叫、在依賴關係下規劃、判斷不可信輸入、把生成論述扎根到真實依據——這些能力上的差異,常常被單一聚合分數蓋掉。同時多數 benchmark 靠人工或另一個 LLM 當裁判打分,答案本身的正確性就有爭議空間。

### 中階導讀

- **問題**:想像兩個 agent 在同一個排行榜上都拿到差不多的準確率,但其中一個是靠瞎猜蒙對、另一個每一步都嚴謹判斷、正確處理不信任輸入——只看聚合分數,完全看不出誰比較可靠、誰比較危險。
- **方法**:BekchiAI-Benchmark 用 13 個工具使用 ReAct agent 涵蓋 7 種任務類型(算術、SQL、資安偵測、URL grounding、規劃、編排、工具政策),共 2,057 個確定性、可驗證的測試任務,答案由跑真實 SQL、算 DAG 精確排程或算封閉形式 lambda 直接算出;資安任務刻意搭配「故意不完美的簽章掃描器」,逼 agent 自己判斷而非直接複製掃描器結果。額外定義工具呼叫遵從度、URL 幻覺率與來源比對、per-model token 成本等行為指標,搭配 BekchiAI-Platform 提供即時觀測與遠端喊停能力。
- **為什麼重要**:當你要在 Qwen3.7-Max、gemma-4-31B-it、gemma4:26b、gpt-oss-120b 這類模型之間做選型判斷,單一聚合分數不夠用——真正決定能不能上線的,往往是行為指標裡的「家族內部分佈」。

### 深入要點

- 規模:13 個工具使用 ReAct agent × 7 個任務類別,共 2,057 個確定性、可驗證的測試任務
- 出題方式:SQL 任務答案來自對真實資料庫跑正式查詢、規劃任務答案來自計算 DAG 的精確排程、部分任務用封閉形式 lambda 直接算出正確答案,刻意避開「用另一個 LLM 當裁判」的做法
- 資安任務搭配故意不完美的簽章掃描器,測試 agent 是否只是複製掃描器結果
- 對比四個模型家族:Qwen3.7-Max、gemma-4-31B-it、gemma4:26b、gpt-oss-120b,論文強調的重點是家族內部差異的分佈而非單一聚合分數
- BekchiAI-Platform 提供完整 token/延遲遙測與遠端終止能力,benchmark、評測工具、平台皆公開釋出
- Limitation:單一作者論文,四模型比較樣本仍偏小,尚待更多模型與獨立團隊複現 ⚠️

### Reviewer 一句話評

用「可驗證答案 + 行為指標」取代準確率排行榜的方向正確,任務設計(尤其資安偵測配不完美掃描器)有巧思;但單一作者、四模型的比較規模有限,能否推廣到更大規模的模型陣容還待觀察。

### 給你的 take-away

- 如果你在做 agent 評測或選型:別只看聚合準確率,BekchiAI 的工具呼叫遵從度、URL 幻覺率、per-token 成本這組行為指標可以直接借用來補足現有排行榜
- 如果你在維運正式環境的 agent:BekchiAI-Platform 的遠端終止設計,是「先求可觀測、再求可控制」的具體參考做法

## 論文三｜狼來了的護欄:嚇人的字詞如何讓 Agent 護欄誤拒合法操作

**The Guard That Cried Wolf: How Scary Words Make Agent Guardrails Refuse Legitimate Actions**
Yingjie Zhang, Yuanbo Xie, Kai Chen（機構未在論文標明）　·　arxiv: 2608.27009

連結: [arxiv](https://arxiv.org/abs/2608.27009) · [alphaxiv](https://www.alphaxiv.org/abs/2608.27009)

### TL;DR

新基準 Cautious Bench 用 756 組「良性/孿生」配對(三種命名方式共 2,268 組測量配對)測試六套護欄,發現每一套都對「聽起來嚇人」的物件名稱有更高的誤拒率——只換名稱、其他條件不變,證明護欄讀的是表面字詞而非真正的授權情境。

### Read Priority

必讀 — 如果你正在部署或設計 agent 護欄,這篇直接證明過度拒絕(over-safety)不是隨機雜訊,而是可以被物件命名系統性操弄的偏誤,會實際影響任務能不能被順利執行。

### 領域背景

護欄是在 agent 執行動作前核准或拒絕的檢查機制,目的是擋下危險操作。但護欄有時會誤拒明明安全的請求,這種過度安全會直接阻礙部署。評估過度安全本身很難:在決策邊界上,授權和未授權的操作看起來很像,「安全/不安全」的標籤其實是授權政策的選擇,不是動作本身固定的屬性;而真實資料裡邊界案例本來就難蒐集、標籤也難驗證。

### 中階導讀

- **問題**:想像你請 agent 「刪除 temp_cache 資料夾」,護欄二話不說擋下來,因為「刪除」聽起來危險;但你請它「刪除 my_precious_backup_2019」,護欄反而放行,因為字面上看不出風險。護欄到底在判斷「這個操作安全不安全」,還是只在判斷「這串文字聽起來嚇不嚇人」?
- **方法**:作者打造 Cautious Bench,針對同一個授權情境只替換物件名稱(嚇人 vs. 中性 vs. 良性),做出 756 組良性/孿生配對,在三種命名方式下共 2,268 組測量配對,另外標出 40 組本質上無法判斷的邊界案例獨立處理。每筆樣本的安全/不安全標籤都由一個明訂的授權政策機械推導出來,由 build-time gate 重新驗證每個範例,不是人工逐筆打分,確保基準本身不含糊。
- **為什麼重要**:這篇證明市面上的護欄機制普遍讀的是表面文字的危險程度訊號,而不是操作在目前授權情境下是否合法——過度防禦不是隨機雜訊,而是系統性、可被物件命名操弄的偏誤。

### 深入要點

- 基準規模:756 組 Decidable 良性/孿生配對 × 3 種物件命名方式 = 2,268 組測量配對,另有 40 組 Undecidable 邊界案例獨立回報
- 測試對象:六套來自五種不同設計的護欄機制
- 核心發現(name-superstition effect):其他條件完全相同、只改變物件名稱的對照實驗中,每一套護欄都對聽起來嚇人的物件名稱有更高的誤拒率
- 標籤產生方式:每個測試樣本的標籤由 build-time gate 根據明訂的授權政策機械式重新推導驗證,不依賴人工逐筆判斷
- Limitation:論文聚焦「物件命名」這一種表面訊號操弄,語氣、指令長度等其他表面偏誤是否也有同樣效應,論文未涵蓋 ⚠️
- 落地門檻:要修正這個偏誤,護欄設計需要把授權政策真正當作判斷輸入,而不是只在文字表面做模式比對,通常需要重新設計護欄的輸入介面

### Reviewer 一句話評

Cautious Bench 用「只換物件名稱」的極簡對照設計把 over-safety 的成因釘死在讀表面字詞這一點上,實驗邏輯乾淨且有說服力;但目前只驗證了物件命名這一種操弄方式,其他觸發過度拒絕的表面訊號還有待後續研究補齊。

### 給你的 take-away

- 如果你正在部署 agent 護欄:用 Cautious Bench 的良性/孿生配對思路自己做一輪內部測試,檢查你的護欄是不是也對特定字眼(檔名、變數名稱)有系統性偏見
- 如果你在設計新的護欄機制:把授權政策明確餵給判斷模型當輸入,而不是只讓它看操作描述的文字,可能是修正 name-superstition 的第一步

## 今日收穫

之前以為 agent 安全的問題是「護欄不夠嚴」或「評測不夠難」,今天發現更根本的問題是護欄和評測量測的維度本身就設定錯了——單輪視角的監控在數學上注定漏掉跨輪攻擊,而護欄的誤拒可能只是被一個嚇人的名字騙過去,這些都不是靠加強現有機制能解決的,而是要重新設計它們在「看什麼」。
