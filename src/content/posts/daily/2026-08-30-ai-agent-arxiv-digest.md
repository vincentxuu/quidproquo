## 今日總覽

今天三篇論文從三個不同切面逼近同一件事：「Agent 記憶」不能只看相關性夠不夠。Recuris 談的是記憶怎麼自己演化——把「追蹤任務進度」跟「累積技能經驗」分開，用可定位的執行證據去修正技能庫，讓長程 agent 能持續自我改進而不被歷史拖垮；GraphMemix 談的是記憶怎麼組織——用查詢驅動長出的證據森林取代離線先做摘要或純向量相似度檢索，抓到表面不像但語意上真正相關的證據；而「When Stale Constraints Go Unchecked」是一記警鐘——就算記憶組織得再好，只要沒有專門檢查「這條記憶是不是已經過期」，agent 有七成以上的機率照樣依照被推翻的舊限制做決策。三篇合起來看，記憶系統的比較標準正在從「記得多不多、查得準不準」，往前走向「記得的東西還新不新鮮、能不能自己演化」。

## 讀這篇前該知道的詞

| 詞 | 白話解釋 |
|---|---|
| Agent（智能代理） | 可以自己規劃步驟、呼叫工具、迭代執行的 AI 系統，不是一問一答的聊天機器人 |
| 長程任務（Long-Horizon Task） | 需要跨很多輪互動才能完成的任務，歷史一長就容易掩蓋「現在到底該做什麼」 |
| 鷹架（Harness） | 驅動 agent 的程式框架——包含 system prompt、工具定義、執行迴圈，不含模型本身 |
| 技能記憶（Skill Memory） | Agent 把過去學會的可重用操作方式存下來的記憶區塊，跟單純的事件記錄不同 |
| 溯源路徑（Provenance Path） | 一筆記憶「從哪裡來、憑什麼成立」的線索；記錄本身不可竄改，但哪筆才是目前有效的可能已經變了（supersession） |
| 證據森林（Evidence Forest） | 把記憶組織成一組樹狀關聯結構而非扁平列表，讓檢索時能同時保留多條互補、可信的證據鏈 |

## 論文一｜讓 Agent 自己演化技能記憶：Recuris 把長程任務拆成進度追蹤與技能兩塊

**Recursive Experiential-Working Memory Evolution for Long-Horizon Agent Harnesses**
Zhaochen Yu, Yingcheng Wu, Zhenfei Yin et al.　·　arxiv: 2608.24876

連結: [arxiv](https://arxiv.org/abs/2608.24876) · [alphaxiv](https://www.alphaxiv.org/abs/2608.24876)

### TL;DR

Recuris 把長程 agent 的記憶拆成 Working Memory（追蹤任務進度、引導技能選擇）跟 Experiential Memory（存過去經驗），用一個固定的 Meta-Agent 把執行過程變成證據去修正 Skill Memory，形成有邊界的遞迴演化迴圈；在四個長程 benchmark、十個模型的 37 組組合中，35 組進步，tau-bench 上把 Claude Opus 5 拉到 87.9%（+15.6 分）。

### Read Priority

必讀 — 直接針對長程 agent 最痛的「歷史掩蓋任務狀態、技能誤用」問題，且有大規模跨模型、跨 benchmark 驗證，數字扎實，不是單一場景的概念驗證。

### 領域背景

遞迴自我改進（RSI）在長程任務中一直很難落地，因為隨著互動歷史增長，agent 很難從龐大的歷史裡判斷「現在該用哪個技能」，容易造成技能誤用或呼叫時機錯誤。以往做法多是把整段歷史塞進 context 或做摘要，但摘要會抹除細節，而且歷史本身通常無法直接告訴 agent「現在」該做什麼。

### 中階導讀

- **問題**：想像一個 agent 已經跑了 300 步的複雜任務，手上累積了幾十個學會的技能，卻必須在每一步決定「現在要不要用這個技能」——光看整段歷史很難判斷技能該在什麼時候用、什麼時候該淘汰。
- **方法**：Recuris 把記憶拆成兩塊——Working Memory 只追蹤「任務進度」，並用它來引導從 Experiential Memory 挑技能，讓技能呼叫只根據「現在需要什麼」而非整段歷史；執行過程本身變成結構化證據，能精準定位是哪個記憶元件出了問題。一個固定的 Meta-Agent 讀這些證據，對 Skill Memory 做「有驗證閘門」的局部更新，新的執行又產生新證據，形成一個有邊界的遞迴迴圈。
- **為什麼重要**：把 RSI 從「不斷累積、無限膨脹的歷史」變成「有邊界、可驗證的技能演化迴圈」——代表可以讓 agent 長期運作而不被自己的記憶拖垮，且改進的地方是可定位、可驗證的，不需要重新訓練整個模型。

### 深入要點

- 四個長程 benchmark、十個模型的 37 組模型-benchmark 組合中，35 組進步；tau-bench 上 GPT-5.6 Sol +17.8 分、Claude Opus 5 +15.6 分（拉到 87.9%）；SkillFlow 上 Qwen3.6-27B/35B 分別 +16.6/+13.5 分
- 互動時間拉得越長優勢越大：在最長任務上優勢擴大到 +32.2 分
- 常見長程失敗率下降最多達 80%
- 落地訊號：程式碼已開源（github.com/Gen-Verse/Recuris），非純概念驗證
- 落地門檻：核心機制依賴「驗證閘門」把關 Skill Memory 更新，若場景本身沒有穩定的任務成功訊號（reward/驗證標準模糊），閘門怎麼設計會是實際落地的難點
- Limitation：37 組模型-benchmark 組合中仍有 2 組沒有進步，論文摘要未說明是哪些組合、失效原因為何 ⚠️（需查論文內文或附錄才能確認具體條件）

### Reviewer 一句話評

把記憶拆成「進度追蹤」跟「技能庫」分開演化的設計乾淨且可解釋，大規模跨模型驗證的說服力也強；但 35/37 這種接近全勝的數字要留意 benchmark 選擇是否帶有優勢，那 2 組失敗案例也沒被進一步解釋。

### 給你的 take-away

- 如果你在做需要長時間運行、會不斷累積技能的 agent 平台（客服、RPA、coding agent）：Recuris「進度追蹤與技能選擇分離」的架構值得直接參考，尤其如果你已經有可驗證的任務成功訊號
- 如果你在設計 agent 的自我改進機制：先把「執行過程變成可定位的證據」這個子想法獨立拿來用，不需要整套 Recuris 架構，從「失敗能不能定位到具體記憶元件」開始做

## 論文二｜記憶不該只靠相似度找：GraphMemix 用查詢驅動的證據森林組織多模態記憶

**GraphMemix: Query-Aware Evidence Forests for Long-Term Multimodal Agent Memory**
Geng Li, Yuhao Wang, Dong Li, Jianye Hao, Yuxin Peng　·　arxiv: 2608.26983

連結: [arxiv](https://arxiv.org/abs/2608.26983) · [alphaxiv](https://www.alphaxiv.org/abs/2608.26983)

### TL;DR

GraphMemix 把多模態 agent 的長期記憶組織問題轉成「以查詢為中心建構證據森林」的組合最佳化問題，同時避開離線先做摘要的高成本與純向量相似度檢索容易漏掉關鍵低相似度證據的問題，在四個長期多模態記憶 benchmark 上，建立了準確率與記憶生命週期成本之間新的 Pareto 前緣。

### Read Priority

略讀 — 對做多模態 agent（影像/影片/文字混合輸入）長期記憶的團隊直接相關，但方法本身的組合最佳化與圖結構設計需要額外工程投入，對純文字 agent 平台的立即參考價值較低。

### 領域背景

多模態 agent 的長期記憶組織比純文字更難——記憶不只是文字片段，還牽涉影像、實體關係、時序等多種型態。既有做法要嘛在寫入時就先做一次昂貴的離線摘要（不管未來查詢是什麼都先做，成本高且可能摘掉之後用得到的細節），要嘛用向量相似度檢索（快但只抓得到「看起來像」的記憶，容易漏掉語意上真正相關但表面不像的證據，也容易抓進重複、矛盾的雜訊）。

### 中階導讀

- **問題**：想像 agent 記得「上週三看到一張貓咪照片」跟「上個月使用者說『我養的動物怕水』」，這兩則記憶表面上毫不相似，向量檢索很難把它們連在一起，但如果使用者現在問「我的貓會不會怕洗澡」，這兩則記憶其實都該被找出來。
- **方法**：GraphMemix 分三步走——先用多視角的「種子記憶」透過 schema 與語意關係擴展候選圖，抓到查詢相關的原始上下文；接著把「這則記憶直接支持答案」跟「這則記憶要靠關聯關係才站得住腳」分開驗證，抑制重複或彼此矛盾的資訊；最後在一個「證據預算」上限內，聯合選出一組森林狀的記憶子圖，同時保留可靠的關聯結構。
- **為什麼重要**：把記憶檢索從「一次性的相似度排序」變成「以查詢為中心動態長出的證據結構」，讓系統能撈到向量相似度會漏掉的低相似度但關鍵的互補證據，同時不必為每個記憶庫先做一次昂貴的全庫摘要。

### 深入要點

- 在四個長期多模態記憶 benchmark 上，對不同基礎模型都有提升，核心貢獻是建立準確率與「生命週期成本」（維護記憶庫、做摘要、檢索的總開銷）之間新的 Pareto 前緣——同樣成本能拿到更高準確率，或同樣準確率成本更低
- 三個模組職責分離：候選圖建構（廣度）、證據效用與啟用成本（精度，去重去衝突）、森林最佳化（在預算內選子圖）——工程上可以逐一替換或調參
- 落地門檻：需要維護一個持續擴張的候選記憶圖並實作組合最佳化求解器（森林選擇），比單純的向量資料庫檢索多一層工程複雜度
- 已開源專案頁與程式碼（github.com/ligeng0197/graphmemix），可直接檢視實作
- Limitation：論文摘要層級未提供具體提升百分比等數字，實際增益幅度需要查原文實驗章節才能確認 ⚠️

### Reviewer 一句話評

把記憶檢索明確定義成組合最佳化問題、用森林結構取代扁平相似度排序，概念上比純向量檢索更貼近多模態記憶的真實結構；但摘要層級沒有給出量化提升幅度，實際效益需要看論文內文的具體實驗數字才能判斷。

### 給你的 take-away

- 如果你在做多模態 agent（影像/影片理解、多模態客服）的長期記憶系統：GraphMemix「查詢驅動長出候選圖、再用預算選森林」的三段式架構值得深入研究其論文內文的具體實作
- 如果你的記憶庫是純文字：這篇的圖結構設計仍可參考，但先評估組合最佳化求解器的額外工程成本是否划算，對小團隊未必是最優先的投資

## 論文三｜相關不等於新鮮：Stale Constraints 揭露 agent 有七成機率照過期記憶做決策

**When Stale Constraints Go Unchecked: Budgeted Verification Failures in Inherited Agent Memory**
Kazuki Nakayashiki　·　arxiv: 2608.25553

連結: [arxiv](https://arxiv.org/abs/2608.25553) · [alphaxiv](https://www.alphaxiv.org/abs/2608.25553)

### TL;DR

當 agent 繼承一份已整理過的記憶、裡面某個限制條件早已被新記錄推翻時，agent 在有限的查證預算下平均只有約五分之一的機率會主動去查那條記憶的溯源路徑；一旦條件真的被推翻，agent 仍有 74.7%–77.3% 的機率照舊依照過時資訊做決策。

### Read Priority

必讀 — 這篇不是提出新方法，而是用嚴謹的控制實驗揭露一個所有記憶系統都可能踩到的坑：記憶的「相關性」跟「新鮮度」是兩回事，而現有系統普遍只顧相關性。

### 領域背景

長期 agent 的記憶系統通常會把歷史整理、壓縮成「已確認的限制條件」或「已知事實」存起來，查詢時只看「跟目前問題相不相關」，卻很少去查這條記憶是不是後來已經被更新的資訊推翻。這篇論文把「記錄不可竄改，但哪筆記錄才是目前有效的」（provenance vs. supersession）明確拆開來設計實驗，測試 agent 在有限查證資源下能不能發現「這條限制其實已經過期了」。

### 中階導讀

- **問題**：想像一個客服 agent 記得「這位客戶三個月前說過『不要打電話給我，只用 email』」，但客戶上週已經打電話更新偏好改回「可以打電話」。三個月前那條記錄依然存在、沒有被竄改，只是已經不是目前有效的規則——agent 如果沒有額外花力氣去查「這條規則後來有沒有被推翻」，就會一直照過期規則行動。
- **方法**：作者設計實驗，固定每個 agent 只有「兩筆記錄」的查證預算：一種是 agent 自己決定要查哪兩筆（native allocation），另一種是研究者介入，把其中一個名額硬性分配去查「關鍵溯源路徑」（最可能發現限制已被推翻的線索）或隨機一筆記錄，藉此比較差異。
- **為什麼重要**：這篇量化證明了一件容易被忽略的事——現有記憶系統普遍只做「相關性」比對，沒有做「這則記憶是不是已經過期」的新鮮度／取代檢查，而且 agent 自己不會主動花額外力氣去查這件事，除非系統設計上強制它去查。

### 深入要點

- Agent 在「限制條件已陳述」的情況下，只有約 1/5 的機率會主動查該限制的溯源路徑
- 當限制真的已被新記錄推翻，agent 自己選擇查證對象（native allocation）時，在主要實驗、換句話重複實驗、跟另一個獨立領域測試中，做出「過時但一致」決策的機率分別高達 77.3%、74.7%、74.7%
- 強制把一個查證名額分配去查「關鍵溯源路徑」，能讓「符合目前有效記錄」的決策比例提升 +74.0、+72.7、+61.3 分，六個模型全數正向
- 論文主動揭露並修正了一個瑕疵：其中一個獨立領域測試場景後來被發現有時間邏輯矛盾，作者做了修正重跑（先在外部存證再執行），修正後仍是 +73.3 分（六個模型中五個正向，第六個模型本身查證命中率已是零，無從再改善）——這種主動揭露並公開重跑的透明度在 agent 評測論文裡不常見
- Limitation（作者自陳）：研究者介入分配查證名額的做法「不是一套排程演算法」，只是用來量化「若知道關鍵路徑，能救回多少」的理論上限，不代表系統自己就能找到這條關鍵路徑 ⚠️
- 落地訊號：單一作者研究，完整資料與時間戳證明已存到 Zenodo（doi:10.5281/zenodo.22117197），可驗證性做得比多數論文更嚴謹

### Reviewer 一句話評

拿「provenance 不可變、但 supersession 會變」這個乾淨的概念框架去量化記憶系統的盲點，控制實驗設計嚴謹、還主動揭露並修正自己發現的瑕疵，透明度值得肯定；但目前只驗證了「知道關鍵路徑」的理論上限，並未提出實際可行的偵測機制，落地仍需要後續工作。

### 給你的 take-away

- 如果你在做任何會累積、繼承歷史記憶的 agent（客服、個人助理、企業知識庫）：先假設你的記憶系統目前完全沒有「新鮮度／推翻檢查」，盤點高風險的限制條件類記憶（權限、偏好、合規規則）有沒有被動地只依賴相關性檢索
- 如果你在設計記憶系統的架構：這篇提示的方向是「幫每筆記憶標記溯源路徑，並對高風險類型的記憶強制做一次溯源查證」，而不是假設檢索到最相關的記錄就等於是最新的記錄

## 今日收穫

之前以為記憶系統的比較標準主要是「檢索準不準、記得多不多」，今天發現一個更容易被忽略的維度是「新鮮度」——就算記憶檢索系統把「最相關」的記錄完美找出來，如果那筆記錄已經被更新的資訊推翻，agent 照樣有七成以上的機率做出錯誤決策。相關性跟新鮮度是兩個獨立的軸線，Recuris 跟 GraphMemix 都在優化「找得對、組織得好」，但如果沒有像「Stale Constraints」提醒的那樣去查「這還算數嗎」，再強的檢索系統也可能穩定地給出過期答案。
