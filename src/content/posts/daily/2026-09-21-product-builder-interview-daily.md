## 今日主題

Product Sense 面試最常見的失敗模式,不是候選人講不出功能點子,而是看到「使用者成長停滯」這種模糊的問題描述,就立刻跳進「我會加這個功能、那個功能」的清單模式——完全跳過了「問題到底出在哪個環節」這一步。面試官真正想看的,是你能不能先把一個籠統的業務症狀,拆解成可以驗證的使用者行為假設,再從假設回推該做什麼。

這個主題在面試中重要,是因為它區分了「會列功能的產品人」跟「會定位問題的產品人」——後者才是面試官在找的那種人,因為現實世界裡功能點子從來不缺,缺的是知道該把資源投在哪個環節。

## 核心框架速記

### CIRCLES 框架

拿到一個開放式產品設計題時,用這六步結構化回答,避免漏掉關鍵環節:

| 步驟 | 內容 | 面試時要做的事 |
|------|------|--------------|
| **C**omprehend | 理解情境 | 問清楚:這個產品是給誰的?商業目標是什麼(成長、營收、留存)? |
| **I**dentify | 定義使用者 | 快速分群(新使用者 vs. 老使用者、輕度 vs. 重度使用者),選一群當主要對象 |
| **R**eport | 報告使用者需求 | 針對選定的使用者群,列出他們的核心痛點與未滿足需求 |
| **C**ut | 篩選並排優先序 | 從需求清單中選 1-2 個最值得解的問題,說明為什麼不選其他的 |
| **L**ist | 列出解法 | 針對篩選出的問題,發散提出 3-5 個可能方案 |
| **E**valuate | 評估取捨 | 用一致的標準(使用者價值、開發成本、策略契合度)比較方案 |
| **S**ummarize | 總結建議 | 收斂成一句清楚的推薦,並說明下一步怎麼驗證 |

**面試時的用法**:CIRCLES 的價值不在於背誦六個字母,而在於逼自己不要跳過「定義使用者」跟「篩選優先序」這兩步——這正是候選人最常為了趕時間而省略、卻也是面試官最看重的兩步。

### 使用者問題框架(現況→痛點→根因→機會)

當題目給的是「某個指標停滯」而非「設計一個新功能」時,先用這個四層框架定位問題,再套用 CIRCLES 找方案:

1. **現況**:這個指標的定義是什麼?停滯是相對什麼基準(去年同期、目標值、競品)?
2. **痛點**:把指標拆進漏斗,找出哪一個環節的轉換率或行為量在下滑或停滯
3. **根因**:對停滯的環節提出 2-3 個假設(產品問題、市場問題、使用者群組成變化),並說明怎麼用數據或訪談驗證
4. **機會**:只針對驗證過的根因提方案,不要對還沒驗證的假設直接開發功能

**面試時的用法**:被問「某個指標卡住了,你會怎麼辦」時,先講你會怎麼拆解定位問題(現況→痛點→根因),再進 CIRCLES 的方案階段——這樣面試官會看到你有紀律,不會一聽到症狀就開始開藥方。

## 今日練習題

### 題目

「你是一家生鮮外送 App 的 PM。過去兩季,新使用者簽約數持續以穩定速度成長,行銷團隊的獲客漏斗表現良好。但週活躍使用者數(WAU)已經連續兩個季度持平,沒有跟著新使用者成長而上升。你的主管問你:『我們明明一直在拉新,為什麼活躍使用者沒有跟著漲?你要怎麼查、打算怎麼做?』」

(來源:自擬,情境設計參考 Meta「如何提升 Facebook Marketplace 互動率」與 Capital One 產品面試「客戶留存/活躍度停滯」題型)

### 拆解思路

1. **釐清問題**:先問——WAU 的計算口徑是什麼(登入算不算活躍,還是要有下單行為)?新使用者簽約後的第一週轉換率有沒有變化,還是問題出在老使用者流失加速抵銷了新使用者貢獻?兩季前有沒有發生任何產品或市場端的變動(定價調整、擴張新城市、競品進場)?
2. **定義使用者**:把使用者拆成三群分別檢查——「新簽約但從未真正下單」的使用者(啟動失敗)、「曾經活躍但近期停止使用」的使用者(流失)、「持續活躍」的使用者(健康基本盤)。WAU 持平背後,可能是這三群的比例正在惡化式地變動,而不是單純「大家都變得比較不活躍」。
3. **結構化分析**:用使用者問題框架把 WAU 停滯拆進漏斗——先看新使用者啟用率(簽約 7 天內是否完成首次下單)有沒有下滑,再看已啟用使用者的複購週期有沒有拉長。如果啟用率正常但複購週期變長,問題在留存端;如果啟用率本身在下滑,問題在新使用者體驗端,而不是行銷漏斗品質。
4. **提出方案**:針對驗證出的根因用 CIRCLES 發散方案——若是啟用率下滑,聚焦在首次下單體驗(例如新使用者專屬品項推薦、降低首購門檻);若是複購週期拉長,聚焦在喚回機制(例如個人化補貨提醒、針對常購品項的到期通知)。不對兩個環節同時下藥,先集中資源驗證影響較大的那個。
5. **定義成功**:主要指標鎖定在被驗證為問題根源的那個漏斗環節(例如新使用者 7 天內首購率,或既有使用者 30 天內複購率),護欄指標是客單價與整體 GMV,確保優化啟用或留存的過程中沒有犧牲訂單品質。

### 範例回答(面試時可以這樣講)

> **問題釐清與定位**:「我會先確認 WAU 的計算口徑,以及這兩季有沒有發生任何產品或市場端的變動——因為『拉新持續成長但活躍持平』有兩種完全不同的病因:可能是新使用者根本沒有真正被啟用,也可能是老使用者正在流失、抵銷了新使用者的貢獻。這兩種情況需要完全不同的對策,所以我不會急著提方案。」
>
> **結構化分析**:「確認之後,我會把使用者拆成新簽約未下單、曾活躍已流失、持續活躍三群,分別看漏斗數據。如果我發現新使用者 7 天內首購率本身就在下滑,那問題出在啟動體驗——可能是首購品項不吸引人,或流程摩擦力變高;但如果首購率正常、只是複購週期從兩週拉長到一個月,那問題出在留存端,代表產品本身沒有建立起讓使用者想回來的固定使用習慣。這兩種情況我會分別對應到不同的功能方向,而不是同時做十件事。」
>
> **成功定義**:「假設數據顯示問題出在複購週期拉長,我會把主要指標訂在『30 天內複購率』,護欄指標是客單價跟整體 GMV,確保我推的喚回機制(比如個人化補貨提醒)不是靠低價促銷硬拉回購買,而是真的讓使用者覺得產品有持續價值。我也會設一個時間點——如果三個月內複購率沒有明顯改善,代表我對根因的判斷可能有誤,要回頭重新拆解漏斗。」

### 自我核對清單

用這張表檢查你的回答有沒有漏掉關鍵點:

| 核對項目 | 有提到? |
|---------|---------|
| 先問清楚指標定義與異常發生的時間點,而非直接假設原因 | |
| 把使用者拆成不同群組(新使用者/流失使用者/活躍使用者)分別檢查 | |
| 用漏斗拆解定位問題環節,再對驗證過的根因提方案 | |
| 方案聚焦在單一驗證過的環節,而非同時對多個假設下藥 | |
| 成功指標對應到根因所在的漏斗環節,並搭配護欄指標 | |
| 加分項:提到用真實產品案例佐證「行為數據挖出關鍵洞察」的方法 | |

## 今日案例

**Slack:從使用者行為數據裡挖出「2000 則訊息」這個活化門檻**

Slack 早期分析使用者行為數據時發現,一個團隊只要在使用 Slack 的過程中累積發送滿 2000 則訊息,長期留存的機率就高達 93%——這個數字不是隨便挑的里程碑,而是團隊真正把日常溝通搬進 Slack、形成習慣的訊號。這個洞察直接改變了 Slack 的產品優先序:onboarding 設計的目標不再是「教會使用者所有功能」,而是想盡辦法讓團隊儘快、儘量自然地跨過這條 2000 則訊息的門檻——包括匯入既有的 email 對話紀錄、鼓勵團隊把更多既有頻道(如客服、行銷)搬進來,增加訊息自然發生的場景。

**面試連結**:這個案例是「使用者問題框架」裡「根因驗證」這一步的教科書等級示範——與其憑直覺猜測使用者為什麼留下來,不如像 Slack 一樣直接從行為數據裡找出真正能預測留存的門檻,再把產品資源(尤其是 onboarding)全部押注在讓使用者儘快跨過那條線。回答「你會怎麼提升活化率」這類問題時,可以直接引用這個案例說明「先找到那個關鍵行為門檻,再設計產品去催化它」的思路。
