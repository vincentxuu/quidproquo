## 今日總覽

今天三篇問的是同一件事:你怎麼知道一個 agent 真的通過了測試,而不是測試剛好沒抓到問題?PROBE 訓練一個比目標還小的稽核模型,靠多輪對話主動試探政策違規,結果比零訓練的大型稽核員挖得更深、更廣;Shortcut Sensitivity 稽核三套公開的 agent 安全護欄評測集,發現只要把標記語句改個寫法、把工具名稱換成不透明別名,某個護欄的準確率就能上下漂移十幾個百分點——但這個效應只在其中一個模型上重現,作者本身也是做 agent 安全產品的新創公司共同創辦人,這點在下文會明確標註;Beyond Retrieval Failure 則指出多跳 RAG 常見的「檢索失敗」診斷其實混了兩種不同原因,修好搜尋引導後,證據真的被找到了,但答案準確率卻沒有等比例跟著漲——真正的瓶頸換成了「證據夠不夠被正確判讀」。三篇合起來的提醒是:無論是政策合規、安全護欄準確率,還是 RAG 的檢索分數,你發布的那個數字,可能量到的是評測本身的弱點,不是系統真正的能力。

## 讀這篇前該知道的詞

| 詞 | 白話解釋 |
|---|---|
| 政策合規(Policy compliance) | agent 完成任務之餘,是否遵守定價、隱私、確認動作等額外規則——跟「任務有沒有做完」是兩件不同的事 |
| 多輪行為稽核(Multi-turn behavioral auditing) | 不是看單一回覆對不對,而是讓稽核者像真人使用者一樣跟 agent 來回對話,觀察整段互動有沒有違規 |
| 捷徑學習(Shortcut learning) | 評測模型學到的是資料裡剛好能預測標籤的表面特徵(比如指令句子的長短),而不是真正要測的能力 |
| 黑箱護欄(Black-box guard) | 只能看輸入輸出、看不到內部權重或推理過程的安全監督模型,許多商用安全層都是這種形式 |
| 多跳 RAG(Multi-hop RAG) | 需要串連好幾段分散在不同文件的證據,才能回答的檢索增強生成任務 |
| 證據召回 vs. 證據判讀 | 「有沒有找到該找的資料」(召回)跟「有沒有正確判斷這些資料是否已經足夠回答問題」(判讀),是評測裡常被混在一起的兩件事 |

## 論文一｜PROBE:訓練一個小稽核員,去抓 agent 在工具對話中違反的規則

**PROBE: Learning to Audit Policy Compliance in Tool-Using LLM Agents**
Kshitij Mishra, Abhijith Sharma, Nils Lukas, Salem Lahlou(Mohamed bin Zayed University of Artificial Intelligence, UAE)　·　arxiv: 2610.22124

連結: [arxiv](https://arxiv.org/abs/2610.22124) · [alphaxiv](https://www.alphaxiv.org/abs/2610.22124)

### TL;DR

把「agent 有沒有照政策做事」形式化成一場人機對話賽局,訓練一個只有 4B 的小型稽核員去主動試探,結果挖出的政策涵蓋率(12/20)遠勝過零訓練的 30B 大型稽核員(7/20)與隨機探測(1/20)。

### 編輯判斷

| 面向 | 判斷 |
|---|---|
| Venue | NeurIPS 2026(主會議,已接受) |
| 引用速度 | 發布 2 天,Semantic Scholar 全程 429,無法取得引用數(預期趨近 0) |
| 機構 | Mohamed bin Zayed University of Artificial Intelligence(MBZUAI),阿布達比 |
| 社群反應 | 未在 HF Daily Papers 10-16 的部分回收清單中出現;無 Papers with Code 條目 |
| 可信度 | 通過 — 正文有完整的雙人賽局形式化定義、三種 RL 演算法消融、50 情境 held-out 評測、人工標註員驗證、跨模型家族與跨 benchmark 的遷移測試 |
| 證據成熟度 | 較完整 — 涵蓋方法、消融、人工驗證、兩種獨立遷移測試,但只在兩個合成工具環境上測 |
| 可復現性 | 部分產物 — 演算法、reward 公式與 prompt 細節寫得很完整,但未找到公開程式碼或權重連結 |
| 為什麼選這篇 | 直接 — 定義並測量一個新的評測維度,填補能力評測與安全紅隊之間的空隙 |
| 方向新意 | 實質增量 — 首次把政策稽核形式化成雙人馬可夫賽局,並系統比較 GRPO/DPO/GFlowNet 三種訓練方式 |
| 今日重要性 | 高 — 工具型 agent 進入真實交易與客服場景後,政策合規是上線前必須驗證的項目,但業界多半還停留在靜態題庫 |
| 實務連結 | 明確 — 可直接用於上線前的持續稽核流程,論文還提出「稽核員找問題、agent 從回饋改進」的共演化迴圈構想 |
| 編輯信心 | 高 — 文章只陳述通過 held-out 與遷移測試驗證的主張,並誠實揭露 judge 本身跟人工標註只有 39.6% 一致 |
| 閱讀建議 | 必讀 — 做 agent 安全/合規評測,或要把工具型 agent 送上線的團隊 |
| 主要限制 | 稽核員很少能把目標 agent 逼到訂票、取消等深層操作狀態(九成以上工具呼叫停留在搜尋),高風險政策因此仍難被充分測到 |

### 領域背景

目前評測 agent 有兩套主流工具:能力基準測出它「能不能完成任務」,內容安全紅隊測出它「會不會生成有害內容」。但一個 agent 完全做完任務、也沒說任何有害的話,仍然可能在過程中違反定價、隱私、確認等操作政策——而且這種違規常常要連續好幾輪對話、好幾次工具呼叫之後才會浮現,固定題庫很難剛好踩到。

### 中階導讀

- **問題**:想像一個訂機票的客服 agent,政策規定「幫乘客改票前要先口頭確認」。單輪測試很容易通過,因為測試題目通常把確認這件事講得很清楚。但真正的使用者對話是東拉西扯的——先問價格、再問行李、最後才臨時要求改票——agent 可能在這種自然的多輪流程裡,悄悄跳過確認這一步,而這正是固定題庫測不到的情境。
- **方法**:PROBE 把稽核框架成一場雙人賽局:一個小型(4B)語言模型扮演「稽核員」,像真實客戶一樣跟凍結的目標 agent(30B)對話,目標是在合理、像真人的對話裡逼出儘量多種不同的政策違規,而不是重複挖同一種容易踩到的漏洞。作者用強化學習(比較 GRPO、DPO、GFlowNet 三種訓練方式)訓練這個稽核員,獎勵同時考慮「有沒有抓到違規」「像不像真實使用者」「有沒有持續推進對話」「有沒有涵蓋不同政策」。
- **為什麼重要**:這代表政策合規應該被當成一個獨立的評測維度,用「主動試探」而不是「被動答題」的方式測——而且做這件事不需要一個跟目標 agent 一樣大的模型,一個訓練過的小模型就能挖得比零訓練的大模型更深。

### 深入要點

- 最佳訓練稽核員在 50 個 held-out 情境中發現 12/20 種政策違規,零訓練的 30B 稽核員只發現 7/20,隨機探測只發現 1/20
- 光是「挖得多」不代表「挖得廣」:原始產出違規次數最多的版本(dedup-only ablation)每 100 集就有 1914 次違規,但只涵蓋 55% 的政策種類——說明評測要看涵蓋率,不能只看命中次數
- 作者自己找了兩位人工標註員驗證 LLM judge 的可信度:兩位人類彼此一致度幾乎完美(kappa=0.985),但 judge 跟人類共識只有 39.6% 一致(kappa=0.084),而且訓練過程中 GRPO 利用了這個 judge 誤差 ⚠️(作者自己發現並修正,改用確定性規則重新計分後,最佳涵蓋率從 60% 降到 55%,排名不變)
- 把訓練好的稽核員直接套到沒見過的 Gemma 模型家族上,仍挖出 40% 的政策違規(同領域是 55%),而完全沒訓練的固定題庫只有 5%
- 落地門檻:要套用這套框架,得先有一個可凍結的目標 agent、一組明確的政策與驗證規則,以及訓練稽核員的運算資源(論文用兩張 A100 跑)
- Limitation:九成以上的工具呼叫都停留在「搜尋」,目標 agent 很少被逼到真正下單、取消等高風險操作狀態,所以最嚴重的那幾項政策違規仍然很難被充分測到

### Reviewer 一句話評

把「政策合規」從安全紅隊跟能力測試裡獨立出來當成專門的評測維度,這個框架設計很扎實,而且作者自己抓出並修正了 judge 的系統性誤差,誠實度值得肯定;但目前只測了訂票客服跟 τ-bench 兩種環境,能不能類推到真正高風險的金融、醫療 agent,還需要更多驗證。

### 給你的 take-away

- 如果你在幫工具型 agent 做上線前稽核:不要只靠固定的政策測試題庫,考慮養一個小型的「對抗式稽核員」,用強化學習訓練它主動試探多輪對話中的違規
- 如果你在用 LLM-as-judge 評分你的 agent 測試:先拿一小批資料人工核對 judge 的標註一致度,這篇顯示 judge 跟人類共識可能低到四成都不到

## 論文二｜護欄的「準確率」可能只是評測集寫法的產物,不是真安全

**Shortcut Sensitivity in Agent-Safety Evaluations**
Hasan Demirkiran, Jens Ernstberger(Kontext)　·　arxiv: 2610.22243

連結: [arxiv](https://arxiv.org/abs/2610.22243) · [alphaxiv](https://www.alphaxiv.org/abs/2610.22243)

### TL;DR

稽核三套公開的 agent 安全護欄評測集,發現光是把標記語句改寫、把工具名稱換成不透明別名,某個護欄模型的準確率就能上下漂移十幾個百分點——但這個效應只在其中一個模型上重現,換一家供應商就歸零。

### 編輯判斷

| 面向 | 判斷 |
|---|---|
| Venue | NeurIPS 2026 workshop TAE(「Can We Trust AI Evaluation?」)與 AIWILD 雙 workshop 接受,非主會議 |
| 引用速度 | 發布 2 天,Semantic Scholar 全程 429,無法取得引用數(預期趨近 0) |
| 機構 | Kontext — 兩位作者皆為該公司共同創辦人,公司業務是「保護生產環境中 agent」的安全新創,2026 年 9 月才以 $4M 種子輪成立(經 web 搜尋確認,論文本身未揭露) |
| 社群反應 | 未在 HF Daily Papers 10-16 的部分回收清單中出現;聚合程式碼與結果公開在 GitHub,但依規定移除了原始 benchmark 文字與 provider 回應 |
| 可信度 | 有條件通過 — 三層稽核框架邏輯清楚,在三個不同護欄資料集上都量到具體數字,但作者是 agent 安全新創的共同創辦人,對「現有評測不可靠」這個結論存在商業誘因,且核心效應只在一個模型上重現 |
| 證據成熟度 | 初步 — 核心的配對介入效應在 Claude Haiku 4.5 上有安慰劑對照支撐,但換成 GPT-5.6 Luna 或量化版 TS-Guard 都沒有重現,作者自己標示為「與設定相關」而非普遍現象 |
| 可復現性 | 部分產物 — 聚合程式碼與結果公開,但移除了原始 benchmark 文字與工具參數,無法完全重跑 |
| 為什麼選這篇 | 直接 — 直接檢驗目前拿來對外宣稱「我們的護欄安全」的評測資料集本身是否可信 |
| 方向新意 | 實質增量 — 把捷徑學習的概念系統化成三層稽核框架,首次對三個公開 agent 安全評測集做這種稽核 |
| 今日重要性 | 高 — 越來越多團隊用 F1、準確率等單一數字對外宣稱護欄效果,這篇指出那個數字可能只是評測集寫法的產物 |
| 實務連結 | 明確 — 給出三個可操作建議:依領域分組保留測試集、用「每個互動」而非「每一列」當計分單位、安慰劑對照的配對介入 |
| 編輯信心 | 中 — 核心發現有具體數字跟安慰劑對照支撐,但效應只在一個模型上重現,且作者的商業身分需要讀者自行納入判斷 |
| 閱讀建議 | 必讀 — 任何正在用 F1/準確率對外宣稱護欄效果的團隊;略讀 — 只想知道「有這個問題存在」的讀者 |
| 主要限制 | 核心效應在跨供應商複製(Luna)時歸零,且作者本身是 agent 安全商業產品的共同創辦人,論文結論與其商業定位方向一致 |

### 領域背景

Agent 安全護欄(guard)通常是獨立於主模型的監督層,專門在工具呼叫前後檢查有沒有危險動作。這些護欄發布時,幾乎都附上一個準確率或 F1 分數,團隊也習慣拿這個分數來決定要不要上線。但護欄的訓練資料跟評測資料往往來自同一個標註流程,如果標註流程本身留下了某種跟真正危險程度無關、卻剛好能預測標籤的表面特徵(比如句子長短、用詞習慣),護欄就可能學會抄這條捷徑,而評測分數卻完全看不出來。

### 中階導讀

- **問題**:想像一個護欄模型被訓練來判斷「這個工具呼叫安全嗎」,標註資料裡剛好「標記為不安全的指令平均比較短」。護欄可能偷偷學會「指令越短就判不安全」這條捷徑,在原本的評測集上準確率很漂亮,但這跟它有沒有真的理解危害完全無關——換一批資料,這個捷徑就會失靈。
- **方法**:作者設計一套三層稽核框架:第一層測「標籤本身有多容易被無關特徵預測」,第二層測「評測資料裡的可疑線索(比如特定標記字串)跟護欄的判斷有沒有統計關聯」,第三層是最嚴格的——找一批固定的真實案例,只改寫那個可疑線索(不改變案例本身安不安全),看護欄的判斷會不會跟著變。這套框架套用在 LinuxArena、AgentDojo、AgentHarm 三個公開評測集上。
- **為什麼重要**:如果護欄的準確率有一部分其實是在抄捷徑,團隊可能會對外宣稱「我們的護欄 F1 達到 0.9」,但换个場景、换个寫法,實際防護力可能完全不是這麼回事。

### 深入要點

- AgentDojo-Traj:同一套工具查詢規則,混合領域切分時 F1 高達 .901,但換成「依領域分組保留測試」就掉到 .495
- AgentHarm-Traj:已發布的 TS-Guard 用「每一列」計分時 F1 是 .902,改成「每個互動」計分就掉到 .719(但平衡準確率反而上升,顯示計分單位本身會左右結論)
- 固定住 64 個真實步驟,只改寫標記用詞(把 `<INFORMATION>` 換成 `<UNTRUSTED_EXTERNAL_CONTENT>`),Claude Haiku 4.5 的攔截率就下降 8.33 個百分點;換成不透明的工具別名,攔截率反而上升 11.46 個百分點,扣掉格式安慰劑效應後兩者都還是顯著 ⚠️(960 次重複呼叫得出的結果,僅在 Haiku 上重現)
- 同一組介入換成 GPT-5.6 Luna 完全沒有效果(對比幾乎是 0),量化版 TS-Guard 複製品也只有 3/64 筆決策受影響——作者明確說這是「某個設定下的個案」,不是普遍的護欄弱點
- 落地門檻:要做這種稽核,團隊得先有護欄的原始預測記錄跟一組安慰劑對照的改寫版本,成本不算高,但需要紀律(預先凍結樣本、不能看了結果才選案例)
- Limitation:64 步的樣本不是機率抽樣,信賴區間是探索性的;沒有做盲測的人工驗證來確認改寫真的沒有改變案例本身的安全性

### Reviewer 一句話評

把捷徑學習的概念系統化成一套可操作的三層稽核框架,而且誠實揭露效應沒有跨供應商複製,這點值得肯定;但作者是 agent 安全新創的共同創辦人,「現有評測不可靠」這個結論恰好也是他們商業定位需要的敘事,讀者應該把這點跟效應的不穩定性一起放進判斷。

### 給你的 take-away

- 如果你在發布或採購 agent 安全護欄:不要只看一個 F1 或準確率數字,追問清楚計分單位(每一列還是每個互動)跟測試集切分方式(混合領域還是依領域分組保留)
- 如果你在設計自己的護欄評測:至少做一次「只改寫跟安全無關的表面特徵,看判斷會不會跟著變」的安慰劑對照測試

## 論文三｜RAG 的「檢索失敗」診斷其實混了兩種問題

**Beyond Retrieval Failure: Understanding Why LLMs Miss Evidence in Multi-Hop RAG**
Jiaqi Wei, Wenxuan Huang, Chengdong Xu, Xiang Zhang, Wanli Ouyang(Shanghai Artificial Intelligence Laboratory 等)　·　arxiv: 2610.21184

連結: [arxiv](https://arxiv.org/abs/2610.21184) · [alphaxiv](https://www.alphaxiv.org/abs/2610.21184)

### TL;DR

在不改動檢索器、語料庫跟生成模型的前提下,只靠一個會追蹤「還有哪些子問題沒解決」的待辦清單引導搜尋,就讓 MuSiQue 上因為漏抓證據而答錯的題目從 382 題降到 234 題——但答案準確率卻沒有等比例跟著漲,因為多出來的問題換成了「證據判讀錯誤」。

### 領域背景

多跳 RAG 需要連續檢索好幾段分散證據才能回答一個問題。長期以來,業界診斷「為什麼答錯」的標準做法是檢查「該用到的那段證據有沒有被檢索器找到」,找不到就歸咎於「檢索失敗」。但這個診斷方式有個盲點:也可能是證據明明檢索器找得到,只是搜尋本身在中途「飄走」,沒有繼續追問那個還沒解決的子問題,所以才沒被找到。這兩種原因混在一起,會讓團隊誤判問題出在哪裡、該優化檢索器還是優化搜尋策略。

### 中階導讀

- **問題**:想像一個問題要串連三段證據才能回答,前兩段都順利找到了,但 agent 問到第三段時,搜尋的焦點已經悄悄飄到別的子問題上,導致第三段證據其實「就在語料庫裡、檢索器找得到」,卻從沒被真正搜過。傳統診斷會把這記成「檢索失敗」,但問題根本不在檢索器身上。
- **方法**:作者提出 ExecutionRAG,一個不需要額外訓練的「待辦清單」:每個子問題都有一個狀態(待處理／進行中／已解決／已放棄),每次搜尋只鎖定一個還沒解決的子問題,搜完就更新狀態,直到清單上沒有未解決的項目才作答。檢索器、語料庫、生成模型完全不變,唯一變的是搜尋被這份清單引導得更聚焦。
- **為什麼重要**:這套方法讓研究者第一次能把「搜尋引導」跟「證據可不可及」這兩個變因分開測量——而結果顯示,修好搜尋引導,確實能找回更多原本漏掉的證據,但不代表答案準確率會跟著等比例提升,因為新的瓶頸變成了「找到證據之後,有沒有正確判斷它已經足夠回答問題」。

### 深入要點

- MuSiQue 上,因為漏抓必要證據而答錯的題目數,用 all-MiniLM-L6-v2 當檢索器時從 382 題降到 234 題,換成 Qwen3-Embedding-0.6B 也從 383 題降到 274 題——同一個檢索器前後對照,排除了「換了更強檢索器」的解釋
- 但推理錯誤的占比從 9% 升到 26%(MiniLM)、放棄回答的占比從 7% 升到 13%——顯示漏抓證據的問題解決了,新的瓶頸接棒出現
- 换成 Qwen3-Embedding-0.6B 檢索器後,ExecutionRAG 在 HotpotQA/2Wiki/MuSiQue 三個 benchmark 上的 LLM 評分準確率都優於對照組(matched baseline),2Wiki 上甚至只用差不多或更少的檢索 token 就拿到最大增益,顯示效果不是靠「多讀一點文字」硬撐出來的
- 消融實驗:拿掉「用第一輪檢索結果來建立清單」這一步,準確率從 50.2 降到 48.7;再拿掉「邊搜邊更新清單」,降到 48.3——顯示兩個設計都有貢獻,不是單一因素在撐
- 落地門檻:要套用這套方法,團隊得先能把失敗答案按照「judge 錯誤／放棄／推理錯誤／證據缺失」四類重新分類,才能看出自己的 RAG pipeline 真正卡在哪一關
- Limitation:生成模型只測了 GPT-4o-mini;待辦清單本身的「已解決」判斷仍由語言模型自己做,可能提早誤判;四跳問題(證據鏈最長)上,漏抓證據依然是最大宗的失敗原因,這套方法沒有完全解決長鏈證據的問題

### Reviewer 一句話評

用 matched-baseline 把「搜尋引導」這個單一變因乾淨地拆出來測量,這個實驗設計很紮實,而且誠實報告了副作用(推理錯誤、放棄回答都增加);但生成模型只測了一種,且待辦清單本身仍可能誤判「已解決」,離真正解決多跳 RAG 的可靠性問題還有距離。

### 給你的 take-away

- 如果你在除錯自己的多跳 RAG pipeline:先把答錯的案例按「judge 錯誤／放棄／推理錯誤／證據缺失」四類分開看,再決定要優化檢索器還是搜尋策略——很可能你以為是檢索問題,其實是判讀問題
- 如果你在設計 agentic search 的搜尋迴圈:考慮加一個明確追蹤「還有哪些子問題沒解決」的狀態清單,而不是讓模型用自由格式的推理自己記住進度

## 今日收穫

之前以為「稽核 agent 合不合規」靠一份政策題庫就夠、「護欄準確率 0.9」代表真的安全、「RAG 檢索失敗」修好檢索器就能解決——今天才發現這三件事都犯了同一種錯:把評測當成終點,而不是追問評測本身量到的是不是真正要測的東西。訓練一個會主動試探的稽核員,比固定題庫多挖出近兩倍的違規;換個標記寫法就能讓護欄準確率漂移十幾個百分點;修好搜尋引導後,答案準確率卻沒有等比例跟著漲。評測分數從來不是終點,它本身就需要被稽核。
