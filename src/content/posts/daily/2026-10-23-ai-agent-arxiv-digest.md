## 今日總覽

今天三篇論文圍繞同一個現實：Agent 已經能自主執行會改變真實狀態的動作，但業界在「信任它多少」這件事上明顯補課中。第一篇測出前沿模型完成任務的能力遠遠超前「先備份再動手」的意識——六個模型平均完成 86.1% 的任務，卻只有 15.2% 會在動到可能需要復原的狀態前先備份。第二篇指出把部署政策寫進 prompt 不夠用：允許使用的工具仍可能在違規的情境下被呼叫，而訓練一個獨立的守門模型能明顯壓低這個漏洞。第三篇把視角轉到持久記憶本身——如果 Agent 之間要共享知識庫，怎麼確定沒有被偽造或污染的資訊混進去，這篇提出用形式化證明而非純經驗測試來保證完整性，但受限於本次研究工具限制，只能核對到摘要層級的證據。三篇合起來的訊息很一致：Agent 能做的事已經走在「做得安全」前面。

## 讀這篇前該知道的詞

| 詞 | 白話解釋 |
|---|---|
| Agent（智能代理） | 可以自己規劃步驟、呼叫工具、迭代執行的 AI 系統，不是一問一答的聊天機器人 |
| 備份意識（Backup Awareness） | Agent 能不能認得出「這個動作會改掉之後可能需要的狀態」，並在動手前先保留一份 |
| 政策守門模型（Policy Guard） | 獨立於主要任務 Agent 之外，專門檢查每個工具呼叫是否符合部署政策的模型 |
| 攻擊成功率（ASR） | 對抗測試裡，違規請求真正得手的比例；數字越低代表守門機制越有效 |
| 持久記憶（Persistent Memory） | Agent 跨任務、跨對話保留下來、之後還能被自己或其他 Agent 讀取的記憶 |
| 機器驗證（Machine-Checked Proof） | 用像 Lean 4 這種證明助理逐步檢查過的數學證明，不是人工推導後自己宣稱正確 |

## 論文一｜Agent 完成任務很厲害，但備份意識只有一成五

**Back Up Before You Regret: Measuring Backup Awareness and Automating Backup in Coding Agents**
Xu Li, Simon Yu, Minzhou Pan et al.（Northeastern University + UC Berkeley + University of Chicago + UIUC）　·　arxiv: 2610.28934

連結: [arxiv](https://arxiv.org/abs/2610.28934) · [alphaxiv](https://www.alphaxiv.org/abs/2610.28934)

### TL;DR

205 個從 X.com、GitHub、Stack Overflow 上真實「早知道就該備份」案例改編的執行任務裡，六個前沿模型平均完成 86.1% 的任務，卻只有 15.2% 會在動到可能需要復原的狀態前先備份；外掛的 BackUpper 備份層能覆蓋所有該備份的動作，復原相似度達 92.2%，每個任務只多花 $0.014。

### 領域背景

Coding agent 已經能自主完成多步驟、會修改真實環境的任務——改設定檔、跑腳本、呼叫外部 API。現有 harness（Claude Code、Codex 等）大多只備份工作區或透過內建工具做的編輯，一旦狀態是透過外部工具或遠端服務改掉的，就完全沒有保護。過去的研究多半關注「事後怎麼復原」，但這篇指出：原始狀態一旦被真正銷毀，事後復原常常已經無法挽回。

### 中階導讀

- **問題**：想像一位資深工程師在升級相依套件前，會先把環境複製一份備份。現在把這件事交給 Agent 做，它完成任務的能力很強，但會不會也想到「這個動作之後可能需要復原」這一步？
- **方法**：作者從 X.com、GitHub、Stack Overflow 上蒐集 205 個使用者明確表示「後悔沒有先備份」的真實案例，改寫成可執行、多輪互動的任務，構成 RegretBench。針對「備份意識難以預測」這個問題，BackUpper 把每一次工具呼叫都當成「值得備份」來處理：常見操作（如刪除）用規則直接處理，複雜或模糊的操作（如跑一段腳本）交給一個獨立的輕量子代理判斷，備份過程完全在主 Agent 的對話歷史之外進行。
- **為什麼重要**：結果顯示「任務完成率」跟「備份意識」是兩件不相關的事——完成度最高的模型不代表最會先備份。這代表光是讓模型更強不會自動解決這個問題，需要額外的保護層。

### 深入要點

- 六個前沿模型平均任務完成率 86.1%，但備份率只有 15.2%；表現最差的是 Codex 裡的 GPT 5.6-Sol（5.9%）與 Hermes 裡的 DeepSeek V4-Pro（2.9%）
- BackUpper 覆蓋 RegretBench 裡所有該備份的動作，復原狀態與原始狀態平均相似度 92.2%
- 成本與效率：每任務只多花 $0.014，比主 Agent 自己做備份少用 7 倍 token、延遲低 31.7%
- 個人化：給定使用者偏好時，BackUpper 判斷「這個動作值不值得備份」跟人工標註的一致度達 84.5% F1
- 自我改善：子代理的備份判斷可以被蒸餾成規則，30 個任務後規則覆蓋率翻倍
- 落地門檻：BackUpper 是訓練無關的 plug-in，接到既有 harness 上即可，不需要重新訓練模型 ⚠️（核心數字為作者自測，尚待外部團隊在非自建基準上複現）

### Reviewer 一句話評

把「備份意識」從模糊的工程習慣變成一個可測量、可比較模型的具體指標，而且解法同時兼顧成本與個人化偏好，是這個方向少見的完整工作；但 205 個任務全部來自公開討論的案例，覆蓋的風險類型可能還是偏向使用者「事後抱怨最大聲」的那一類，日常不會被公開討論的細微備份需求未必被涵蓋。

### 給你的 take-away

- 如果你的團隊在部署會動真實環境的 coding agent：直接檢查目前的 harness 有沒有覆蓋「外部工具／遠端服務」這塊，這篇指出五個主流 harness 裡沒有一個做到
- 如果你在設計 Agent 自動化流程：不要假設模型越強就越會自己想到備份，這篇數據顯示完成率跟備份意識並不相關，需要獨立的保護層

## 論文二｜把規則寫進 prompt 擋不住違規工具呼叫，要訓練一個獨立守門員

**AgentPolicyForge: From Executable Environments to Policy Benchmarks and Adaptive Guards**
Chao Shang, Wanyu Du, Yi Zhang, Sandesh Swamy（AWS AI Labs）　·　arxiv: 2610.28989

連結: [arxiv](https://arxiv.org/abs/2610.28989) · [alphaxiv](https://www.alphaxiv.org/abs/2610.28989)

### TL;DR

把部署政策直接寫進任務 Agent 的 prompt，仍有 13–15% 的違規工具呼叫被放行，還誤擋了約 9% 的正常請求；用執行環境產生的政策基準訓練出的獨立守門模型，把攻擊成功率相對降低 40–44%，誤擋也更少。

| 引用速度 | 發布 3 天，Semantic Scholar 查詢多次遭 rate-limit（429），尚無法取得引用數字 |
| 機構 | AWS AI Labs（作者 email 為 @amazon.com） |
| 社群反應 | HF Daily Papers 未上榜；未查到獨立 GitHub repo 或 Papers with Code 項目 |

| 可復現性 | 部分產物 — PolicyGym 構建方式在論文附錄詳述，但未查到公開 code 或資料集連結 |

| 方向新意 | 實質增量 — 用可執行環境把「參數、資源、情境是否合規」變成可訓練、可評測的資料，而非單純工具黑白名單 |
| 今日重要性 | 高 — 企業部署 Agent 最常見也最難防的違規正是「用對了工具、用錯了情境」 |
| 實務連結 | 明確 — 任何要在 Agent 部署裡加「業務規則守門」的團隊都能直接參考這套資料生成流程 |
| 編輯信心 | 高 — 40–44% 的相對降幅有多組對照實驗與外部基準支持 |
| 閱讀建議 | 必讀 — 做 Agent 治理／護欄的團隊；略讀 — 只關心模型能力本身的讀者 |
| 主要限制 | 核心評測集中在作者自建的 PolicyGym 情境，跨企業真實政策的泛化程度僅靠兩個外部基準交叉驗證，樣本仍有限 |

### 領域背景

Agent 部署通常會定義「哪些工具、在什麼條件下可以用」的政策——例如轉帳工具只能用在金額低於某個上限的情況。問題是「允許使用某個工具」跟「這次呼叫是否合規」是兩件事：同一個被允許的工具，換一組參數、換一個情境就可能違規。過去常見做法是把政策寫進任務 Agent 的 prompt，期待它自己判斷，但這篇指出這個做法本身就會漏。

### 中階導讀

- **問題**：想像一間公司允許員工使用公司信用卡，但金額超過某個門檻就需要額外授權。只告訴員工這條規則，不代表他每次刷卡都會記得檢查金額——需要有人在旁邊真的檢查每一筆交易。
- **方法**：AgentPolicyForge 用可執行環境產生政策案例：先把政策綁定到具體的工具與資源，用攻擊者角色生成測試請求，實際執行工具呼叫並記錄結果，再用執行結果（不是單靠語言判斷）標註是否違規。這些案例一部分拿來訓練一個獨立的守門模型，一部分留著做人工覆核過的測試集（PolicyGym：698 個訓練情境、254 個獨立測試情境，橫跨 10 個政策家族）。訓練過程可以反覆進行——攻擊者檔案庫更新後，守門模型再重新訓練一次。
- **為什麼重要**：結果顯示，光靠把政策寫進 prompt，前沿 Agent 仍有 13–15% 的違規請求會被放行，而且還誤擋了大約 9% 的正常請求；換成一個訓練過的獨立守門模型，攻擊成功率能相對降低 40–44%，誤擋的情況也更少。這代表政策治理不該只靠「告訴模型規則」，而是需要一個獨立、可持續訓練的檢查層。

### 深入要點

- 政策提示基準：前沿任務 Agent 在威脅情境裡仍放行 13–15% 違規工具呼叫，並誤擋約 9% 正常請求
- 最終守門模型配置：相對政策提示，攻擊成功率降低 40–44%，同時誤擋更少
- 消融：更新攻擊檔案庫（相較於固定檔案庫）能進一步降低領域內攻擊成功率；用驗證器產生的標籤訓練同樣有效
- 外部驗證：在 VIOLA 這個外部基準上做違規偵測測試，並在 PolicyGuardBench 上確認效能沒有因為換場景而掉太多
- 較小 backbone 複製：Qwen3-8B 這個較小模型重現了同樣的訓練效果，代表方法不只在大模型上才有用
- 落地門檻：要重現這套流程，需要先有可執行的環境把政策綁定到具體工具與資源，對多數團隊是不小的工程投入 ⚠️（核心降幅為作者自測，PolicyGym 情境由作者自建，外部驗證範圍有限）

### Reviewer 一句話評

把「政策合規」從單純的工具黑白名單，變成可執行、可訓練、可持續更新的資料與模型，而且用兩個外部基準交叉驗證過，是這個方向少見的紮實工程工作；但核心評測集中在自建的 PolicyGym 情境，真實企業政策的多樣性能不能被同樣涵蓋，還需要更多跨組織的驗證。

### 給你的 take-away

- 如果你的團隊在設計 Agent 的工具使用政策：不要只把規則寫進 prompt 就當作完成防護，這篇顯示光靠 prompt 仍有 13–15% 的違規請求會過
- 如果你在建 Agent 護欄系統：AgentPolicyForge 的「用可執行環境產生政策案例」流程可以直接參考，比純手寫規則更能覆蓋「參數對但情境不對」這類難防的違規

## 論文三｜持久記憶被污染怎麼防？PerMIT 想用數學證明把關

### 領域背景

Agent 的持久記憶——跨任務、跨對話保留下來的資訊——如果來源是環境或其他 Agent（而不是使用者直接輸入），理論上就有被注入假資訊或惡意內容「污染」的風險。這個風險在多個 Agent 共享同一個知識庫時會被放大：一旦有毒資料混進去，後續讀取這份記憶的 Agent 都可能被影響。過去的防禦多半是經驗性的過濾或偵測，PerMIT 想做的是用可機器檢查的數學證明，而不是「測試過沒出事」來保證安全性。

### 中階導讀

- **問題**：想像一群員工共用一份內部維基，任何人（或任何外部系統）都能提交內容。你要怎麼確保提交的內容在被當作「事實」使用之前，真的有被人確認過，而不是隨便寫寫就生效？
- **方法**：根據摘要，PerMIT 只信任兩種輸入——使用者直接打字輸入的內容，以及經過一個「確認關卡」核准的內容。所有來自環境、工具、其他 Agent 的資訊都要先經過這個關卡，關卡可以是人工、LLM 驗證器，或兩者都用。作者在一個稱為「有限記憶介面」的設計上，用 Lean 4 證明了兩條定理，保證沒被關卡確認過的資訊不會影響敏感動作。由於每次確認都是對「確切內容」的記錄，當很多使用者都確認過同一筆內容，它就能變成「社群已確認」，之後不用每個人都重新驗證。
- **為什麼重要**：如果這個機制如摘要所述運作，代表「多個 Agent 安全共享記憶」這件事可能不需要靠經驗性過濾器，而是能有數學上的保證；社群規模越大，把關的效率反而可能越高。但這些主張目前只查證到摘要層級，讀者應自行查閱全文核對細節。

### 深入要點

- 核心機制：只信任使用者直接輸入與經過確認關卡核准的內容，兩條完整性定理保證未確認資訊不會影響敏感動作，且用 Lean 4 做機器驗證
- Trojan Hippo 測試：使用自我驗證與輕量驗證器，記錄零次攻擊成功 ⚠️（本次僅查證到摘要敘述，未核對完整實驗設定）
- τ²-bench 模擬：最多 90 個自主 Agent 共同建構知識庫，未見有害資訊被直接污染進去，且產生的知識能改善新 Agent 在未見任務上的表現 ⚠️（同上，未核對完整設定）
- 作者提出的「co-scaling」性質：在明訂假設下，社群規模越大，污染被放行與誤刪良性知識的風險都會下降，而每個使用者的驗證負擔不會上升 ⚠️（理論主張，本次未核對完整證明與模擬細節）
- 落地門檻：形式驗證本身需要團隊有能力維護 Lean 4 證明，對多數工程團隊是額外的門檻

## 今日收穫

之前以為「Agent 能不能被信任」主要是一個模型能力問題——等模型夠聰明，自然會知道什麼時候該小心。今天發現真正卡住的是三個獨立的工程缺口：完成任務的能力已經遠遠超前備份意識（15.2% 的備份率對比 86.1% 的完成率）；把規則寫進 prompt 沒辦法擋住「工具對、情境錯」的違規，需要獨立訓練的守門模型；而持久記憶要真正安全，可能需要形式化證明而不只是經驗測試——只是這個方向目前能查證的證據還停在摘要層級。Agent 做得到的事，已經走在「做得安全」前面。
