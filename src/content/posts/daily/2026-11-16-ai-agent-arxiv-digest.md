## 今日總覽

今天三篇從三個不同層次處理同一個卡點：Agent 記憶系統看起來已經有一堆方案在搶著解決「記得住」，但三篇分別指出，光是記得住遠遠不夠。MAPE 用程式演化搜遍整個記憶系統設計空間後發現，真正能跨系統搬得動的提升，來自「保留原始對話當佐證」跟「依查詢意圖重新組織證據」這兩個具體設計，而不是更花俏的檢索演算法。DISCERN 則指出，在企業場景裡「檢索」其實已經接近解決——四個近乎飽和的召回指標證明這點——真正卡住的是「解析」：這個查詢指的是哪個實體、哪個時間點的事實才是現在有效的、以及該不該直接回答。WikiTrace 則揪出記憶系統的陰暗面：記憶不只會沒幫上忙，還會讓 Agent 在原本能解決的任務上失敗，因為錯誤的「教訓」沒有辦法被回頭檢查。三篇合起來看，記憶系統的成熟度正在從「怎麼存更多、搜更準」，往「怎麼知道現在該信哪一條、該用哪個版本、該不該開口」移動。

## 讀這篇前該知道的詞

| 詞 | 白話解釋 |
|---|---|
| 程式演化（Program Evolution） | 讓 LLM 像寫程式一樣持續修改、測試、再修改一套系統的程式碼，每一輪都根據上一輪的實測結果決定怎麼改 |
| 雙時態資料（Bi-temporal Data） | 同時記錄「這件事何時被寫進系統」跟「這件事在現實中何時成立、何時被取代」兩條時間軸，讓舊資料不會因為新資料進來就消失 |
| LLM 評審團（LLM-as-a-Judge Council） | 用多個不同的模型分別打分再多數決，取代單一模型評分，降低單一模型偏袒自己風格輸出的風險 |
| 記憶誘發退化（Memory-Induced Degradation） | Agent 本來不靠記憶就能解決的任務，加上記憶之後反而失敗——通常是因為記住了一條錯的、或用錯場合的「教訓」 |
| 軌跡（Trajectory） | Agent 執行一個任務時，一步步做了什麼動作、看到什麼結果的完整紀錄，是記憶系統用來提煉「教訓」的原始素材 |

## 論文一｜記憶系統怎麼設計最有效？讓程式自己演化出答案

**Discovering Effective Agent Memory Designs through Program Evolution**
Xinheng Ding, Seyyed Saeid Cheshmi, Ziyang Zhang et al.（University of Minnesota、Stevens Institute of Technology）　·　arxiv: 2611.17068

連結: [arxiv](https://arxiv.org/abs/2611.17068) · [alphaxiv](https://www.alphaxiv.org/abs/2611.17068)

### TL;DR

用程式演化從「什麼都不存」開始搜尋記憶系統設計，搜出的系統在 LongMemEval 上比人工設計的最強基準線（RAG）高 11 個百分點（77.00% vs 66.00%），關鍵不是演算法多花俏，而是「保留原始對話」加「依查詢意圖組織證據」這兩個設計，後者移植到五套現有記憶系統全部都有提升。

### 領域背景

記憶系統的建構、組織、維護與檢索過去多是「人工設計」決定的，近期開始有程式演化方法自動發現演算法與結構，但大多把搜尋範圍限制在某個既有架構上微調。MAPE 想知道從最簡單的起點放手讓它演化，會不會找到人沒想過的設計組合。

### 中階導讀

- **問題**：想像你要設計一套「客服 Agent 要記住客戶說過什麼」的記憶系統，手上有十幾種現成做法（摘要式、圖譜式、向量檢索式……），每種都有人宣稱效果最好，但你不知道哪個設計選擇才是真正決定效果的關鍵，還是只是換個包裝。
- **方法**：MAPE 把記憶系統拆成 build（把對話變成可查的記憶）、retrieve（依查詢取出證據）、compose（把取出的證據整理成給模型看的上下文）三個可被程式改寫的階段，從「完全不存記憶」這種最簡單的起點開始，讓一個 LLM 提案者反覆修改程式、拿固定的評測集打分、再根據失敗模式診斷下一輪怎麼改；準確率優先的搜尋跟「準確率+服務成本」聯合搜尋各跑一輪，看兩種目標會演化出什麼不同的系統。
- **為什麼重要**：搜出來的系統不是更複雜的黑箱，而是收斂到兩個清楚、可解釋、可以直接搬到別的系統上的設計選擇——這代表記憶系統的效能瓶頸可能比想像中更集中，不需要重新發明整套架構。

### 深入要點

- LongMemEval（Qwen3-30B 作 serving backbone）：MAPE-ALME 77.00% vs 最強基準線 RAG 66.00%（+11 個百分點）；聯合目標版本 MAPE-PLME 72.25%，服務呼叫數比 ALME 少 90%
- LoCoMo（GPT-4.1 mini）：MAPE-ALCM 87.94%，超越所有基準線的每個子類別；聯合目標版本 MAPE-PLCM 85.18%，服務成本只要 ALCM 的 28%
- 摘要指稱的「12% 絕對準確率增益、35% 服務成本」是跨兩個基準的綜合說法，實際數字依基準與 backbone 不同而有落差（見上）
- 兩個可遷移設計模式：①保留原始對話作為可檢索證據，避免摘要抽取時漏掉細節 ②依查詢意圖路由到專門的組合模板（Query-Routed Scaffolding）；後者移植進 Mem0、A-Mem、LightMem、SimpleMem、Zep 五套系統，準確率全部提升
- 兩種搜尋目標演化出不同的運算分配：只看準確率的版本持續往「LLM 建構記憶」砸運算；準確率與成本聯合的版本把運算從建構期移到查詢期的選擇性處理
- Limitation：論文承認「35%／28% 服務成本」只計入推論期的 LLM／embedding 呼叫成本，沒有把搜尋演化過程本身的運算開銷算進對比

### Reviewer 一句話評

用演化搜尋取代人工設計、再系統性做移植驗證，這個研究設計本身值得信任；但讀者要記得「12% 增益、35% 成本」是摘要層級的概括說法，實際落地前得看清楚自己的基準與 backbone 落在論文的哪個設定格。

### 給你的 take-away

- 如果你在自建記憶系統：別急著加新檢索演算法，先檢查自己有沒有做到「保留原始對話」跟「依查詢意圖路由組合」這兩件事，論文顯示這兩個改動比換檢索演算法更直接有效
- 如果你在評估現成的記憶框架：拿這篇的兩個設計模式當檢查清單，問框架的作者有沒有做到，而不是只看它用了哪個聽起來很潮的演算法名稱

## 論文二｜企業 Agent 記憶卡住的不是檢索，是解析

**DISCERN: Preserve at Write, Resolve at Read for Persistent LLM-Agent Memory**
Chirag Ahuja, Vladislav Tanov, Ramcharan Kakarla et al.（Amazon）　·　arxiv: 2611.15729

連結: [arxiv](https://arxiv.org/abs/2611.15729) · [alphaxiv](https://www.alphaxiv.org/abs/2611.15729)

### TL;DR

在 Amazon 自建的企業銷售場景基準上，一個最普通的 RAG 讀取器召回率已經飆到 0.93-0.98，但答對率只有 0.806；DISCERN 把「寫入時完整保留、讀取時才解析」分開處理後，棄答判斷的 F1 衝到 0.924（次佳 0.802），答對率提升到 0.861，差距主要來自實體解析（0.800，其餘方法沒人超過 0.40）。

### 領域背景

企業 Agent 記憶系統過去多半被當成檢索問題處理——用更好的向量模型、更細的摘要策略去「找到對的那段話」；但在長期累積的企業資料裡，更大的麻煩常常是同名實體、數值隨時間更新、或壓根沒有答案時該不該開口，這些不是靠檢索排序能解決的問題。

### 中階導讀

- **問題**：想像一個銷售顧問 Agent 記了半年的客戶紀錄，某天被問「Zephyron 現在的營收多少？」——問題是公司裡同時存在「Zephyron Cloud Solutions」跟「Zephyron Cloud Systems」兩家客戶，名字很像但完全是兩家公司，一個月前的營收數字也早被最新一次拜訪更新過。檢索系統很可能兩段都找得到、也都「有關」，但答案該挑哪一段、現在該用哪個數字、如果真的分不清楚該不該老實說「不確定」，檢索排序本身回答不了。
- **方法**：DISCERN 遵守一條規則——寫入時保留，讀取時才解析。寫入階段把每次互動的事實疊進一個只增不改的雙時態圖：容易混淆的實體用「相似名稱」連結但永不合併，被更新的數值軟性標記為過期但不刪除，歷史跟最新值都還能被查到。讀取階段不是單次相似度查詢，而是一個會逐層試探的導覽迴圈——先看有幾個候選實體存活，再看這個實體現在有效的值是什麼，最後依照候選數量、是否有效值、是否被更新過這三個條件，決定要回答、更新舊答案、要求使用者澄清，還是老實棄答，四選一，每次只會觸發剛好一種行動。
- **為什麼重要**：大部分記憶系統的評測指標只看「有沒有把對的證據找出來」，而企業場景裡「找到證據」跟「給出正確答案」中間還有一段沒人認真測過的落差——這篇把這段落差直接拆出來獨立評測，證明就算檢索已經做到 0.93-0.98 的近飽和水準，答對率跟棄答判斷照樣可以輸一大截。

### 深入要點

- 八個基準方法在 ENT-310 的「保有」「時效」兩個召回指標上全部落在 0.93-0.98，幾乎飽和，但答對率最強基準線只有 0.806——證明瓶頸不在檢索
- DISCERN 在「實體解析」這個子項拿到 0.800，其餘八個基準方法沒有一個超過 0.40，是整體答對率領先的主要來源
- 棄答判斷（該不該誠實說不知道）F1 0.924，次佳基準只有 0.802——論文另外設計了 100 題刻意「答不出來」的題目來測這項
- 零調參搬到公開的 LoCoMo 語料（情境換成私人多輪對話，不含企業實體混淆設計），DISCERN 答對率仍以 0.663 對 0.638 領先，顯示這不是只為 ENT-310 特化出的結果
- 消融實驗：拿掉讀取時導覽工具（tools-off），答對率從 0.89 直接掉到 0.33——證明效果主要來自「讀取時怎麼查」，不是存儲結構本身
- Limitation：核心基準 ENT-310（10 位銷售人員、50 家目標公司、310 題）是 Amazon 自建的合成資料，目前未公開程式碼或資料，外部無法獨立驗證樣本建構是否存在對自家方法有利的設計

### Reviewer 一句話評

把「記憶問題」從檢索重新框定成解析，這個問題重新定義做得乾淨，用來支撐的消融跟跨基準遷移測試也夠紮實；但核心基準不公開、沒有程式碼，讀者目前只能把 0.861／0.924 這兩個數字當成「這個團隊在自家合成資料上的受控結果」，等外部能拿到資料重跑才能真正確認。

### 給你的 take-away

- 如果你的 Agent 記憶系統服務的是企業內部資料（客戶、合約、內部文件）：先檢查自己的系統有沒有「同名實體會不會被誤判成同一個」「舊數值被覆蓋後還能不能查回來」這兩個具體弱點，這往往比換一個更貴的檢索模型更值得優先修
- 如果你在設計 Agent 的答題策略：參考這篇的四選一治理閘門（答／更新／澄清／棄答），至少讓系統在分不清楚的時候有一個明確的棄答出口，而不是預設永遠給答案

## 論文三｜別只信任記憶：證據鏈記憶降低 Agent 因記憶變笨的機率

**Don't Just Trust Your Memory: Evidence-Linked Memory Reduces Memory-Induced Degradation in LLM Agents**
Yukyeong Lee, Yumin Choi, Jinheon Baek et al.（KAIST AI、DeepAuto.ai）　·　arxiv: 2611.14320

連結: [arxiv](https://arxiv.org/abs/2611.14320) · [alphaxiv](https://www.alphaxiv.org/abs/2611.14320)

### TL;DR

分析發現，Agent 原本不靠記憶就能解決、加了記憶後卻失敗的案例裡，52% 可以追回一條被遵循的「教訓」，其中多數教訓本身就是錯的；WikiTrace 讓每條教訓都連回原始執行軌跡可供查核，在八個測試套件平均把退化率從 6.5% 壓到 4.5%，整體表現比不給軌跡的「純教訓」版本再高 3.2 個百分點。

### 領域背景

Agent 記憶系統過去多半假設「教訓一旦被提煉出來就是可信的」，各種方法比的是怎麼把過去的成功或失敗軌跡提煉得更精煉、更好檢索；但教訓是從一次只有成功或失敗二元標籤的軌跡裡推斷出來的，推斷本身就可能猜錯，而現有系統通常只把教訓本身交給 Agent，軌跡原文反而被丟棄。

### 中階導讀

- **問題**：想像一個 Agent 在玩文字冒險遊戲，學到一條教訓寫著「看到檯燈任務，只要東西放到亮著的燈旁邊就算完成」。這條教訓是從一次成功的軌跡裡提煉出來的，但其實那次成功的真正原因是別的步驟，「放在燈旁邊」只是恰好同時發生、跟成功無關的巧合。下次 Agent 照做這條教訓，反而把一個原本不靠記憶就能解決的任務搞砸了——而且因為教訓的措辭聽起來很合理，Agent 自己也沒有辦法發現這條教訓是錯的。
- **方法**：WikiTrace 把記憶拆成三層，從上到下用連結串起來：每條「教訓」是最精簡的一句建議，往下連到一份「診斷摘要」解釋這次軌跡為什麼成功或失敗，再往下連到完整的「原始軌跡」本身。遇到新任務時，Agent 先拿到所有教訓，但只有在某條教訓資訊不夠、跟別條教訓衝突，或這條教訓來自一次失敗的軌跡時，才會動用終端工具沿著連結往下查，去原始軌跡裡核對這條教訓到底站不站得住腳，查完才決定要不要照做。
- **為什麼重要**：這篇把「記憶是不是真的有幫助」拆成兩半分別量測——Gain（記憶把原本解不開的任務變成解得開）跟 Regression（記憶把原本解得開的任務搞砸）。一般評測只看整體準確率，平均起來很容易讓 Regression 被 Gain 蓋過去，看起來記憶總是在幫忙，但其實同時也在悄悄搞砸一部分任務，沒有人注意到。

### 深入要點

- 歸因分析：在三次重複測試裡「不靠記憶都能解決，加了記憶就失敗」的案例中，52% 能追回一條被遵循的記憶項目，其中最常見的原因（佔 20%）是這條教訓本身根本是錯的
- 八個測試套件平均：WikiTrace 90.2% vs No Memory 79.5%（+10.7 分），vs 只給教訓不給軌跡的 Insights Only 87.0%（+3.2 分）
- 退化率（Regression）：既有記憶方法平均跟「完全不用記憶重跑一次」差不多甚至更高，WikiTrace 把這個數字從 6.5% 壓到 4.5%
- 單項最大跳幅在 PlanCraft Challenge（Minecraft 合成任務）：No Memory 56.3% → Insights Only 73.0% → WikiTrace 81.3%，顯示「能回頭查證據」在高難度任務上的邊際效益最大
- 分析顯示 Agent 在難度較高的任務上更常主動下鑽查原始軌跡，而且下鑽後改變原計畫的次數，跟最終效能提升幅度正相關
- Limitation：退化率是降低而非消除（4.5%），論文也沒有量化「下鑽查軌跡」這個額外步驟帶來的工具呼叫次數與延遲成本

### Reviewer 一句話評

把「記憶到底有沒有幫助」拆成 Gain 跟 Regression 分開報，這個評測設計本身就該是記憶系統研究的標準配備，歸因分析也做得具體誠實；但論文沒有把「下鑽查證據」這個額外步驟的延遲與工具呼叫成本量化，讀者在考慮導入前要自己評估這筆額外開銷划不划算。

### 給你的 take-away

- 如果你已經在生產環境用技能庫或教訓庫累積 Agent 經驗：不要只看整體準確率有沒有上升，額外拆出「原本解得開、加了記憶後反而解不開」這個子集合單獨追蹤，你可能已經在付退化成本而不自知
- 如果你在設計記憶系統的資料結構：至少讓每條教訓能連回它的原始執行記錄，就算不做到 WikiTrace 完整的三層架構，一個「這條教訓是哪次執行得出的」的指標欄位，也能讓之後的除錯跟人工稽核容易很多

## 今日收穫

之前以為記憶系統的進步方向是「存更多、搜更準」，今天發現三篇論文各自在說同一件更底層的事：程式演化搜遍整個設計空間後找到的關鍵不是演算法，而是「別丟掉原始證據」跟「依意圖組織」兩個具體選擇；企業場景裡檢索早就接近飽和，真正卡住的是解析——這個查詢問的是誰、現在哪個版本才算數；而就算教訓看起來言之有理，沒有辦法回頭查核的教訓本身就可能是錯的。記憶系統成熟的下一步，不是記得更多，是要知道什麼時候該信、該查、該閉嘴。
