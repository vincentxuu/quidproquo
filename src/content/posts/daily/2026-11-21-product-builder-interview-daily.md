## 今日主題

Technical PM 面試常考的不是「你會不會寫程式」，而是工程團隊丟出一個限制時，你能不能分清楚「這真的做不到」還是「只是其中一種做法做不到」，並能在 PM 的高度上把技術取捨講清楚、講出理由。今天用兩件事練這個能力：一是 RFC（Request for Comment）／設計文件這種跨團隊決策機制，什麼時候該寫、該寫多細；二是一道 Meta 技術 PM 面試常見的架構取捨題——替一個媒合平台設計產品架構，在媒合速度與媒合品質之間做明確選擇。

## 核心框架速記

### 框架一：RFC 該不該寫，看複雜度與依賴，不是看規模

工程團隊常見的誤區，是把 RFC 當成「大公司才需要」的官僚流程，或是「每件事都要寫」的教條。實務上判斷標準很簡單：

| 情境 | 建議 |
|---|---|
| 小改動、沒有跨團隊依賴 | 不用寫，直接做 |
| 中等複雜度、有一些依賴 | 考慮寫一份，篇幅跟著複雜度走，很多欄位可以留空或跳過 |
| 高風險、跨團隊、依賴多 | 一定要寫，列明確的 approver，要他們「簽名」同意或提異議 |

不想寫完整 RFC 時，最小可行的決策記錄是 ADR（Architecture Decision Record）的四個欄位：**Status**（提案中／已採用／已棄用）、**Context**（為什麼現在要做這個決定）、**Decision**（決定了什麼）、**Consequences**（這個決定帶來的好處與代價）。四欄位寫完，日後有人問「這個為什麼這樣設計」，答案就在文件裡，不用重新開會。

### 框架二：PM 做架構取捨的四步驟

技術 PM 被問到「設計一個 XX 系統的架構」時，面試官要看的不是你能不能畫出低層級的技術細節，而是你能不能守住 PM 的視角：

1. **先定範圍**：誰是這個系統的角色？試營運的地理範圍多大？有沒有上線前就要過的法規或資安要求？
2. **抓最小可行路徑**，不是功能清單：先讓「第一次成功完成核心動作」能跑通，評分、進階設定這類加分項都排到後面。
3. **挑一個明確的 trade-off 並正面回答**：不要含糊地說「看情況」，要講清楚選 A 犧牲什麼、換到什麼；選 B 又是相反的代價。
4. **定義指標與實驗**，證明這個選擇是對的：上線前先想清楚哪個指標會告訴你「選錯了」，而不是上線後再補。

## 今日練習題

### 題目

「你是 Meta 的技術 PM，要替一個遛狗媒合平台（dog-walking marketplace）設計產品架構——從使用者旅程、媒合邏輯、信任與安全、到金流都要考慮，並說清楚你會怎麼在媒合速度與媒合品質之間取捨。」(來源：PracHub《Technical Architecture For Product Managers》面試概念指南，Meta 技術 PM 面試情境)

### 拆解思路

1. **先問清楚範圍**：飼主、遛狗者、客服這三種角色各自的核心流程是什麼？是單一城市試營運還是全國？背景調查、保險這類安全機制是不是上線前就得有？
2. **用最小可行路徑定義 MVP**：第一次成功配對 → 完成遛狗 → 收到款，這條路徑先打通；評分系統、保險、進階路線規劃都排在後面，用「影響力 × 實作成本」決定砍什麼、為什麼砍。
3. **挑出媒合邏輯的 trade-off 並選邊站**：就近配對（greedy proximity）延遲低、使用者體驗簡單，容易在早期市場衝出規模，但媒合品質和定價控制較弱；批次拍賣式配對（batched auction）媒合品質與定價更好，但延遲更高、工程成本更高。早期市場為了把「完成媒合」的轉換率衝起來，先選就近配對，並說清楚之後要滿足什麼條件（供需比、流量規模）才切換到批次配對。
4. **信任、安全與金流是產品決策，不是丟給工程**：身分驗證、背景調查、評價、事故上報怎麼分階段上線（早期選用、規模變大後強制），儲值待結（escrow）還是即時撥款、退款窗口怎麼定，都直接影響使用者信任與現金流。
5. **定義成功指標與實驗**：供需比（DAU/MAU）、填單率（fill rate，已配對請求 ÷ 總請求）、配對時間中位數與 p90、供給側流失率，上線前用有把握的樣本量跑 A/B，分階段放量縮小出錯的影響範圍。

### 範例回答（面試時可以這樣講）

> **先收斂範圍，再談架構**：「我會先把範圍定在單一城市的試營運，角色分成飼主、遛狗者、客服三種，第一版先不做保險，但背景調查做成上線前必過的硬性條件——信任是這個產品的地基，一開始就垮了後面很難補。MVP 只要能撐住『搜尋 → 媒合 → 完成遛狗 → 付款』這條完整路徑，評分系統和進階路線規劃都先不做。」
>
> **媒合邏輯直接選邊站，不含糊**：「媒合策略我會先選就近配對：延遲低、邏輯簡單，能在早期市場快速衝出完成媒合的轉換率，讓飼主和遛狗者都願意留下來。批次拍賣式配對雖然能提升媒合品質跟定價控制，但延遲更高、工程成本也更高，在供給量還不夠厚的早期階段不值得。我會把『當日活躍遛狗者數』當成切換的觀察指標——量夠厚之後再評估要不要換成批次配對。」
>
> **指標跟護欄一起講**：「我會追蹤填單率跟配對時間 p90 作為主指標，但同時盯著供給側流失率跟事故上報率作為護欄——如果媒合速度衝得很快但遛狗者抱怨分配不公平、陸續離開，這個成長其實是在吃未來的供給。」

### 自我核對清單

用這張表檢查你的回答有沒有漏掉關鍵點：

| 核對項目 | 有提到？ |
|---------|---------|
| 有沒有先定義角色與試營運範圍 | |
| MVP 有沒有排出優先序，而不是列功能清單 | |
| 媒合 trade-off 有沒有講清楚延遲 vs 品質，並選一邊 | |
| 信任、安全與金流有沒有當成產品決策，不是丟給工程 | |
| 有沒有定義填單率、配對時間 p90 這類上線指標 | |
| 加分項：有沒有說清楚規模變大後，什麼條件會讓這個 trade-off 反過來 |

## 今日案例

**Uber 的 RFC 制度：從一個工程師的「DUCK」文件，長成按風險分級的審查流程**

Uber 在 2010 年成立，2011 年招進第一個全職工程師，到 2012、2013 年工程團隊還不到 50 人時，一名工程師做了一份叫「DUCK」的 Google 文件——名字來自「rubber duck」式的自問自答，用簡單的語言寫清楚提案、挑戰或問題，開始在新服務上線前流傳。這個做法很快被採用成標準流程：新服務上線前要寫一份 DUCK，送到訂閱清單，讓其他團隊能提早發現依賴關係。隨著 Uber 到 2016 年已經有超過 1,000 個微服務，DUCK 演化成 RFC（Request for Comment），後端、Web、行動團隊各自拉出分流的訂閱清單降低噪音，複雜提案加上「approver」欄位，要求關鍵的人讀過並署名同意或提出異議。這套機制撐住了 2017 年 Uber 為了回應 Lyft 搶先推出小費功能、在約兩個月內讓小費功能上線的速度——這次改動牽動數十個系統、超過二十個工程團隊。但當工程團隊成長到超過 2,000 人後，RFC 制度開始出問題：每週數百份 RFC 送進大型訂閱清單造成噪音、每個團隊對「什麼時候該寫 RFC」各有解讀、文件散落在不同 Google Drive 資料夾裡難以搜尋。Uber 由一位首席工程師主導,把流程整併成按風險分級的工程規劃制度:做一套可搜尋、approver 清楚標示、跟任務系統整合的工具,小改動用輕量範本,大規模或跨組織的改動用更正式的範本,最高風險的改動才需要資深工程師每週開會審查。

**面試連結**：這個案例是框架一「RFC 怎麼決定要不要寫、寫多細」最乾淨的實例——規則是跟著痛點長出來的,不是一開始就訂死。面試被問到「怎麼讓工程決策在快速成長中保持品質,又不拖慢速度」時,可以用這三個階段(個人的 DUCK 習慣 → 全組織的 RFC → 按風險分級的審查)回答,並點出轉折的訊號不是「公司變大了」,而是具體出現噪音、解讀不一致、文件找不到這三個症狀才該改制度。
