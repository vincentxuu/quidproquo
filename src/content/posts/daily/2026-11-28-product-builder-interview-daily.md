## 今日主題

Technical PM 面試裡的 API 設計題，考的不是「REST 跟 GraphQL 哪個比較潮」，而是你會不會先把模糊的抱怨（「串接起來很麻煩」）拆成具體的技術症狀，再去對應該用哪種方案解決。很多候選人一聽到「要不要換 API 風格」就直接選邊站，卻說不出來現在的 API 具體卡在哪個維度——是查詢彈性不夠、是版本管理太重、還是快取做不起來。面試官要看的是這個拆解過程，不是最終選了哪個技術。

## 核心框架速記

### API 設計決策矩陣

| 維度 | REST | GraphQL | gRPC |
|------|------|---------|------|
| 查詢彈性 | 固定回應形狀，常要組合多次呼叫 | 客戶端自訂要哪些欄位，單次查詢可拿到完整視圖 | 強型別合約，彈性介於兩者之間 |
| 版本管理 | 常見用 `/v1`、`/v2` 或日期命名版本 | 傾向用 schema 增量演進、欄位標記 deprecated，不出大版號 | 用 protobuf 欄位編號管理相容性 |
| 快取 | HTTP 快取機制成熟、直接可用 | 需要額外設計查詢層級的快取策略 | 需要自己設計快取層 |
| 學習曲線 | 低，生態成熟 | 較高，要學 schema 設計與查詢語言 | 較高，需要 proto 定義與工具鏈 |
| 適合情境 | 公開 API、資源邊界清楚、呼叫端單一 | 多種客戶端（網頁／行動／第三方）查詢需求差異大 | 內部服務間高效能通訊 |

### 技術可行性評估的三個問題

面試被問「要不要重做這個技術決定」時，先問完這三個問題再回答,而不是直接下結論：

1. **症狀有多普遍**：這個問題是所有使用者都遇到，還是特定情境（例如行動端）才出現？
2. **換了之後誰要承擔遷移成本**：既有整合方 vs 還沒串接的新開發者，成本完全不同
3. **能不能先用小範圍驗證**：有沒有辦法挑一個低風險的功能先試，而不是直接宣布全面重寫

這三個問題解決的是同一件事：**技術選型不是二選一的信仰問題，是把模糊的「用起來不爽」翻譯成具體維度，再決定要不要承擔切換的代價。**

## 今日練習題

### 題目

你的公司要開放一個新的開發者 API，讓第三方整合商串接訂單資料。工程團隊原本打算直接把內部管理後台已經在用的 REST API 開放出去，省下重新設計的時間。但業務團隊回饋，兩家目標客戶的工程師在 demo 時抱怨：光是組出一筆訂單的完整檢視（基本資料、商品明細、物流狀態）就要打五次 API，而且每次回應裡有一半欄位他們根本用不到。你會建議工程團隊怎麼做？

(來源：自擬，整合 Soreno.ai 技術 PM 面試準備重點與 GitHub 2016 年推出 GraphQL API 時遇到的「過度抓取／抓取不足同時發生」問題)

### 拆解思路

1. **釐清問題**：先問清楚「打五次 API」是所有整合商都這樣，還是特定使用情境（例如行動端報表 vs 後台管理介面）才這樣——症狀的普遍程度決定要不要動到核心架構。
2. **定義使用者**：區分兩種使用者：已經在用現有 REST API 的既有客戶（換了要承擔遷移成本），和還沒串接的新開發者（換了幾乎無痛）。
3. **結構化分析**：用 API 設計決策矩陣，把「打五次 API」「欄位用不到一半」這兩個症狀，分別對應到「查詢彈性」和「過度抓取」兩個維度，而不是籠統說「REST 不夠好」。
4. **提出方案**：不要讓工程團隊直接重寫整個對外 API。先挑一個範圍小、風險低的功能（例如訂單查詢這個單一場景）做 GraphQL 層的驗證,確認真的能解決抱怨,再決定要不要擴大範圍。
5. **定義成功**：用「組裝一次完整資源平均要打幾次 API」和「回應裡實際被使用到的欄位比例」這兩個數字，做驗證前後的對比指標，而不是憑感覺說「開發者體驗變好了」。

### 範例回答（面試時可以這樣講）

> **先拆症狀，不先選技術**：客戶說「串接很麻煩」,我會先去問清楚這個麻煩具體發生在哪一步。如果答案是「要打五次 API 才能組出一筆訂單」,這其實是兩個不同的症狀：一個是查詢彈性不夠（沒辦法一次拿到跨資源的完整視圖）,一個是過度抓取（拿到的欄位用不到一半）。這兩個症狀剛好都是 REST 風格在處理多資源組合查詢時常見的痛點。
>
> **不直接重寫，先切小範圍驗證**：但我不會因為兩個客戶抱怨就建議把整個對外 API 重寫成 GraphQL,因為既有整合商已經在用現在的 REST API,重寫等於逼他們一起遷移。我會建議先挑訂單查詢這一個場景做 GraphQL 層的小範圍驗證——跟那兩家抱怨的客戶一起測,看看「平均組裝一次訂單視圖要打幾次 API」這個數字有沒有真的從五次降到一次。
>
> **用數字決定要不要擴大範圍**：如果驗證結果是明顯改善,而且其他整合商的查詢模式也差異很大（像有的只要基本資料、有的要完整物流追蹤）,那就有理由把 GraphQL 層擴大到更多資源;如果只有這兩家客戶的用法特殊,維持現有 REST、額外開一個組合查詢的 batch endpoint 可能成本更低。决定權不是我一個人憑喜好拍板,是看驗證出來的數字。

## 今日案例

**GitHub：先拿一個小功能驗證 GraphQL，再決定要不要全面換血**

GitHub 在 2016 年對外說明他們為什麼要在既有 REST API 之外，再推出 GraphQL API。當時 GitHub 的 REST API 已經占到資料庫層超過 60% 的請求量，原因之一是 hypermedia 導向的設計要求客戶端不斷來回請求才能拿到完整資訊——組出一個資源的完整視圖經常要打兩三次 API，而且每次回應裡塞滿了供導覽用的 `*_url` 欄位，整合方同時抱怨「資料太多」又「資料不夠」。GitHub 工程團隊原本準備照慣例推出 REST APIv4 來解決這個問題,但盤點需求後發現還想要更細的 OAuth scope 資訊、更聰明的分頁、型別安全、自動產生文件與客戶端——比對過幾種既有 API 規範後,沒有一個完全符合,才找到 GraphQL。他們沒有直接把整套 REST API 搬過去,而是在 Platform 團隊內先挑了一個範圍很小的功能——留言的 emoji reactions——用 GraphQL 重新實作，確認可行之後才逐步把個人檔案頁、star 數、watch 功能等社交功能搬過去，用 Scientist 這個內部工具比對新舊兩套實作的結果差異，最後才讓 GraphQL 進入正式環境對外開放。

**面試連結**：這個案例可以直接拿來回答「要不要換技術方案」類的題目——重點不是「REST 跟 GraphQL 哪個比較好」，是「先用小範圍驗證降低承諾的風險，再決定要不要擴大」。
