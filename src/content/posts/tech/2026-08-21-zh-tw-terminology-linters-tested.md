LLM 的中文語料以中國內容為大宗，所以它寫出來的「繁體中文」常常是**字形正確、詞彙錯誤**：軟件、視頻、用戶、質量。我想把手工維護的 18 條 grep pattern 換成有人維護的工具，找到五個候選，全部實測。

過程中我測錯了一次，而且差點就照著錯的數字下結論。那段比工具比較本身更值得寫，所以放在前面。

## 五個候選是什麼

**[zhtw-mcp](https://github.com/sysprog21/zhtw-mcp)**（sysprog21，MIT，Rust）依據教育部《重訂標點符號手冊》與《國字標準字體》，跨海峽詞彙以 OpenCC 的 TWPhrases／TWVariants 為基礎，1,882 條詞彙規則。CLI 與 MCP 雙介面，歧義詞會反問宿主 AI 助理。

**[twlint](https://github.com/HCYT/twlint)**（npm 上是 `@termdock/twlint`，Apache-2.0）ESLint 風格的 CLI，兩條規則：`simplified-chars`（error）與 `mainland-terms`（warning），詞庫分八個領域約 1,946 條。

**[Chinese-Vocabulary-Radar](https://github.com/aronhack/Chinese-Vocabulary-Radar)** 是 Chrome 擴充功能，詞庫是單一個 CC0 的 JSON，788 筆。

**[tongwen-dict](https://github.com/tongwentang/tongwen-dict)** 是新同文堂的辭庫，詞彙表 7,186 條。

**[OpenCC](https://github.com/BYVoid/OpenCC)** 的 `s2twp`，簡體轉台灣正體並套台灣詞彙，是這個領域的事實標準。

## 我第一次測錯了

第一輪我取 120 篇文章（`ls src/content/posts/*/*.md | head -120`），跑完得到這組數字：

| 來源 | 命中 | 精確率 |
|---|---|---|
| twlint `--deep` | 1,588 | 0.3% |
| Chinese-Vocabulary-Radar | 1,463 | 0.3% |

我差點就寫成「現成詞庫全部不能用」。

後來查了一件事：**那 120 篇裡，`用戶`、`視頻`、`網絡`、`質量`、`軟件`、`界面` 出現次數全部是 0。**

樣本裡根本沒有要找的東西。精確率的分子必然接近零，跟工具好壞無關。唯一被算成真陽的 5 次是「調用」。

**在一份沒有陽性的樣本上量精確率，量到的是抽樣，不是工具。** 我用的是 `head -120`，按檔名排序，於是拿到的幾乎全是同一批 AI 分類的文章。

## 重測

改用**確實含有中國用語的 109 篇**（用站內既有的 18 條 pattern 篩出來的），這批共有 567 次真陽性。同時把 zhtw-mcp 加進來：

| 工具 | 報出問題 | 真陽 | 精確率 | 召回 |
|---|---|---|---|---|
| **zhtw-mcp**（cross_strait） | 1,888 | 556 | **29.4%** | **85.2%** |
| twlint `--deep` | 2,522 | 535 | 21.2% | 82.5% |

召回都在八成以上。這跟第一輪的「0.3%」是完全不同的結論——**兩個工具都能找到問題，差別在噪音量與噪音的性質。**

（這組數字本身也修過一次。第一次算出 25.6% / 18.6%，是因為我的真值清單只有 17 個詞，把工具抓到的真中國用語算成了假陽性——下面〈工具修正了我的清單〉那節說明。）

## 工具修正了我的清單，兩個方向都有

算精確率要有真值。我用的是站上既有的 18 條 pattern——結果那份清單本身有錯，而 zhtw-mcp 把兩個方向都指出來了。

**它抓到五個我沒列的真中國用語：**

| 詞 | 站內次數 | zhtw-mcp 報 | 台灣說法 |
|---|---|---|---|
| 激活 | 23 | 23 | 啟用 |
| 插件 | 19 | 19 | 外掛 |
| 反饋 | 17 | 17 | 回饋 |
| 智能 | 21 | 8 | 智慧 |
| 兼容 | 1 | 1 | 相容 |

「智能」只報 8/21，是因為它有語境條件，沒把「人工智慧」誤報。同理「質量」站內 14 次只報 3 次——物理語境被排除掉了。

**它也擋下一個我誤列的。** 我的 pattern 把「審計」當中國用語，站內 36 次。zhtw-mcp 一次都沒報，而它是對的：這 36 次全是「SOC2 審計」這種語境，而審計部是中華民國的機關，這個詞在台灣是正規用語。

主要詞的實測抓取率：

| 詞 | 文章裡 | zhtw-mcp 報 |
|---|---|---|
| 用戶 | 424 | 418 |
| 信號 | 52 | 51 |
| 視頻 | 4 | 3 |
| 界面 | 4 | 3 |
| 審計 | 36 | 0（正確不報） |

## 噪音的性質比數字重要

兩者的精確率只差八個百分點，但誤判的**種類**差很多。

### twlint：195 個 error 級判斷，全是把正體字當簡體字

| 它說 | 出現次數 | 問題 |
|---|---|---|
| 簡體字「干」→「幹」 | 60 | 干擾、干預、若干 |
| 簡體字「污」→「汙」 | 47 | 兩者皆為正體，非簡繁關係 |
| 簡體字「只」→「隻」 | 15 | 只是、只有 |
| 簡體字「占」→「佔」 | 14 | 占卜、占星 |
| 簡體字「岩」→「巖」 | 7 | 岩是正體標準字形 |
| 簡體字「准」→「準」 | 6 | 准許、批准 |

這一整類是 error 級而且 `--fix` 會動它。跑下去會把「只是」改成「隻是」、「干擾」改成「幹擾」。

### zhtw-mcp：誤判是用詞主張，不是字形破壞

| 它說 | 出現次數 | 我的判斷 |
|---|---|---|
| 場景 → 情境 | 122 | 有道理但我不打算改 |
| 開源 → 開放原始碼 | 19 | 正式文件對，部落格太累贅 |
| 循環 → 迴圈 | 2 | 程式語境對 |
| 函式 → 函數 / 函數 → 函式 | 各 1 | 兩個方向都有規則，內部不一致 |

這些是**可以爭論的立場**，不是壞掉的字。你不同意就關掉那條規則，不會有東西被改壞。

## zhtw-mcp 的規則設計

翻它的 `assets/ruleset.json`，1,882 條規則裡有 413 條（22%）帶防誤殺機制：66 條有 `exceptions`、349 條有 `context_clues`、72 條有 `negative_context_clues`。

三個直接對上我遇到的坑：

**`文件 → 檔案` 被主動標成 `disabled`**，理由寫在資料裡：

> tw 「文件」= document (正確用法)；cn 「文件」= file。裸詞歧義無法消歧，停用以避免誤判。複合詞 (文件夾→資料夾、頭文件→標頭檔) 不受影響

同一個詞，twlint 報了 50 次，Chinese-Vocabulary-Radar 報了 632 次。

**`用戶 → 使用者` 帶 `exceptions: ["用戶端", "用戶端作業系統"]`。**

**`只` 的規則方向是反的**：`隻 → 只`，type 標 `confusable`，說明是「OpenCC 轉換時可能誤植『只』(only) 為『隻』」。twlint 剛好把這個 bug 當成規則。

還有一個發生在建置階段：產生字元轉換表的 `gen-s2t-tables.py` 會印出 **「Ambiguous: 15 chars excluded」**——一簡對多繁的歧義字直接排除在自動轉換之外。twlint 那 195 個 error 全部屬於這一類。

`優化` 那條則帶 `context_suggestions`：出現「微服務／服務端／用戶端」建議「最佳化」，出現「流程／體驗／服務／營運」建議「改善／提升」。官方文件解釋了為什麼不把兩組都塞進 `to`——那會讓 IT 語境也失去自動修復。

## tongwen 與 OpenCC 為什麼結構上就不行

這兩個是最成熟的專案，但**方向反了**。實測 tongwen-dict 的詞彙表：

```
视频 → 視訊       ✓ 在詞庫
視頻 → ✗ 不在詞庫
软件 → 軟體       ✓ 在詞庫
軟件 → ✗ 不在詞庫
用户 → 使用者     ✓ 在詞庫
用戶 → ✗ 不在詞庫
```

7,186 條的 key 全部是**簡體字**。OpenCC 的 `s2twp` 同理。

而 LLM 產出的問題文本是**字形已經是繁體、詞彙是中國的**。「視頻」不是「视频」，簡繁轉換器看它就是個已經轉好的正常詞。

這不是 bug，是設計目標不同：它們解「把簡體文章轉成台灣看得懂的樣子」，我要的是「檢查一篇本來就是繁體的文章裡有沒有中國詞」。輸入形態不一樣，詞庫的 key 就不一樣。

## 結論：用工具校準清單，用清單當閘門

測完之後我沒有把 zhtw-mcp 接進 CI，因為它的噪音散在 **187 個不同的詞**上——關掉最吵的 50 條也只消掉 79%，109 篇還剩 294 次，平均每篇 2.7 次。當 pre-commit 硬閘門太吵。

但它做到一件更有價值的事：**把我那份手工清單的兩個錯都指出來了**——補五個、拿掉一個。

所以分工是這樣：

| 角色 | 用什麼 | 為什麼 |
|---|---|---|
| **閘門**（每次 commit 擋） | 你自己的窄清單 | 零噪音，紅燈就一定要看 |
| **健檢**（定期跑一次） | zhtw-mcp | 找出「你不知道自己在用」的中國用語，拿去擴充清單 |
| 簡繁轉換 | OpenCC / tongwen | 它們本來就是做這個的 |

具體操作：

1. **zhtw-mcp 先關掉你站上刻意要用的詞**。它支援專案層 `.zhtw-mcp.toml` 與使用者層 `overrides.json`，官方文件的範例正好就是停用「優化」：

   ```json
   {"from": "優化", "to": ["最佳化"], "type": "cross_strait", "disabled": true}
   ```

   以我的規範要關的是優化、數據、場景、開源、設備。
2. **不要開 `--fix` 直到你讀完一輪報告。** twlint 的教訓：能自動修的規則裡有 195 條會把字改壞。
3. **拿含有問題的樣本測，不要隨機抽。** 這是我這次最大的錯——`head -120` 抽到一批沒有陽性的檔案，量出 0.3%，差點寫成「全部不能用」。
4. **定期把工具的報告當候選清單看**，不是當待辦清單修。它報 1,888 次，你要挑的是那五個該進清單的詞。

最後一件事：我第一版文章寫完、跑完驗證、連外部連結都檢查過了，才發現抽樣是錯的；改完之後又發現真值清單也是錯的。**格式全綠不代表方法對，而方法對了也不代表你的判準對。**

## 如果你不寫程式

上面整篇都在講指令和設定檔，但被 AI 寫出「軟件、視頻、用戶」困擾的人，多半是在 ChatGPT、Word、Notion 裡寫東西，不是在 repo 裡。這一節給你。

### 最省事：裝一個瀏覽器擴充功能

[中國用語雷達](https://chromewebstore.google.com/detail/lecgchakaccigfbbaeialhjplbmgipge)（Chrome）裝好之後，你在網頁上看到的中國用語會被標成黃色——包含你在 Google Docs、Notion、ChatGPT 對話框裡寫的字。不用設定，不用學指令。

它只標不改，要不要改你自己決定。這反而是對的：**沒有工具能替你判斷「質量」在你這句話裡是不是物理**。

### 貼上去就好：線上轉換

- [繁化姬](https://zhconvert.org/)：貼文字，選「台灣化」，它會轉簡繁並套台灣用詞
- [Taiwan.md 用語轉換器](https://taiwan.md/terminology/converter/)：3,901 條對照規則，會標出改了哪裡

兩個都不用註冊。缺點是要手動貼來貼去，長文很累。

### 直接叫 AI 幫你對照

如果你本來就在用 ChatGPT 或 Claude 寫稿，最簡單的做法是把詞表丟給它：

```
請根據這份對照表，檢查以下文字裡有沒有中國用語，
只列出來不要直接改：
https://raw.githubusercontent.com/aronhack/Chinese-Vocabulary-Radar/refs/heads/main/chrome-extension/taiwan_china_vocabs.json

（貼上你的文字）
```

**「只列出來不要直接改」這句很重要。** 讓它直接改，你會失去判斷的機會，而它一定會改錯幾個。

### 不管用哪個工具，這四件事一樣

這是我這次踩出來的，跟工具無關：

**一、工具會把你領域裡的正常詞當成錯的。** 我寫無人機，文章裡每一個「質量」都是物理學的質量；我寫 AI，每一個「激活」都是神經網路的 activation。工具全部標紅。你要能認出哪些是你的專業詞彙。

**二、引用別人的話不要改。** 你引述一個中國受訪者說「這個視頻的質量真的不行」，那八個字一個都不能動——改了就是竄改引文。

**三、專有名詞不要改。** 「北京人工智能研究院」是機構的名字。「博客來」是書店，不是「部落格來」。

**四、批次取代之前先看過一遍。** 我這次用程式一次改 419 個地方，事前先跑了一次「只看不改」，結果抓到三個會出事的：「激活」改掉會毀掉所有 AI 段落、「貼標」會變成「貼上標籤籤」、還有它把這篇文章本身也改了——因為這篇在討論這些詞。

第四點對用 Word「全部取代」的人一樣成立。**先按「尋找」看過所有結果，再決定要不要按「全部取代」。**

### 一個更根本的建議

與其事後抓，不如**在 AI 寫之前就講清楚**。在 ChatGPT 的自訂指令、或 Claude 的 Project 說明裡加一段：

```
用台灣的中文寫。不要用：軟件、視頻、用戶、質量、默認、
插件、兼容、屏幕、鼠標、賦能、抓手、閉環、對標、復盤。
對應要寫成：軟體、影片、使用者、品質、預設、外掛、相容、
螢幕、滑鼠。
```

這比事後校對省力得多，而且列出「不要用什麼」比說「請用台灣用語」有效——後者太抽象，模型不知道你指的是哪些詞。

## 如果你有 repo（給工程師）

把上面那套做成 CI 檢查的話，順序是這樣：

### 1. 先做一份你自己的窄清單

不要從別人的 1,000 條詞庫開始。從**你確定不能用的十幾個詞**開始，分兩級：

- **A 級**：台灣沒有正當用法，紅燈擋 commit（用戶、視頻、軟件、插件…）
- **B 級**：看語境，只提示（質量、智能、信號、反饋…）

### 2. 排除四種區域，否則一定誤殺

| 區域 | 為什麼 |
|---|---|
| 程式碼與行內程式碼 | 變數名不是中文寫作 |
| 連結網址 | URL 裡的字不是你寫的 |
| blockquote 引述原文 | 引文一個字都不能改 |
| 參考資料的外部文章標題 | 別人的標題不該被你改 |

還要有詞層的 carve-out：`用戶` 會match到台灣正規的「用戶端」、`對標` 會match到「針**對標**註」、`博客` 會match到「博客來」。

另外**要能排除整篇文章**——像這篇在討論這些詞，被檢查就會誤判。

### 3. 用 zhtw-mcp 校準清單，不是取代清單

跑一次，讀報告，問自己「這個詞該不該進我的清單」。跑之前先在 `overrides.json` 關掉你刻意使用的詞。

### 4. 批次替換一定要先 dry-run

理由見上一節第四點。

### 5. 全綠之後才接成閘門

我的順序：寫檢查（只報告）→ 清 419 處 → 剩下 8 處人工改 → A 級歸零 → 才接進 `pnpm verify`。倒過來做會擋死所有人。
